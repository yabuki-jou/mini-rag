# 项目分析

## 软件目标

本项目为工程项目资料提供“上传、解析、人工确认、正式索引、受控检索和引用问答”的本地智慧档案工作台后端。一次成功运行必须在已认证用户的项目范围内，只从已确认且未被删除阻断的档案中返回可定位的原始 Chunk；若没有可靠证据，则应返回空证据，由上层问答服务拒绝编造答案。它不是公开部署的多租户产品，也不把历史 Milvus 或单文档 canary 当作当前 Chroma 质量结论。

## 目标用户与价值

目标用户是学习 AI 应用和 Agent 工程的开发者，以及在本地环境演示项目资料归档流程的小范围使用者。其价值在于把人工确认的业务事实、PostgreSQL 授权范围、Chroma 向量候选、本地模型和引用溯源放在同一条可验证链路中：模型只帮助匹配和排序，确认状态、资源归属、删除可见性和审计仍由确定性服务控制。

## 能力清单

1. 项目档案处理：上传 TXT、Markdown、PDF 或 DOCX，解析并保留版本化快照与定位信息。
2. 人工确认与索引：将已确认字段、字段证据与 Final Chunk 写入 PostgreSQL 和 Chroma，并支持取消确认和物理删除。
3. 正式档案检索：在受认证用户、项目、知识库和正式文档范围内，返回带文件名、定位和原文摘录的 Top-K 证据。
4. 证据问答：仅依据正式检索证据组织答案；证据为空时拒答，而不是生成无依据结论。
5. Agent 制度检索：在会话绑定的知识库范围内，由服务端注入身份与知识库上下文后执行只读检索。
6. 审计与恢复：对关键操作写入脱敏审计，并在跨 PostgreSQL、Chroma 和文件系统失败时提供受控恢复路径。

## 真实输入特征

- 档案文件可能是 20 至 1,000,000 字符的中文工程资料，包含段落、编号列表、表格化文本、页码或行号定位；PDF 还可能是短文本或无法提取正文的扫描件。
- 检索问题通常是 1 至 2,000 个字符的中文自然语言，可能出现口语省略、字段名称与正文表达不一致、同义表述和跨段落信息需求。
- 一个项目含多份档案，每份档案可生成多个 Final Chunk；正确证据可能不是 Chroma 距离最近的片段，但引用仍必须保留原始文件名和位置。
- 真实访问带有项目边界：客户端可能猜测 UUID、重复请求确认/删除，或查询已取消确认、已删除和其他项目的档案。

## 困难点与失败模式

1. 候选排序错误：正确证据进入 Chroma 候选集，但 dense cosine distance 仍让同文档错误片段或无据片段排在前面。
2. 无据误命中：阈值放宽后，无据问题获得看似相关的向量候选；阈值收紧又会滤掉有据问题的正确证据。
3. 授权与可见性绕过：Chroma 返回的元数据与 PostgreSQL 确认/删除状态不一致，或不属于当前用户、项目、知识库和正式文档范围。
4. 引用失真：为向量化加入的字段上下文被错误地作为 API 引用正文返回，或重排后丢失原始 Chunk 的定位。
5. 外部依赖失败：本地 Embedding、Chroma 或后续 Reranker 模型不可用；服务不得静默使用另一种检索策略并把它当成已验证质量结果。
6. 跨存储残留：取消确认或物理删除后，PostgreSQL、Chroma 与文件系统的可见性和清理状态不一致。
