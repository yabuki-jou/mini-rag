# 项目档案助手评测项目分析

## 软件解决的问题

项目档案助手面向工程项目资料管理人员，在已登录且已绑定单一项目的持久会话中，帮助用户浏览已经
人工确认的正式档案，并针对档案原文提问。成功的一轮交互不是“模型给出像答案的文本”，而是模型在
服务端限定的用户、项目和知识库范围内选择正确的只读工具，服务端只依据正式档案生成目录或证据回答，
证据不足时稳定拒答，同时返回可追溯且不暴露内部标识和检索分数的引用。

## 目标用户与价值

目标用户是需要在一个工程项目内快速查找文件、登记字段和原文事实的档案管理或项目管理人员。相比
直接把全部文件交给通用聊天模型，本应用把人工确认状态、项目隔离、检索范围、引用和拒答都放在
服务端控制，重点价值是“可追溯且不越权”，而不是开放式聊天或自由生成内容。

## 能力清单

1. 正式目录导航：按文档类型、项目阶段、日期、编制单位和分页浏览当前项目正式档案的五个登记字段。
2. 原文证据问答：对用户问题检索当前项目正式档案的 Top-8 候选，再由公共 D5/D6 判定层决定回答或拒答。
3. 多轮会话：在同一持久线程中保留完整用户/助手轮次，使后续追问可以使用此前已确认的对话上下文。
4. 可信引用：回答只返回文件名、位置范围和原文摘录，不返回 document/chunk 标识或检索分数。
5. 安全拒答：零候选或证据不足时返回固定拒答，不能利用常识、相似主题或其他项目资料补全事实。
6. 范围隔离与审计：用户、项目、知识库和会话类型由服务端注入，工具调用只保存脱敏摘要并支持重试去重。

## 真实输入特征

- 用户消息为 1～2000 个 Unicode 码点，可能包含口语化省略、换行、同义改写、日期或机构筛选条件。
- 单项目最多 100 份文档，正式检索只包含 `CONFIRMED` 且未被删除流程阻断的 TXT、MD、PDF、DOCX 档案。
- 文档可能跨页或跨段，字段值与原文事实可能位于不同 Chunk；正式候选固定为最多 Top-8。
- 目录问题可能带多个筛选条件和分页；事实问题可能需要从相近文件中区分版本、日期、金额、单位或审批结论。
- 多轮输入既包含第二轮省略主语的追问，也包含从目录导航切换到指定档案原文事实的追问。
- 固定评测基线按已确认计划复用 8 个有据、2 个无据、2 个项目隔离问题，另增加 2 个目录场景和
  2 组两轮追问；Ground Truth 只能保留在离线评测元数据中。

## 难点与失败模式

1. 工具路由错误：目录问题误用证据工具，或事实问题不调用工具直接回答，会造成不完整结果或幻觉。
2. 证据充分性误判：高相似候选只讨论相近主题却不包含所问事实，模型可能据此编造金额、日期或责任单位。
3. 项目范围越界：同名项目、文件或知识库中的其他用户/项目资料可能被误检索并泄露。
4. 引用错位：两次工具调用或候选重新编号后，回答引用可能指向错误文件、位置或摘录。
5. 多轮上下文漂移：第二轮追问可能丢失当前项目、线程或上轮对象，或者把早先工具结果当成当前轮证据。
6. 内部数据泄漏：模型参数、ToolMessage、响应或 Trace 可能暴露 user/project/kb、document/chunk 标识、
   检索分数、完整正文或查询原文。
7. 重试副作用：模型、工具或判定层重试可能重复写可见消息或审计记录，或突破单轮两次工具调用上限。
8. 删除与可见性竞争：删除中的文档或已删除项目会话如果仍可被目录、问答或历史入口使用，会破坏正式范围。
