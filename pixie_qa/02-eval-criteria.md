# 评估标准

## 使用场景

1. 有据档案查询（常规）：用户询问已确认档案中的字段或正文事实，检索必须返回包含人工标注证据的原始 Chunk。
2. 同文档相近片段查询（困难）：问题与多个同一文件 Chunk 都有表面关联，排序必须将真正支持结论的片段排在无关片段之前。
3. 无据问题（困难）：项目资料不能支持问题时，检索必须在阈值筛选后返回空证据，供问答层明确拒答。
4. 跨项目探测（安全）：用户查询当前项目时，即使另一项目存在匹配正文，也不得返回另一项目的文件或摘录。
5. 模型依赖故障（异常）：本地 Reranker 不能加载或推理失败时，接口应返回稳定错误，而不是悄悄改用未验证的排序策略。

## 评估标准

| # | 标准 | 适用范围 | 需要观测的数据 |
| --- | --- | --- | --- |
| 1 | 已确认问题的返回项是否包含与 Ground Truth 文件、定位和摘录一致的原始证据，而非仅词面相近的 Chunk。 | 场景 1、2 | `archive_retrieval_result`、固定集标准证据匹配结果 |
| 2 | 无据问题在独立重排阈值下是否返回空证据，避免上层问答依据伪相关 Chunk 生成答案。 | 场景 3 | `archive_retrieval_result`、阈值计分结果 |
| 3 | 检索范围是否始终局限于 Bearer 身份所属项目的正式文档，且 Reranker 前已完成元数据校验。 | 场景 1–4 | `archive_retrieval_scope`、`archive_retrieval_result` |
| 4 | 重排是否只改变候选顺序和筛选，不改变返回项的原始文件名、定位、Chunk ID 与摘录。 | 场景 1、2 | `archive_retrieval_result`、服务级候选投影 |
| 5 | 本地 Reranker 故障是否显式可见，并且不将纯 Chroma 结果伪装成重排结果。 | 场景 5 | Reranker 服务错误码、HTTP 响应 |

标准 1 和 2 是语义标准：即使响应 JSON 结构正确，只要错误 Chunk 排在前面或无据问题出现候选，就应失败。标准 3 至 5 验证安全与可复现性边界。

## 能力覆盖

已覆盖：项目档案正式检索、证据问答的检索前提、授权隔离、Reranker 故障处理。

暂不覆盖：上传/解析、人工确认、物理删除与 Agent 制度检索；这些能力已有独立确定性测试，且本轮 P14 的唯一变量是候选重排。真实 DeepSeek 问答质量必须在检索固定集通过后另行评估。
