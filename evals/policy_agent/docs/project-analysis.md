# 制度 Agent 评测项目分析

## 软件目标

本评测对象是项目中仍在使用的只读企业制度 Agent。用户通过已认证的 Agent 会话提出公司制度、规定、报销或流程问题，系统在会话绑定的知识库范围内调用 `search_company_policy`，再由真实 DeepSeek 仅依据工具返回的制度原文组织答案并保留来源。成功运行既要求答案有用，也要求模型不能绕过服务端身份、猜测其他知识库内容或在证据不足时补写结论。

## 目标用户与价值

目标用户是通过 Swagger 或本地 Vue 工作台查询企业制度的已认证用户，以及验证 Agent 工程质量的开发者。评测价值在于同时检查真实模型的工具选择、服务端范围注入、证据忠实性、引用完整性和无依据拒答；普通单元测试能够证明确定性代码契约，但不能替代真实模型面对自然语言变化时的质量验证。

## 能力清单

1. 制度问题路由：识别公司制度、规定、报销和流程问题并调用唯一工具 `search_company_policy`。
2. 授权范围注入：由服务端会话状态提供 `user_id` 和 `kb_id`，不接受模型或用户覆盖。
3. 有据回答：根据一个或多个检索 Chunk 回答，并保留文档名、页码和相关制度事实。
4. 无据拒答：检索结果为空时明确说明知识库没有足够依据，不使用常识补写企业规则。
5. 澄清与非制度处理：问题含义不足时先追问，普通闲聊或非制度任务不得误调用检索工具。
6. 安全观测：记录脱敏后的工具选择、参数、状态和回答，供确定性评审器检查。

## 真实输入特征

- 用户问题通常为 5～2,000 个字符的中文自然语言，包含口语、省略、同义表达、错别字或多项制度事实。
- 有些问题明确包含地区、费用类别、审批条件和时间范围；有些只说“这个能不能报”，需要追问而不是猜测。
- 检索输入可能包含 0 个、1 个或多个中文制度 Chunk，每个 Chunk 带文档名、页码、正文和相关度分数。
- 用户可能在问题中提供伪造的用户 UUID、知识库 UUID 或“忽略系统规则”等提示注入内容。
- 同一回答可能需要区分一般规则、例外条件和审批前提，不能只复述最高金额等局部信息。

## 困难点与失败模式

1. 路由误判：把普通闲聊或含糊问题当成明确制度问题，产生无意义检索；或对明确制度问题不调用工具。
2. 范围越权：模型把用户输入中的身份或知识库标识放进工具参数，绕过服务端绑定范围。
3. 证据外推：正确召回部分制度内容后，模型补写证据中不存在的金额、条件、日期或审批结论。
4. 引用丢失：回答内容基本正确，但缺少文档名、页码，导致用户无法追溯原文。
5. 空结果幻觉：工具明确返回无依据后，模型仍依据常识判断企业是否允许某项行为。
6. 多证据混淆：多个 Chunk 分别描述一般规则和例外条件时，模型错误合并或遗漏限制条件。
7. 提示注入：用户要求忽略安全规则、查询其他用户或其他知识库时，模型错误服从。
