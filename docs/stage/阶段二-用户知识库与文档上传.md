## 3. 三种存储的分工

当前项目不是把所有数据都保存在同一个地方，而是使用三种存储。

| 存储 | 当前保存内容 | 主要作用 |
|---|---|---|
| SQLite | 用户、知识库、文档元数据和状态 | 业务管理和权限判断 |
| 文件系统 | TXT、Markdown、PDF、DOCX 原文件 | 保存待解析的原始内容 |
| Milvus | 阶段三写入 Chunk、向量和关联字段 | 向量检索 |

当前关系：

```text
SQLite
User
  └─ KnowledgeBase
       └─ Document
            │
            ├─ storage_path → 文件系统中的原文件
            │
            └─ document_id  → 阶段三关联 Milvus Chunk
```

SQLite 与 Milvus 不是主从数据库关系，也不存在跨数据库外键。应用通过相同的 `user_id`、`kb_id` 和 `document_id` 维持关联。

阶段二上传链路没有调用 Milvus，因此 Milvus 暂时关闭也不影响用户、知识库和上传接口。阶段三开始前需要重新启动 Milvus。

## 4. 数据库模型

### 4.1 DocumentStatus

```text
UPLOADED      原文件已保存，尚未解析
PROCESSING    正在解析、切分或向量化
READY         已完成向量入库，可以检索
FAILED        解析或入库失败
DELETING      正在删除关联资源
DELETE_FAILED 删除失败，可以重试
```

枚举必须真正赋值：

```python
UPLOADED = "UPLOADED"
```

只写：

```python
UPLOADED: str
```

只是类型注解，不会创建枚举成员。

### 4.2 User

```text
id          UUID 主键，自动生成
name        显示名称，1～100 字符，建立索引
created_at  UTC 创建时间
updated_at  UTC 更新时间
```

`id` 使用：

```python
Field(default_factory=uuid4, primary_key=True)
```

不能写成 `default_factory=uuid4()`，因为后者会在定义模型时立即调用函数。

### 4.3 KnowledgeBase

```text
id          UUID 主键
owner_id    外键指向 users.id
name        知识库名称
created_at  UTC 创建时间
updated_at  UTC 更新时间
```

`owner_id` 表示知识库的所有者。客户端不能提交或覆盖该字段，它必须来自已经验证的当前用户。

### 4.4 Document

```text
id             UUID 主键
kb_id          外键指向 knowledge_bases.id
filename       安全文件名
storage_path   服务器内部文件路径
content_hash   64 字符 SHA-256
status         默认 UPLOADED
chunk_count    默认 0
error_message  默认 None
created_at     UTC 创建时间
updated_at     UTC 更新时间
```

上传完成时：

```text
status = UPLOADED
chunk_count = 0
```

它表示文件已经保存，但没有解析、切分或写入 Milvus。

## 6. API Schema 与数据库 Model

数据库模型描述完整记录，API Schema 决定客户端可以提交和看到哪些字段。

```text
UserCreate          客户端只能提交 name
UserRead            返回 id、name 和时间

KnowledgeBaseCreate 客户端只能提交 name
KnowledgeBaseRead   返回 id、owner_id、name 和时间

DocumentRead        返回文档信息，但隐藏 storage_path
```

请求 Schema 使用：

```python
model_config = ConfigDict(extra="forbid")
```

这样客户端额外提交 `id` 或 `owner_id` 时返回 HTTP 422，而不是静默忽略。

响应 Schema 使用：

```python
model_config = ConfigDict(from_attributes=True)
```

它允许 Pydantic 从 SQLModel 数据库对象读取属性。

`DocumentRead` 不返回 `storage_path`，因为绝对路径是服务器内部信息，暴露它没有业务价值，还可能泄露目录结构。

## 7. Session 的作用

Session 是一次数据库操作过程的工作单元，不是数据库本身，也不会把 SQLite 全部内容加载进内存。

它负责：

- 查询数据库。
- 跟踪新增、修改和删除的对象。
- 管理事务。
- 在需要时从 Engine 获取连接。
- 提交、回滚并关闭数据库操作。

```text
HTTP 请求
→ get_session() 创建 Session
→ 路由和依赖查询或写入
→ commit 或 rollback
→ 请求结束
→ with 退出并关闭 Session
```

直接调用：

```python
session = get_session()
```

得到的是生成器，不是 Session。FastAPI 需要通过 `Depends(get_session)` 执行到 `yield`，取得真正的 Session，并在请求结束后继续完成关闭逻辑。

## 8. 身份模拟与知识库权限

当前项目没有真正的登录系统，使用请求头模拟身份：

```text
X-User-ID
→ FastAPI 校验 UUID 格式
→ SQLite 查询 User
→ 不存在则返回 401
→ 将 User 注入路由
```

知识库权限：

```text
路径 kb_id
→ 查询 KnowledgeBase
→ 不存在返回 404
→ 比较 knowledge_base.owner_id 与 current_user.id
→ 不相等返回 403
→ 相等则返回 KnowledgeBase
```

状态码：

| 场景 | HTTP | 业务代码 |
|---|---:|---|
| 缺少请求头 | 422 | `VALIDATION_ERROR` |
| UUID 格式错误 | 422 | `VALIDATION_ERROR` |
| 用户不存在 | 401 | `INVALID_USER` |
| 知识库不存在 | 404 | `KNOWLEDGE_BASE_NOT_FOUND` |
| 不是知识库所有者 | 403 | `KNOWLEDGE_BASE_FORBIDDEN` |

`X-User-ID` 不是安全认证。知道其他用户 UUID 的客户端可以伪造身份，所以它只能用于当前学习阶段。

## 9. 重复用户名

当前 `User.name` 是显示名称，不是登录账号，因此允许重复。真正区分用户的是 UUID。

```text
name = 张三，id = UUID-A
name = 张三，id = UUID-B
```

二者仍然是不同用户。

生产系统通常拆分为：

```text
id             唯一 UUID
username/email 唯一登录标识
display_name   可重复显示名称
password_hash  密码哈希
```

因此当前阶段不需要给显示名称增加唯一约束。真正的登录、密码、JWT 和注销计划在后续 Spring Boot 工程化阶段实现。

## 10. 文件名安全

允许的文件类型：

```text
.txt
.md
.pdf
.docx
```

文件名处理：

```text
原始 filename
→ 检查 None 和空白
→ 同时处理 / 和 \\ 路径分隔符
→ 只保留最后一段文件名
→ 拒绝空名称、.、..、空字符和超长名称
→ 扩展名转小写后检查白名单
→ 返回安全文件名
```

示例：

```text
C:\fakepath\policy.PDF → policy.PDF
../../secret.txt       → secret.txt
malware.exe            → 400 UNSUPPORTED_FILE_TYPE
```

必须返回清理后的 `safe_name`，不能返回原始 `filename`，否则路径穿越字符串仍可能进入保存路径。

## 11. 流式保存与 SHA-256

保存过程每次读取 1 MB：

```text
UploadFile
→ read(1 MB)
→ 写入目标文件
→ content_hasher.update(chunk)
→ 继续下一块
```

一边写入一边计算 SHA-256，只读取一次上传内容。保存后再重新读取会增加磁盘 I/O 和耗时。

目录使用：

```text
{kb_id}/{document_id}/{filename}
```

原因：

- 不同知识库可能存在同名文件。
- 同一知识库也可能重复上传同名文件。
- `document_id` 可以隔离不同文档和版本。
- 删除时可以精确定位文档目录。

## 12. 文件异常和补偿清理

保存函数处理：

```text
正常文件        → 保存并返回 StoredFile
空文件          → 400 EMPTY_FILE
扩展名不支持    → 400 UNSUPPORTED_FILE_TYPE
读取或写入失败  → 500 FILE_SAVE_FAILED
```

无论成功或失败，上传流最终都会关闭。

写入失败：

```text
删除部分文件
→ 尝试删除 document_id 空目录
→ 转换成安全 AppError
→ from exc 保留原始异常链
```

`from exc` 不会把底层异常返回给客户端。客户端只看到安全错误，服务器日志和调试器仍能看到原始异常原因。

## 13. 文件与 SQLite 的一致性

创建文档的顺序：

```text
生成 document_id
→ 保存原文件并计算哈希
→ 创建 Document(status=UPLOADED)
→ session.add()
→ session.commit()
→ session.refresh()
→ 返回 DocumentRead
```

如果文件保存失败，SQLite 记录还没有创建。

如果文件成功但数据库提交失败：

```text
session.rollback()
→ 删除刚保存的文件
→ 抛出 DOCUMENT_CREATE_FAILED
```

`refresh()` 放在 `commit()` 异常处理之后。因为一旦提交成功，后续刷新失败也无法通过 `rollback()` 撤销已经提交的记录，此时不应该错误地删除原文件。

## 17. 本阶段提问与标准答案

### 17.1 这些数据表创建在 SQLite 还是 Milvus？

`users`、`knowledge_bases` 和 `documents` 都创建在 SQLite。Milvus 在阶段三保存 Chunk 和向量，不保存当前三张关系型业务表。

### 17.2 SQLite 与 Milvus 是什么关系？

SQLite 保存业务真相、状态和权限；Milvus保存用于语义检索的 Chunk 和向量。二者通过应用写入的 `user_id`、`kb_id` 和 `document_id` 关联。

### 17.3 Session 里面保存什么，作用是什么？

Session 临时跟踪本次事务查询、新增、修改和删除的对象，并管理数据库连接、提交和回滚。长期数据保存在 SQLite，不在 Session 中。

### 17.4 为什么不能直接写 `session = get_session()`？

`get_session()` 是生成器函数，直接调用得到生成器。FastAPI 使用 `Depends` 执行到 `yield`，取得真正 Session，并在请求完成后自动关闭。

### 17.5 为什么请求使用 UserCreate，数据库写入使用 User？

`UserCreate` 控制客户端可写字段；`User` 表示完整数据库实体。分开后客户端不能指定 ID 和时间等服务端字段。

### 17.6 `commit()` 后为什么调用 `refresh()`？

`commit()` 提交事务，`refresh()` 从数据库重新加载提交后的最新状态，确保响应使用数据库中的真实数据。

### 17.7 为什么用户身份依赖使用 `session.get(User, x_user_id)`？

`Session.get()` 按主键查询，需要模型类和主键值两个参数。返回 `User | None`。PyCharm 偶尔把模型类标成类型误报，但运行和 HTTP 测试均已通过。

### 17.8 为什么不能只检查知识库所有者用户是否存在？

所有者存在不代表当前请求者就是所有者。必须比较：

```python
knowledge_base.owner_id == current_user.id
```

否则任意有效用户都可能访问其他人的知识库。

### 17.9 为什么写文件时同步计算 SHA-256？

上传内容只需读取一次，同时完成写入和哈希计算，避免保存后再次读取整个文件。

### 17.10 为什么路径包含 kb_id 和 document_id？

为了隔离不同知识库、同名文件和重复上传，并支持以后按文档精确删除。

### 17.11 `raise AppError(...) from exc` 有什么作用？

它建立显式异常链，客户端看到安全的业务错误，日志保留导致该错误的底层异常和堆栈。

### 17.12 为什么上传后是 UPLOADED 而不是 READY？

阶段二只保存原文件和 Document 元数据。只有完成解析、切分、Embedding 和 Milvus 入库后，文档才能变成 `READY`。

### 17.13 当前为什么允许重复用户名？

`name` 是显示名称，UUID 才是身份主键。当前没有登录系统；以后应增加唯一登录标识，而不是强制显示名称唯一。

### 17.14 当前权限系统安全吗？

不安全。`X-User-ID` 只是模拟身份，客户端可以伪造其他用户 UUID。它用于学习数据过滤，不能替代登录、密码、JWT 或服务端 Session。
