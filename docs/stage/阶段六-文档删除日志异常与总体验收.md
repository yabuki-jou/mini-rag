# 阶段六：文档删除、日志、异常与总体验收

## 本阶段接口

```http
DELETE /knowledge-bases/{kb_id}/documents/{document_id}
X-User-ID: <user_id>
```

功能：删除指定文档的全部 Milvus Chunk、本地原文件和 SQLite 文档记录。

- 请求体：无。
- 成功响应：`204 No Content`。
- 文档已经不存在：仍返回 204，支持重复调用。
- 文档正在 `PROCESSING`：返回 409。
- 其他用户的知识库：返回 403。
- 中途失败：文档保留为 `DELETE_FAILED`，允许重试。

日志属于内部能力，不额外暴露 HTTP 查询接口。

## 函数层级关系

```text
DELETE /knowledge-bases/{kb_id}/documents/{document_id}
└─ get_current_user()
   └─ 根据 X-User-ID 从 SQLite 查询真实用户
└─ get_owned_knowledge_base()
   └─ 验证 kb_id 存在且 owner_id 等于当前用户
└─ delete_document_endpoint()
   └─ 接收路径参数和已验证依赖，不直接操作存储
      └─ delete_document()
         ├─ 从 SQLite 查询 document_id，并限制 kb_id
         ├─ 标记 DELETING
         ├─ delete_document_chunks()
         │  ├─ 构造 user_id + kb_id + document_id 过滤表达式
         │  ├─ 从 Milvus 删除全部匹配 Chunk
         │  └─ flush() 使删除结果可见
         ├─ delete_stored_document_file()
         │  ├─ 验证目标仍位于 FILE_STORAGE_DIR
         │  ├─ 幂等删除原文件
         │  └─ 只尝试删除空文档目录
         ├─ session.delete(document) + commit()
         └─ 失败时 _mark_document_delete_failed()
            └─ 回滚事务并持久化 DELETE_FAILED 与安全错误摘要
```

## 删除顺序为什么这样安排

```text
Milvus Chunk → 原文件 → SQLite Document
```

SQLite Document 是删除重试需要的“操作凭据”，其中保存了 `document_id`、
`kb_id` 和 `storage_path`。如果一开始就删掉它，后续 Milvus 或文件清理失败时将失去
定位信息。因此最后才删除 SQLite 记录。

已经成功删除的步骤再次执行时必须安全：

- Milvus 没有匹配 Chunk时返回删除 0 条。
- 原文件不存在时 `missing_ok=True`。
- SQLite 文档不存在时接口直接返回 204。

所以第一次执行到一半失败后，第二次可以从头重试而不会产生副作用。

## 路径安全

原文件删除前同时对存储根目录和目标路径执行 `resolve()`，再使用
`relative_to()` 验证目标属于存储根目录。

不能使用字符串 `startswith()` 判断路径，因为：

```text
C:\data\files2\a.txt
```

也会以：

```text
C:\data\files
```

开头，但它并不属于该目录。

路径还必须至少满足：

```text
kb_id/document_id/filename
```

目标不能是目录。删除成功后只尝试清理空的 `document_id` 目录，不递归删除，也不
删除 `kb_id` 目录。

## 请求和性能日志

```text
HTTP 请求
→ RequestContextMiddleware 生成或读取 X-Request-ID
→ ContextVar 把 request_id 传给当前调用链日志
→ 服务层记录业务 ID、参数、候选结果和分阶段耗时
→ 响应头返回同一个 X-Request-ID
```

主要日志：

- HTTP：方法、路径、状态码、总耗时。
- 解析：页数、Chunk 数、解析/Embedding/入库/总耗时。
- 检索：Top-K、Top-N、阈值、候选 Chunk ID 与分数、最终 Prompt Chunk。
- 问答：拒答原因、Prompt Chunk、LLM 耗时和总耗时。
- 删除：用户、知识库、文档、删除 Chunk 数、耗时和失败代码。

日志不写入 API 密钥和完整 Chunk 正文。

## 自动化验收

当前测试覆盖：

1. 相同输入的 Chunk ID 稳定，正文或位置变化时改变。
2. 重新解析先删除旧 Chunk，最终数量不会累积。
3. 解析失败进入 `FAILED`。
4. 检索等于阈值时保留，低于阈值时过滤。
5. 检索始终包含 `user_id + kb_id`。
6. DeepSeek 使用 Mock，无依据问题不调用模型。
7. 删除始终包含 `user_id + kb_id + document_id`。
8. 文件路径不能越出存储目录。
9. 重复删除返回 204。
10. 删除失败进入 `DELETE_FAILED`。
11. 其他用户不能访问、解析或删除资源。

## 三个验收问题

### 1. 为什么 SQLite 文档记录必须最后删除？

因为它保存后续重试所需的文档身份和原文件位置。如果外部资源尚未清理就先删除
SQLite 记录，失败后将难以精确补偿。

### 2. 为什么按 document_id 删除比重新计算 Chunk ID 更可靠？

重新切分后正文、页码、位置或切分参数可能变化，重新计算的 Chunk ID 无法覆盖旧
版本全部记录。按文档归属删除表达的是“删除此文档的所有 Chunk”，不依赖当前切分
结果。

### 3. 为什么 Milvus 的 user_id/kb_id 过滤不能替代接口权限校验？

Milvus 条件只负责限制数据查询或删除范围，不负责证明调用者有权使用这些 ID。接口
必须先根据真实用户记录验证知识库所有权，再把可信 ID 传给 Milvus。
