## 6. 历史业务方向（已停止推进）

### 6.1 项目名称

**[历史规划，已停止] 工程企业招投标文档智能审查平台**

简历候选名称：

> 基于 LangGraph 与 RAG 的工程招投标智能审查 Agent

### 6.2 目标行业和用户

- 电力设备企业、工程技术企业、建筑设计和工程咨询企业。
- 招投标部门、售前人员、项目经理、技术审核人员和法务人员。

### 6.3 要解决的真实问题

- 招标文件篇幅长，资格、商务、技术、评分和废标条件分散。
- 人工阅读容易遗漏关键要求、时间节点、签章和格式要求。
- 投标响应找不到对应的公司资质、业绩和技术证明。
- 多人修改后可能出现参数、工期、人员和报价信息不一致。
- 审查结论缺少原文页码、章节、证据和责任记录。

### 6.4 核心业务产物

项目价值不以聊天回答为中心，而应输出：

- 招标要求清单
- 投标响应矩阵
- 缺失材料清单
- 技术和商务偏离项
- 合规风险清单
- 原文引用与证据映射
- 人工审核状态和处理记录
- 有依据的投标目录、响应草稿或审查报告

其中最关键的业务关系是：

```text
招标要求 -> 投标响应位置 -> 公司证明材料 -> 审核状态 -> 处理记录
```

### 6.5 与 IT 智能客服的本质区别

| IT 智能客服 | 招投标文档审查 Agent |
| --- | --- |
| 输入单个问题 | 输入完整投标项目及多类材料 |
| 输出自然语言答案 | 输出要求矩阵、风险清单和审查报告 |
| 主要读取知识库 | 同时处理招标要求、公司资质、业绩和投标响应 |
| 通常没有业务状态 | 每条要求都有响应、证据、负责人和审核状态 |
| 对话结束即完成 | 需要整改、复核、批准和审计记录 |
| 错答通常是服务质量问题 | 遗漏可能导致废标或错误承诺 |

## 7. 现有项目向新方向迁移时的四类能力

### 7.1 已有

- FastAPI 服务和分层结构。
- RAG、Milvus、Embedding、引用溯源。
- LangGraph 单 Agent、Tool Calling、多轮消息和 Checkpoint。
- 用户资源隔离和脱敏工具日志。
- PostgreSQL 业务配置、Alembic 迁移和自动化测试基础（以当前复验结果为准）。

### 7.2 缺失

- 投标项目、招标要求、公司材料、投标响应、审查问题等业务模型。
- 对招标文件章节、表格、评分项、废标条件和时间节点的结构化解析。
- PDF / Word / Excel 的招投标专用解析能力；当前尤其缺少 OCR 和表格专用解析。
- 招标要求与企业资质、业绩、技术材料之间的证据映射。
- 响应矩阵、风险问题、整改、复核和负责人状态。
- 多版本投标文件对比。
- 招投标场景的评估数据集和可量化验收标准。
- 面向求职演示的前端工作台。

### 7.3 值得实现

- 招标要求结构化提取。
- 要求、响应和证据三者之间的可追溯映射。
- 缺失项、冲突项、过期材料和无依据承诺检测。
- 每个风险问题的原文页码、章节和判断依据。
- 人工确认、问题指派、整改和复核闭环。
- 基于已有公司材料生成有依据的响应草稿。
- 针对多文档、空结果、阈值边界、错误引用和跨项目隔离的真实评估。

### 7.4 不适合照搬或暂不实现

- 为了展示技术而引入没有业务必要的多 Agent。
- 自动决定投标报价、工期和技术承诺。
- 自动编造企业资质、业绩、人员或证书。
- 无人审核直接生成和提交最终投标文件。
- 自动登录第三方招投标平台并提交材料。
- 一开始覆盖所有行业和全部标书类型。
- 直接照搬 `agent-service-toolkit` 的全部模块。
- 在当前阶段引入 Kubernetes、复杂微服务或模型训练与微调平台。
