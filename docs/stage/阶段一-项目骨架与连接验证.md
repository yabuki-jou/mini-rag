## 4. 配置管理

`Settings` 从环境变量或项目根目录下的 `.env` 读取配置。核心配置包括：

```text
DATABASE_URL
MILVUS_URI
MILVUS_TOKEN
MILVUS_COLLECTION
EMBEDDING_MODEL_PATH
EMBEDDING_DEVICE
EMBEDDING_DIMENSION
DEEPSEEK_API_KEY
DEEPSEEK_BASE_URL
DEEPSEEK_MODEL
```

`SettingsConfigDict` 参数：

- `env_file`：指定 `.env` 文件位置。
- `env_file_encoding="utf-8"`：使用 UTF-8 读取中文和其他字符。
- `case_sensitive=False`：环境变量名不区分大小写。
- `extra="ignore"`：忽略 `.env` 中当前 `Settings` 未声明的额外字段。

配置来源的通常优先级是：真实环境变量高于 `.env`，`.env` 高于字段默认值。

### 稳定路径解析

不能把 `Path("data/model")` 直接当作稳定的项目路径，因为它默认相对于进程的当前工作目录，而当前工作目录可能随着启动方式变化。

项目先确定：

```python
PROJECT_ROOT = Path(__file__).resolve().parents[2]
```

然后把配置中的相对路径拼接到 `PROJECT_ROOT`，因此从项目根目录、父目录或 PyCharm 启动都能得到同一个绝对路径。

`EMBEDDING_MODEL_PATH` 以 `../` 开头，表示从手写项目根目录先进入父目录，再进入已有项目的模型目录。它本身仍是相对路径，经过 `resolve_path()` 后才成为绝对路径。

## 5. SQLite 与 SQLModel

数据库链路：

```text
DATABASE_URL
→ 解析 SQLite 文件路径
→ 转换为基于 PROJECT_ROOT 的绝对路径
→ 创建父目录
→ create_engine()
→ create_db_and_tables()
```

`check_same_thread=False` 允许 SQLite 连接在 FastAPI/SQLAlchemy 的工作线程之间使用。它不表示可以把同一个 Session 随意共享给所有并发请求；每个请求仍应获取并关闭自己的 Session。

`get_session()` 使用 `yield`：

```python
def get_session() -> Generator[Session, None, None]:
    with Session(engine) as session:
        yield session
```

执行顺序：

```text
创建 Session
→ yield 给路由使用
→ 请求处理结束
→ 返回 with 代码块
→ 自动关闭 Session
```

如果直接 `return Session(engine)`，依赖函数无法在请求结束后自然执行关闭逻辑。

## 6. 统一异常处理

项目把异常分为三类：

- `AppError`：预期内的业务错误，可以安全返回自定义状态码、业务代码和消息。
- `RequestValidationError`：FastAPI/Pydantic 请求参数校验错误，返回 HTTP 422。
- 未知 `Exception`：返回固定 HTTP 500 和 `INTERNAL_ERROR`，原始堆栈只写入服务器日志。

响应同时使用 HTTP 状态码和业务错误代码：

```json
{
  "error": {
    "code": "MILVUS_UNAVAILABLE",
    "message": "Milvus 当前不可用"
  }
}
```

- HTTP 状态码供浏览器、网关和监控系统判断错误大类。
- 业务错误代码供客户端稳定地区分具体业务原因。
- 人类可读的 `message` 用于展示和排查。

未知异常不能直接把 `str(exc)` 返回给客户端，因为它可能包含数据库地址、文件路径、请求数据、第三方服务信息或其他内部实现细节。

`logger.exception()` 会在异常处理上下文中记录消息和完整异常堆栈；`logger.error()` 默认只记录错误消息，除非显式传入堆栈信息。

## 8. Milvus 连接

项目使用 `pymilvus.MilvusClient` 执行阶段一的底层连接检查：

```text
Settings.milvus_connection_args
→ MilvusClient
→ list_collections()
→ 验证服务可连接
```

验证时检测到：

```text
mini_rag_chunks
docs
```

健康检查只调用 `list_collections()`，不创建 Collection，原因是健康检查应该是只读、可重复、无副作用的。如果探活请求会创建或修改资源，监控系统的频繁调用可能意外改变业务数据。

手写项目使用不同的 `MILVUS_COLLECTION` 是为了避免与旧项目的数据、Schema 和删除操作互相影响。Collection 不等同于 MySQL 数据库，更接近数据库中的“表”；Milvus 自身还存在 Database 层级。

访问 <http://localhost:19530/> 并不等同于打开管理后台。`19530` 是 Milvus 客户端/API 服务端口，主要供 SDK 调用，不是普通网页管理界面。

`get_milvus_client()` 使用缓存，是为了复用同一个 PyMilvus 客户端，减少重复创建客户端和连接资源。本阶段并没有在这里创建 LangChain Milvus 对象。

```python
raise AppError(...) from exc
```

`from exc` 建立显式异常链：对外抛出统一的 `AppError`，同时保留原始异常作为 `__cause__`，日志和调试器仍能看到底层失败原因。

## 9. 健康检查

`GET /health` 分别检查：

```text
API        → 路由能够执行
database   → SELECT 1
milvus     → list_collections()
embedding  → 生成测试向量并检查是否为 512 维
```

每个组件使用独立的 `try/except`。一个组件失败后，其他检查仍然继续，因此一次响应能够展示所有依赖的状态。

全部正常：

```text
HTTP 200
status = ok
```

任一组件异常：

```text
HTTP 503
status = degraded
```

最终验证结果：

```json
{
  "status": "ok",
  "components": {
    "api": {"status": "ok", "detail": null},
    "database": {"status": "ok", "detail": null},
    "milvus": {"status": "ok", "detail": "collections=2"},
    "embedding": {"status": "ok", "detail": "dimension=512"}
  }
}
```

健康检查不应只判断模型目录是否存在。目录存在只能说明文件在磁盘上；真正生成向量并检查维度，才能发现模型文件损坏、依赖错误、设备配置错误或模型与配置维度不一致等问题。

## 10. FastAPI 应用生命周期

```python
@asynccontextmanager
async def lifespan(_: FastAPI) -> AsyncIterator[None]:
    create_db_and_tables()
    yield
```

`@asynccontextmanager` 把包含 `yield` 的异步生成器转换为异步上下文管理器：

- `yield` 前面的代码在应用启动时执行。
- `yield` 期间应用接收请求。
- `yield` 后面的代码在应用关闭时执行，可用于释放资源。

```python
app = FastAPI(lifespan=lifespan)
```

左侧 `lifespan` 是 FastAPI 的构造参数，右侧 `lifespan` 是项目定义的函数。这行代码把生命周期函数注册给 FastAPI；只定义函数但不传入，FastAPI 不会执行它。

## 12. 本阶段提问与标准答案

### 12.1 FastAPI 和 Uvicorn 分别负责什么？

Uvicorn 是 ASGI 服务器，负责监听端口、接收 HTTP 请求并调用应用。FastAPI 负责路由、参数校验、依赖注入、业务逻辑和响应生成。

```text
浏览器/客户端 → Uvicorn → FastAPI → 路由与业务代码
```

### 12.2 为什么同时需要 `langchain-milvus` 和 `pymilvus`？

`langchain-milvus` 提供符合 LangChain 习惯的向量存储和 Retriever 接口；`pymilvus` 是官方底层 Python SDK，适合创建 Schema、标量过滤、精确删除和管理 Collection。本阶段的连接检查使用 PyMilvus，后续常规向量操作再使用 LangChain Milvus。

### 12.3 为什么测试依赖单独放在 `requirements-dev.txt`？

用于区分运行环境和开发环境，减少生产安装体积、依赖冲突和维护范围，同时让依赖用途更清晰。

### 12.4 为什么两个项目都写 `./data/mini_rag.db`，却不会使用同一个文件？

相对路径分别基于各自的项目根目录解析，所以实际得到两个不同的绝对路径。当前代码主动基于 `PROJECT_ROOT` 解析，避免启动目录变化影响结果。

### 12.5 为什么新项目必须使用不同的 Milvus Collection？

为了隔离新旧项目的 Schema、测试数据和删除操作，避免手写练习误删旧项目向量。Collection 更接近关系数据库中的表，不是整个 MySQL 数据库。

### 12.6 为什么不能直接使用 `Path("data/model")` 作为稳定路径？

因为相对 `Path` 默认依赖进程当前工作目录。终端、PyCharm、测试工具可能使用不同工作目录，导致同一配置指向不同位置；真正原因不是路径“可能被占用”。

### 12.7 为什么密钥字段使用 `SecretStr`？

`SecretStr` 会在对象打印、日志和调试输出中隐藏真实内容，降低意外泄露风险。调用底层 SDK 时，仍需通过 `get_secret_value()` 显式取出字符串。

### 12.8 为什么 `get_settings()` 使用 `lru_cache`？

第一次调用创建 `Settings`，后续调用复用同一个实例，避免反复解析 `.env`，并让应用各处读取一致配置。测试修改环境变量时需要清理缓存或重新创建实例。

### 12.9 `args = {"uri": self.milvus_uri}` 能阻止 URI 为空吗？

不能。它只会把当前字符串放入字典，空字符串也能进入。若要在配置层禁止空值，可以使用 `Field(min_length=1)` 或字段校验器。即使没有提前校验，Milvus 客户端也会在连接阶段报错，但错误位置更深、不够清晰。

### 12.10 为什么 SQLite 使用 `check_same_thread=False`？

FastAPI 的同步代码可能在线程池的不同线程执行。关闭 SQLite 的同线程限制可以配合 SQLAlchemy 使用连接；它不等于允许多个请求共享同一个 Session。

### 12.11 为什么 `get_session()` 使用 `yield`？

为了在请求处理期间保持 Session 可用，并在请求结束后返回依赖函数继续执行 `with` 的退出逻辑，自动关闭 Session。它不是让连接永久保持打开。

### 12.12 为什么创建 Engine 前要确保数据库父目录存在？

SQLite 可以创建数据库文件，但不会递归创建不存在的父目录。父目录不存在时，连接会失败。

### 12.13 为什么未知异常不能直接返回 `str(exc)`？

它可能泄露密钥、请求数据、数据库结构、连接地址和本地路径。未知异常应记录到服务端日志，对客户端返回固定、安全的信息。

### 12.14 为什么同时需要 HTTP 状态码和业务错误代码？

HTTP 状态码表示通用错误类别；业务代码表示应用内的具体、稳定错误类型。例如多个错误都可能是 HTTP 503，但可以分别使用 `MILVUS_UNAVAILABLE` 和 `EMBEDDING_MODEL_NOT_FOUND`。

### 12.15 `logger.exception()` 和 `logger.error()` 有什么区别？

`logger.exception()` 在异常处理上下文中自动记录当前异常堆栈；`logger.error()` 默认只记录消息，除非显式请求输出异常信息。

### 12.16 为什么健康检查只调用 `list_collections()`，不创建 Collection？

健康检查应该只读、幂等且没有业务副作用。能够列出 Collection 已足以证明客户端可以向 Milvus 发出有效请求。

### 12.17 为什么 `get_milvus_client()` 使用缓存？

为了复用 PyMilvus 客户端，减少重复创建连接资源。它不会同时自动缓存一个 LangChain Milvus 对象，两者是不同层次的对象。

### 12.18 `raise AppError(...) from exc` 保留了什么？

它保留原始异常作为新异常的直接原因，形成异常链。客户端只看到安全的业务错误，日志仍可以追踪到原始底层异常。

### 12.19 为什么健康检查要实际生成向量？

只检查目录存在无法证明模型可以加载和推理。实际调用 `embed_query()` 并检查维度，才能覆盖模型权重、依赖、设备和配置等问题。

### 12.20 为什么每个健康组件要独立 `try/except`？

如果全部检查放进一个 `try`，第一个失败会中止后续检查。独立捕获可以在一次响应中展示数据库、Milvus 和 Embedding 的完整状态。

### 12.21 为什么部分组件失败时返回 HTTP 503？

API 进程虽然仍在运行，但核心依赖不可用，应用不能完整提供服务。`503 Service Unavailable` 能让监控、负载均衡和调用方正确识别“服务已启动但当前不可用”。

### 12.22 `@asynccontextmanager` 和 `lifespan=lifespan` 分别做什么？

`@asynccontextmanager` 用 `yield` 分隔启动阶段和关闭阶段；`lifespan=lifespan` 把定义好的生命周期函数注册给 FastAPI。当前项目在 `yield` 前创建 SQLite 表。
