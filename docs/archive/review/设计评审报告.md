## 3. 逻辑完整性评审

### 🔴 必须澄清(建议进入 API 设计前明确)

#### 问题 1:AC-FR-034-03 的触发场景在状态机中不可达

- **涉及位置**:需求 V1.1 FR-034 验收标准 AC-FR-034-03;FR-034 前置条件;架构 §11.1 状态机
- **问题描述**:AC-FR-034-03 写"Given 用户已编辑字段草稿,When 请求重新生成建议,Then 系统不得静默覆盖人工内容"。但按 FR-034 前置条件,AI 建议只允许从 `PARSED` / `SUGGESTION_FAILED` 发起;而"已编辑字段草稿"必然处于 `PENDING_CONFIRMATION`(FR-035 前置条件限定字段编辑状态),状态机中 `PENDING_CONFIRMATION` 没有任何指向建议生成的动作。**该 AC 的触发场景在当前状态机中无法发生**,对应测试用例无法执行。
- **修改建议**:在 API 设计阶段明确二选一并写入契约:
  1. **支持**:新增"重新生成建议"接口,限定仅在字段全部仍为 `PENDING_CHECK`(即未产生人工内容)时允许,覆盖策略为"全空草稿可直接覆盖,含人工内容必须拒绝或合并";或
  2. **不支持**:在 API 设计中显式声明"`PENDING_CONFIRMATION` 状态下无重新建议接口,AC-FR-034-03 为防御性验收,不提供对应端点",并调整测试说明。
  - 无论哪种,AC-FR-034-03 的"不得静默覆盖"约束都应保留为服务层不变式。

#### 问题 2:"取消确认"与"字段/证据变更"合并映射为 `PENDING_RECONFIRMATION`,语义被折叠

- **涉及位置**:架构 §11.1 状态机边 `CONFIRMED → PENDING_RECONFIRMATION: field/evidence change or cancel confirmation`;需求 FR-036
- **问题描述**:取消确认是**用户主动撤回**(动机:撤销入档),字段变更后待重确认是**数据变化触发的强制流程**(动机:内容已改)。两者被映射为同一状态,后续行为相同(退出正式范围),但业务语义不同:
  - 取消确认后,`checklist_links` 保持 `CONFIRMED` 是否合适?需求 BR-019 规定满足 = 已确认档案 ∧ 已确认关联,档案取消后关联虽然仍 CONFIRMED,但清单会因档案状态退回"缺失"。重新确认后关联自动恢复满足——这看似合理,但文档未明确说明,实现者可能对"取消确认是否应同时失效关联"产生分歧。
- **修改建议**:在 API 设计中明确:
  1. 取消确认使用独立的审计操作类型(如 `CANCEL_CONFIRMATION`),与字段修改(`FIELD_CHANGE`)区分,便于追溯;
  2. 明确"取消确认不改变 `checklist_links.status`,清单满足性仅由档案状态与关联状态共同派生";该语义写入数据库设计 §6.8 或 API 文档。

### 🟡 建议优化

#### 建议 1:"重新解析替换快照"的表述与状态机不一致,且与 `ON DELETE RESTRICT` 存在潜在冲突

- **涉及位置**:数据库设计 §6.4(parsed_snapshots)、§6.6(field_evidences 的 `snapshot_id ON DELETE RESTRICT`);需求 FR-033
- **说明**:数据库设计 §6.4 写"重新解析替换快照前必须先满足状态和操作锁规则",但按 FR-033,V1 中普通解析只允许 `UPLOADED`,重新解析只允许 `PARSE_FAILED`(该状态无成功快照)。**V1 内不存在"替换已有快照"的可触发路径**,实现者会困惑"替换"在什么场景发生;若未来开放 PARSED 文档重解析,旧证据通过 `snapshot_id ON DELETE RESTRICT` 会阻止快照删除,新旧快照切换将无法完成。
- **优化方案**:数据库设计 §6.4 明确表述为"V1 中快照一旦创建不可替换(重解析仅适用于 `PARSE_FAILED`,该状态无快照);快照替换机制属于未来能力,若启用需同步设计证据表与快照的关联迁移策略"。避免在 V1 数据库实现中为"替换"预留不可达逻辑。

#### 建议 2:进入人工草稿后无法再获得 AI 建议,缺少放弃人工改走 AI 的路径

- **涉及位置**:需求 FR-034/FR-035;架构 §10.2
- **说明**:用户从 `PARSED` 选择"开始人工草稿"进入 `PENDING_CONFIRMATION` 后,若反悔想改用 AI 建议,没有路径(只能删除重来)。对演示型产品可接受,但应在文档中明示,避免用户体验困惑。
- **优化方案**:API 设计阶段可提供"放弃草稿并重新建议"接口(仅当七个字段全部为 `PENDING_CHECK` 时允许),或明确声明不支持并在 README 说明。

#### 建议 3:`archive_operations` 中 `SUCCEEDED` 记录的生命周期未定义

- **涉及位置**:数据库设计 §6.9
- **说明**:`archive_operations` 的索引 `(operation_status, updated_at)` 明显为恢复扫描(RUNNING/FAILED)设计,但 `SUCCEEDED` 记录会随文档生命周期无限累积;文档删除时随 `archive_documents` 级联清理,但存活文档的每次解析/建议/确认都会留一条成功记录,长期增长。需求明确"不提供审计删除和保留期限配置"针对的是业务审计表,内部操作表未定义策略。
- **优化方案**:V1 可接受(学习项目规模小),但建议在实现计划中说明成功记录的清理策略(如按文档级联 + 可选定期清理),或在数据库设计中加一行说明,避免被误读为无限增长隐患。

#### 建议 4:审计 `operation_type` 的固定取值需在 API 阶段固化为 Schema 枚举

- **涉及位置**:数据库设计 §6.10(`operation_type VARCHAR(64)`);评审 MSG 24/26 已提出一次
- **说明**:上一轮已确认该字段不能用 `archive_operation_type`(审计动作范围更广),但若不固化取值列表,Swagger 契约不清晰,客户端无法可靠消费。
- **优化方案**:API 设计阶段为审计操作类型定义完整枚举(确认/取消确认/字段修改/清单增删改/关联确认/关联删除/手动重试/删除等),作为响应 Schema 的 enum 输出。

### 4.2 关键改造点风险排序

1. **位置感知 Parser(最高)**:有效文本阈值、DOCX 段落/表格/编号列表处理、TXT/MD 换行归一化未定义——架构已正确将其推入 Parser 设计阶段,但这是全链路最容易返工的部分,建议在 API 设计前先做 Parser 可行性验证(用真实样本 PDF/DOCX 试跑)。
2. **双存储一致性(高)**:确认/删除跨 PostgreSQL、文件系统、Milvus 的补偿逻辑依赖 `archive_operations` 的恢复能力,而恢复入口算法本身标注为 TODO-IMPLEMENTATION。建议在实施计划中把"Operation 恢复流程"作为独立可验证任务先行设计。
3. **双重闸门收敛性(中)**:所有新检索入口必须复用 ArchiveRetrievalService,文档已列为风险并给出应对,实施时需用集成测试锁定。

### 4.3 结论

架构与数据库设计在当前 FastAPI + PostgreSQL + Milvus + BGE + DeepSeek 基座下**可落地**;主要风险集中在 Parser 与跨存储补偿两个环节,均已被设计文档正确识别并列入下游 TODO,不构成架构层面的阻塞。

## 6. 风险提示

1. **X-User-ID 模拟身份**:需求与架构均已声明,仅学习用途;若用于公开演示需显著提示,否则易被误认为生产认证方案。
2. **同步确认阻塞**:确认时同步 Embedding + 写 Milvus,20MB/100 份上限缓解了风险,但大文件确认延迟需在 README 中说明。
3. **`active_document_count` 反规范化计数**:依赖行锁原子维护,若未来引入分布式或多实例部署将失效;V1 单体可接受。
4. **`snapshot_hash` 规范化序列化格式**:定义依赖"有序片段序列",其序列化规则必须在 Parser 设计阶段冻结,否则相同内容在不同解析器版本下哈希不一致,证据锚定失效。
5. **数据外发 DeepSeek**:仅允许虚构/脱敏资料,Swagger/README 需强制展示提示语(已列入 NFR-020,须落实)。
6. **无真实代码核验**:本评审基于文档自洽性;实施前应核对架构 §3 的现有模块声明与代码现状是否一致。
