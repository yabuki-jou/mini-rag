## 补丁 1:API §3.2(分页、Idempotency-Key)+ §8(问答参数)+ §12(待确认事项)

### 1.1 分页(替换 §3.2 中 [ASK USER] 分页条目)

```text
- 列表使用 `page`（从 1 开始）和 `page_size`；默认 `page=1`、`page_size=20`、最大
  `100`。所有列表统一追加 `id DESC` 作为次级排序，见本小节排序规则。
```

### 1.2 Idempotency-Key(替换 §3.2 中 [ASK USER] 条目)

```text
- 第一版不引入 `Idempotency-Key` 请求头。写操作幂等性由以下机制共同保证：
  聚合 `expected_version` 乐观锁、`archive_operations` 单 RUNNING 操作锁、
  重复确认业务幂等、上传 `file_hash` 去重、删除失败复用未完成操作。
- 明确边界：不保证客户端因"响应丢失"而重发 POST 时返回第一次响应（无
  Idempotency-Key 时无法做到传输重放幂等）；只保证上述机制不重复产生文件、
  记录、Chunk、档案或成功审计等关键副作用。网络自动重试仅限连接失败/超时一次。
```

### 1.3 问答检索参数(替换 §8 中两处 [ASK USER])🔄 R1

`archive-retrieval` 小节:

```text
`top_k` 固定为默认 `5`、最大 `10`。检索与过滤规则与 `archive-questions` 共用
（同一服务、同一 `top_k` 与同一 `min_relevance_score`），保证核对接口与问答
行为一致。过滤后无候选时返回 `200` 与空 `items`。
```

`archive-questions` 小节:

```text
服务先用 PostgreSQL 获取正式 `document_id` 集合，再以服务器注入的
`user_id + project_id + kb_id + document_id` 过滤 Milvus，内部检索固定
`top_k=5`，候选 Chunk 按相似度降序截取前 5 条；随后应用相关性阈值
`min_relevance_score`：仅保留相似度达到阈值的 Chunk 作为回答上下文。
过滤后无候选 → 直接返回 `REFUSED_NO_EVIDENCE`，不调用 DeepSeek，不编造引用。
问题长度限制为 `1..2000` 个字符。

`min_relevance_score` 的冻结流程（不凭空指定）：
1. 在 Parser/BGE 可行性验证阶段，使用需求 12.1 的 12~18 份验收资料与 12.3 的
   12 个固定问答用例标定阈值；
2. 标定目标：8 个有据问题全部通过、2 个无据问题全部被拒、2 个项目隔离问题
   不泄露任何内容、引用正确率 100%；
3. 冻结后的阈值写入实施计划与验收说明，并作为问答服务的固定配置；验证阶段的
   标定过程与结果数据记录在验收报告。
```

## 补丁 2:API §7 confirm 小节(重复 confirm 幂等)🔄 R2

在 `POST .../confirm` 小节末尾追加:

```text
幂等语义（业务幂等，非传输重放幂等）：
- 文档已为 `CONFIRMED` 且 `expected_version` 等于当前版本时，重复 `confirm`
  幂等返回 `200` 当前档案，不重新生成 Final Chunk、不新增成功审计。
- `expected_version` 与当前版本不一致（含网络重放旧版本）时返回
  `409 VERSION_CONFLICT`。
- 该幂等仅覆盖"同一最新版本的重复确认请求"；因响应丢失而重发旧版本请求时返回
  409 而非首次响应——V1 无 Idempotency-Key，不承诺传输重放幂等。
- `confirm` 允许的状态为 `PENDING_CONFIRMATION`、`PENDING_RECONFIRMATION`
  与幂等返回的 `CONFIRMED`；其他状态返回 `409 CONFIRM_NOT_ALLOWED`。
```

## 补丁 7:API §7 与 §10(模型输出格式错误稳定错误码)🔄 R5

### 7.1 §7 建议接口段落修正

将"并返回 `503 ARCHIVE_SUGGESTION_UNAVAILABLE` 或稳定的格式错误"改为:

```text
并返回 `503 ARCHIVE_SUGGESTION_UNAVAILABLE`；模型输出不合格（无法解析为固定
字典字段或证据结构）时返回 `422 SUGGESTION_INVALID_OUTPUT`。
```

### 7.2 §10 错误码表新增一行

```text
| 422 | `SUGGESTION_INVALID_OUTPUT` | 模型返回内容无法解析为固定字典字段或证据结构；不自动重试（符合 BR-023） |
```

### 7.3 §7 补充 `SUGGESTION_INVALID_OUTPUT` 的状态语义

```text
`SUGGESTION_INVALID_OUTPUT` 的状态行为按发起场景区分：
- 首次建议（从 `PARSED` 发起）或失败后重试（从 `SUGGESTION_FAILED` 发起）遇到
  模型格式错误：文档进入/保持 `SUGGESTION_FAILED`，不自动重试；用户可再次重试
  建议或转为手工草稿。
- 重新生成建议（从 `PENDING_CONFIRMATION` 发起）遇到该错误：保留现有草稿与
  `PENDING_CONFIRMATION` 状态，原草稿不被丢弃，不转为 `SUGGESTION_FAILED`。
- 与 `503 ARCHIVE_SUGGESTION_UNAVAILABLE` 的区分：503 表示模型不可用（连接
  失败/超时/未配置，自动重试一次）；422 表示模型可访问但输出不合格（不自动重试）。
```

## 补丁 9:数据库 §6.9(内部操作记录生命周期)+ §12(验收清单)🔄 R6

### 9.1 §6.9 末尾追加生命周期说明

```text
操作记录生命周期（控制表增长）：

- `DELETE` 类：未完成（`RUNNING`/`FAILED`）记录必须保留至删除完成（部分唯一索引
  保证至多一条）；删除成功后 `archive_documents` 物理删除，操作记录随 ON DELETE
  CASCADE 清理，最终不残留。
- 非 DELETE 类（`PARSE`/`SUGGEST`/`INDEX`）：每次操作进入终态
  （`SUCCEEDED`/`FAILED`）后，删除该文档同类型更早的终态记录，仅保留最新一条；
  文档删除时随级联清理。因此每文档每非删除类型至多保留一条历史记录，表规模有界
  （约等于文档数 × 3 + 未完成删除操作数）。
- `RUNNING` 记录不清理；服务重启后按 `(operation_status, updated_at)` 索引扫描
  恢复未完成操作。
- 审计关联说明：清理操作记录不影响审计。`archive_audit_logs.operation_id` 是
  "历史关联 ID"，数据库未对其设外键（§6.10），仅用于"一次成功结果不重复写审计"
  的唯一性约束；操作记录被清理后，审计仍独立保留，查询审计不依赖操作记录存在。
```

### 9.2 §12 数据库验收清单追加一条

```text
- 每份文档每非删除操作类型至多保留一条终态记录；未完成 `DELETE` 记录保持
  `visibility_blocking` 直到删除完成。
- 清理操作记录后，对应审计记录（`operation_id`）仍可独立查询，不受影响。
```
