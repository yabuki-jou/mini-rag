## 1. 目标与已核实问题

修正回答质量评测中两个已证实的诊断问题，并为一个真实拒答错误制定最小应用层修正：

- 拒答预期的样本仍带候选内引用时，当前 evaluator 把“拒答契约失败”误标成 `CITATION_NOT_IN_CANDIDATES`。最终分数虽为 0，但失败原因不准确。
- 补充排序的三条正确金额答案均表达 250 百万美元，却因固定检查 `US$250 million` 子串而得到 0/3。扩展样例须显式接受经人工确认的等价金额表达，不放宽为只检查数字 `250`。
- `WB-UNSUPPORTED-DRAW-01` 三次将“当前或完工时实际提款金额”回答为 250 million。原页只给出截至 2015-03-05 的 `Amount=250`、`Disbursed=0`；模型把贷款金额用于回答实际提款，违反时间和字段口径。应拒答。

应用问题来自 FR-039/FR-042 共用的档案回答服务；本计划不假定单一根因已证实。Trace 显示完整表头、数值、日期和问题均进入模型输入，但单一文档的三次输出不足以证明仅修改 Prompt 就能修复。

## 3. 实施顺序（全部按 TDD）

### 阶段 A：修正 evaluator 并离线复评分

1. **RED — 拒答诊断：**新增测试覆盖正确固定拒答且零引用、预期拒答却回答并附候选内引用、预期拒答却回答并附候选外引用。拒答的映射字段须标为不适用；后两者应因拒答契约失败，不得输出候选映射错误码。预期有据回答的映射失败仍须保持失败。
2. **RED — 等价金额：**为扩展样例加入 `answer_alternatives: list[list[str]]`：外层条件全部满足、每个内层组任一表达命中即可（例如 `[["US$250 million", "250 million US Dollars", "250百万美元", "2.5亿美元"]]`）。有据答案仍须至少含一个 `answer_fragments` 条件或一个有效替代表达组；现有 `answer_fragments` 的全条件语义保持不变。测试每种形式通过，错误数值、只有 `250` 的无单位文本及畸形组不通过。
3. **GREEN/REFACTOR：**只修改 evaluator、扩展样例构造和相应测试；不把拒答的“必须零引用”伪装成候选映射指标。
4. **离线重评：**用修正后的 evaluator 重评现有 21 条输入/输出，不重放模型。保留本轮原始 Trace 和既有 `12/21` 评分快照，另存清楚标注“离线复评分”的结果；预计只因金额等价契约使补充排序组由 0/3 变为 3/3，严格冻结页结果与无据提款失败保持不变。若实际分数不同，报告逐项差异，不强行对齐预期。

### 阶段 B：修正金额字段与时间口径拒答

1. **RED — 确定性回归：**在 `tests/services/archive/test_questions.py` 增加 Prompt 构造用例，锁定回答必须同时匹配用户询问的表格字段、单位和统计日期；明确 `Amount`、`Disbursed`、`Undisbursed` 不可互换，历史时点值不能证明当前或完工时值。该测试仅验证提示契约，不作为 LLM 质量证据。
2. **GREEN：**只在共享档案回答提示中补充上述规则。保持请求/响应 Schema、拒答文案、引用组装和检索路径不变；不加入针对 Belarus、项目名或金额的硬编码逻辑。
3. **回归：**阶段 B 实现后运行档案问答相关测试，确认 Prompt 契约和相邻行为通过。全量测试与编译留到阶段 C 的独立运行器/数据集准备结束后统一执行一次，确保最终全量验证覆盖全部代码改动。
4. **真实质量门：**阶段 C 在 A/B 完成并通过确定性回归后运行。使用已保存的同一份真实 Belarus Snapshot 第 16 页 Top-8 候选，不访问 PostgreSQL/Chroma、不重新检索：批准贷款金额应答 250；截至 2015-03-05 已提款额应答 0 并注明日期；当前/完工实际提款额应固定拒答且无引用。每个条件重复三次，总上限 9 次真实调用；运行器硬上限为 9、模型客户端重试关闭，每条只调用一次，达到上限即停止。三组均达 3/3 方可报告该单页样例通过，否则返回方案评审。只对这一轮实际 Pixie 运行立即完成 Step 6 结果分析；不据单页结果宣称普遍语义质量通过。

### 阶段 C：执行已授权的真实模型对照

1. 从 `acceptance/be69bcb22cd24b77/extension-candidates.json` 中固定同一份八条 Belarus Snapshot 候选；三份 `WB-UNSUPPORTED-DRAW-01` 的完整检索负载哈希均为 `c6f9169f32a66c879aa791e5d9fee331bf69152dd73c62c326f5f42d3c27e4d0`。验证三种问题输入和 `eval_input` 与正式问答服务的观测接口精确匹配；不重新检索、不写业务数据库/向量库。
2. 建立三组各三次的独立评测条目，明确总条目数为 9，并在 Runnable 入口实施不可由评测输入覆盖的硬调用上限 9；每次模型调用前先占用预算，DeepSeek 客户端重试数设为 0。运行前核对调用计数和输出目录为空，运行后核实实际调用总数不超过 9。
3. 在第一次真实调用前，对完成后的全部代码运行一次后端全量 `python -m pytest -q -p no:cacheprovider`、`python -m compileall -q app tests scripts evals pixie_qa` 和 `git diff --check`；任何一项失败都停止，不调用模型。
4. 用 evaluator 检查金额等价表达、指定字段/日期、引用页及拒答无引用契约；复核九条原始输出与逐条分数。真实输出和扩展来源评测结果只进入非冻结报告。
5. 本轮 Pixie 成功运行后立即完成 Step 6：逐条分析通过/失败和根因，更新 action plan、summary、pending evaluations，并运行其验证器。若运行未成功，保留安全诊断并停止，不自动重跑模型。

### 阶段 D 授权后的真实模型复验（2026-09-26）

- 用户授权最多 9 次模型 HTTP 尝试，固定为三组各 3 条；沿用阶段 C 的隔离候选，不重检索、不访问或写入 PostgreSQL、Chroma、Checkpoint 或原文件。运行前确认数据集恰有 9 条、三组各 3 条，每条仅输入用户问题并注入相同的 8 条候选，候选包含 Belarus Snapshot 第 16 页。结果根为 `tests/pytest_docs/public_projects/world_bank_belarus_m6/acceptance/answer-boundary-stage-d-20260926/pixie/`。
- 生产判定服务首个模型调用进入 `model.invoke()` 后失败，安全分类为 `MODEL_CALL_FAILED`；预算器在调用前记账一次，客户端隐藏重试为 0。Runnable 首错熔断，未发起后续样本的模型调用；实际 HTTP 请求是否到达 DeepSeek 服务端无法从允许的安全观测确认。本授权下不再重试，剩余预算不转作补跑。
- Pixie CLI 随后在打印失败标记 `✗` 时发生 `UnicodeEncodeError`（GBK 终端无法编码该字符）；按 CLI 保存顺序，失败发生在标准 RunResult 保存之前。隔离结果根只有逐条 Trace，没有官方 evaluation 输出/评分结果；未读取运行日志或 Trace 正文。因此本轮无三组评分、无质量门结论、无 Step 6 工件。可选 provider 依赖提示不作为模型调用失败根因证据。
- 运行错误归因边界：`MODEL_CALL_FAILED` 是代码已确认的调用阶段分类，底层传输/API 根因未确认；GBK 错误是本地 CLI 输出环境故障，不说明项目生产代码缺陷。它们合并记录为本次运行的两个不同故障，不新增项目缺陷修复文档，不因终端问题重跑模型。
- 结论：阶段 D 提示变更的真实模型效果仍未知；先前 `3/9` 是修改前的历史回答结果，本次失败尝试不能更新该质量分数。任何进一步真实模型请求都需要单独新授权；FR-042 Graph→真实 Chroma 还需 PostgreSQL 隔离预检先恢复。

### 阶段 D：补齐历史时点正向口径与失败分类观测

阶段 C 的真实结果显示，当前/完工提款题 `3/3` 正确拒答，但应回答的批准金额和指定日期提款额题均 `0/3`；九题提示与候选证据均进入模型，不能把过度拒答归因于已证实的单一根因。阶段 D 先做不调用模型的最小修正与安全观测，为另行授权的真实复验提供更明确的契约和诊断。

1. **RED — 时间口径正反例提示契约：**在 `tests/services/archive/test_questions.py` 新增断言：问题所问字段与证据字段一致、且问题明确要求的日期与证据 `as-of` 日期一致时，提示明确要求将该历史值视为可回答，并在答案中注明日期；问题要求当前/完工时而证据只有更早日期时仍须拒答。`Amount`、`Disbursed`、`Undisbursed` 不得互换。测试不写项目名、固定金额或 Belarus 专属规则。
2. **GREEN — 最小提示澄清：**只补充上述历史日期精确匹配的正向规则和与当前/完工口径的对照，不更改 API、检索、引用组装或固定集。
3. **RED/GREEN — 安全失败分类：**在相同测试模块覆盖提示输入构造失败、`model.invoke()` 调用失败、模型输出 JSON/契约校验失败三类；内部 `ArchiveAnswerJudgmentError` 只携带固定白名单 `failure_kind`，保留现有传输错误重试规则。`eval_wrap` 与服务端日志只记录白名单类别，不记录异常正文、模型原始响应、密钥或业务证据；HTTP 仍映射到现有稳定 503 契约。验证 Trace/日志可区分调用失败与输出格式失败。
4. **确定性回归：**先运行相关服务、FR-042 Graph 和评测运行器定向测试，再在本阶段所有实现完成后运行一次后端全量测试、`compileall` 和差异检查。
5. **真实质量门未授权：**真实 FR-042 Graph 应使用固定三组问题、同一已核验 Belarus 来源及真实证据工具/检索链路，每组 3 次；需先通过专用 PostgreSQL/Chroma 隔离预检，并另行获得 DeepSeek 调用预算。按当前 Graph 最坏路径每轮最多 8 次 HTTP 尝试，9 轮预算上限暂按 72 次计算；每次调用前计数、总预算不可覆盖、首次运行故障熔断、不补跑。若预算、隔离资源或成功 Pixie Step 6 不能保证，不得宣称 FR-042 端到端质量通过。该预算是待授权上限，不是当前授权。
