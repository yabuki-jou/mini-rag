# 企业规模 RAG 真实链路复测实施计划

## 1. 目标与边界

本轮使用当前仓库中已确认的需求、架构、接口、实施、评审和交接文档作为事实来源，生成一套
接近企业项目资料密度的虚构评测语料，并实际验证：上传、解析、人工字段确认、正式入档、
PostgreSQL 业务范围、Chroma 索引、bge-base-zh-v1.5 Embedding、本地 Reranker、Top-8
证据保留、DeepSeek 回答、引用和跨项目隔离。

本轮是新增扩展评测，不替换 AV1-P02 固定 12 题，不改变正式模型、Prompt、Chunk、Top-8、
Top-30、Reranker 查询表达或既定质量门。生成资料、运行结果和真实上传副本均为本地临时数据；
源码和标注不得包含 `.env`、Token、数据库内容、上传文件、运行日志或真实业务资料。

## 2. 评测材料规模

- 两个互相隔离的虚构企业项目。
- 规模以当前项目已有文档、模块和业务链路为基准，覆盖需求、架构、数据、安全、接口、实施、
  测试和交接等真实主题；不设置脱离现有项目规模的文件数、字符数或题数硬指标。
- 每份文档包含来自当前项目的实质内容和清晰章节，并保留来源文件清单，使材料可回查到当前
  仓库；不得复制或重复段落凑体量。
- 问题同时覆盖有据、无据和跨项目隔离三类，数量由可稳定标注的实际素材自然确定。
- 有据题必须保存确定答案和准确证据定位；无据题必须与已有主题接近但缺少所问事实；隔离题的
  答案只能存在于另一个项目。
- 所有素材均为项目源码和文档的派生虚构材料，不包含真实账号、主机、密钥或业务数据。

## 3. TDD 实施顺序

### RED

1. 为企业资料生成器增加材料规模、项目隔离、类别分布、证据原文、来源可追溯和敏感模式测试。
2. 为 P14 验收脚本增加自定义评测根目录、企业捕获阶段、Top-8、动态问题数量及输出文件保护测试。
3. 实际运行新增测试并保存失败证据；不得把尚未实现导致的预期描述当作 RED。

### GREEN

1. 新增确定性生成器，将版本化规则生成到 Git 忽略目录，不提交大体量派生文档。
2. 最小扩展现有验收脚本；复用既有注册、项目创建、上传、解析、字段确认、正式入档、检索、
   捕获和精确清理流程。
3. 生成 Pixie 数据集时只把问题发送给生产问答入口，检索候选来自本轮真实 Chroma 请求；
   Ground Truth 只保留在离线评测元数据中。

### REFACTOR 与验证

1. 运行新增材料测试、P14 脚本测试、Pixie 材料测试、完整测试和 `compileall`。
2. 检查 Git Diff，确保没有修改既定架构、公开 API、核心数据库结构和正式质量参数。

## 4. 真实运行与清理

1. 只通过回环地址访问本机 API 和 Chroma；启动前验证 API、PostgreSQL、Chroma、Embedding。
2. 创建唯一临时账号和两个项目，逐份上传、解析、人工确认字段并正式索引。
3. 对全部问题执行真实检索，记录候选池完整性、公开证据覆盖、类别数量和 P95；随后通过 Pixie
   调用真实 DeepSeek，评估答案、引用、证据忠实和拒答。
4. 无论成功或失败，都精确删除本轮文档、项目、会话、用户、文件及对应 Chroma Chunk；清理失败
   必须作为最终失败报告，不得只相信脚本退出码。
5. 结果只保存脱敏聚合、引用定位和虚构文本；完成 pending 评分、dataset analysis、action plan
   与 Step 6 verifier。

## 5. 结果判定

- 真实链路执行完成：全部资料经过公开业务接口进入正式状态，全部问题获得检索响应，清理核对通过。
- 检索结果如实报告：候选池完整率、实际有据题的 Top-8 证据覆盖率，以及无据题和隔离题结果；
  不为达到预设数量重复或硬凑材料。
- 回答质量目标：有据正确回答并正确引用率不低于 80%，无据和隔离题全部正确拒答。
- 新目标只用于本企业规模扩展集；失败时记录问题，不降低目标、不改答案，也不反向宣称 AV1-P02
  固定质量门失效。
