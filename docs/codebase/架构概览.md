# 当前代码架构

## 1. 架构风格

- 主体是同步 FastAPI 模块化单体，目录按横向层划分。
- 请求一般经 `Router → Dependency → Service → PostgreSQL / 文件系统 / Milvus / DeepSeek`。
- 旧制度 Agent 是特例：业务服务调用 `AdminAgentRuntime`，再执行 LangGraph 与受控只读工具；Checkpoint 保存到独立 SQLite。
- 智慧档案当前已实现 P01～P03 基础、P04 前置模型分层、P04.1 项目 CRUD 和 P04.2 清单项 CRUD/派生状态：归档模型、迁移、`ProjectContext`、独立 Parser，以及 `/projects` 的项目和清单 Router/Service/Schema；上传与归档应用服务尚未实现。

## 2. 两条已存在的数据流

```text
旧文档上传/处理：
documents Router → 资源所有权依赖 → document_service
→ 文件系统 → parser/chunk/embedding → Milvus → PostgreSQL documents

旧 Agent 问答：
agent Router → Agent 会话所有权依赖 → agent_service
→ AdminAgentRuntime(SQLite Checkpoint) → LangGraph ToolNode
→ policy_tools → retrieval_service → Milvus
→ PostgreSQL agent_sessions / agent_tool_call_logs
```

`app/main.py::lifespan()` 在启动时先执行 `upgrade_database()`；正式 Schema 由 Alembic 而非 `create_all()` 建立。

## 3. 各层职责

| 模块 | 当前职责 | 不应承担 | 证据 |
|---|---|---|---|
| Router | HTTP 契约、依赖注入、调用服务 | Milvus、DeepSeek、跨存储补偿 | `app/routers/projects.py`、`app/routers/agent.py` |
| Dependency | 当前用户和资源所有权；项目范围绑定 | 归档确认、清单计算 | `app/dependencies/resources.py`、`project_context.py` |
| Service | 状态迁移、事务、外部资源调用 | FastAPI 响应对象 | `app/services/document_service.py`、`chat_service.py` |
| Agent | Prompt、Graph、工具调用观测、Checkpoint | SQLModel Session 生命周期 | `app/agents/admin/` |
| Model / Schema | 分别表达持久化事实与 HTTP 契约 | 复用为可写入的同一对象 | `app/models/`、`app/schemas/` |

## 4. 重复使用的模式

| 模式 | 位置 | 目的 |
|---|---|---|
| FastAPI typed dependency | `CurrentUserDep`、`Owned*Dep`、`ProjectContextDep` | 将身份与资源范围在进入路由前固定 |
| 应用错误 | `AppError` | 统一稳定错误码并隐藏内部异常 |
| 缓存客户端 | `lru_cache` 的模型/Milvus客户端 | 避免进程内重复加载模型和连接配置 |
| 不可变数据载体 | `TextChunk`、`EmbeddedChunk`、`RetrievedChunk`、`ParsedArchiveDocument` | 限制流水线中间值被意外修改 |
| 显式补偿状态 | `DocumentStatus`、`ArchiveOperation` | 处理文件/向量/数据库非原子操作 |

## 5. 类与模块划分判断

- `User`、`KnowledgeBase`、`Document`、聊天、Agent 的模型已按领域拆分；Pydantic Schema 独立，划分合理。
- `ProjectContext` 是小型不可变值对象，放在 dependencies 合理：它是授权范围，不是持久化实体。
- 归档模型已按职责拆分：`project.py` 管理项目隔离与容量计数，`archive.py` 管理档案/快照/字段/证据，`checklist.py` 管理项目清单与人工关联，`archive_audit.py` 管理内部操作和脱敏审计。`app.models` 保持原有公共导出，调用方无需跟随文件移动改写导入。
- `agent_service.py`（618 行）同时处理会话创建、Checkpoint 消息映射、Graph 执行、工具审计持久化和 HTTP 响应组装。其内部私有函数已有分组，但职责过多；后续修改 Agent 时宜按“执行/消息映射/审计”拆分，而非继续添加函数。
- `document_service.py`（369 行）包含旧 RAG 的上传、立即向量化和删除补偿。它对旧文档聚合仍然内聚；智慧档案不应继续往其中加入新状态机，应创建独立归档服务。

## 6. 已知架构风险

- 旧 `users.py`、`knowledge_bases.py` 和文档列表在 Router 内直连 Session，与已声明的 Router→Service 目标不完全一致。
- PostgreSQL 业务库已切换，但多处旧代码注释和文档字符串仍称“SQLite 业务记录”，会误导后续实现。
- 同步解析、BGE 与 DeepSeek 调用会占用请求线程；这是已知 V1 范围限制。
