**亮点(比评审建议更优的两处):**
1. **独立路由 `suggestions/regenerate`** 而非复用 `suggestions`——状态机语义更显式,与"普通解析/解析重试/建议重试/建议重新生成是不同应用服务入口"(架构 §10.2)完全一致;
2. **数据库 §6.5 新增 `source = AI` 仅由建议服务写入**——用户任何字段/证据保存都被强制标记 `MANUAL`,从存储层杜绝了"客户端伪造 AI 来源绕过重新生成保护"的漏洞,这是方案 B 判定可靠性的关键支撑。

## 4. 遗留建议优化(不阻塞,建议实施计划评审时一并处理)

### 上轮已列、本轮未修订(多为文档补句)

1. **`CONFIRMED` 状态下重复 `confirm` 语义未明确**(API §3.2 与 §7 冲突隐患):建议明确"已 CONFIRMED 且版本匹配时幂等返回 200、不重新生成 Chunk 不写审计"。
2. **字段 `PUT` 的版本递增规则未明确**:建议写明"每次成功写入字段/证据使 `archive_documents.version` 原子 +1"。
3. **列表排序 tie-breaker 未固定**:建议统一追加 `id DESC`(NFR-019 稳定性)。
4. **取消确认对 `checklist_links` 的处理未说明**:建议补一句"取消确认不改变关联状态,清单满足性由档案状态与关联状态共同派生"。
5. **正式档案详情与 `archive-retrieval` 响应示例缺失**:建议补充 JSON 示例。
6. **NFR-020 免责声明未写入 API 文档**:建议在通用约定中要求调用 DeepSeek 的接口 OpenAPI 描述包含外部模型数据提示。
7. **问答内部检索参数未固定**(top_k/阈值):建议实施计划中固定,保证 12 个验收问题可复现。

### 本轮新发现

8. **"模型输出不合格"缺少稳定错误码**(API §7 第 389 行写"返回 `503` 或稳定的格式错误",但 §10 错误码表无对应码):建议新增 `422 SUGGESTION_INVALID_OUTPUT`(模型格式错误,不自动重试,符合 BR-023)或明确复用现有码,避免实现歧义。
9. **§7 状态表 regenerate 行措辞"原子替换 AI 草稿"**:当原草稿为空白人工草稿(无 AI 值)时表述略不精确,建议改为"原子替换现有草稿"。
