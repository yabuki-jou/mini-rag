草案整体质量可接受：独立 Graph、独立 Checkpoint 文件、两个只读工具、完成轮次标记、
`DELETING` 会话、幂等线程清理这六个选择，都能在实际代码中找到承接点，也与 DEC-015～DEC-017
的裁决一致。§16.1 的 AC 映射基本完整（AC-01～AC-18 均有承接，无遗漏）。

D5/D6 判定逻辑或第二套会话状态机。因此本轮不确认。

## 4. 必须修改

### A1 事务与锁范围：项目行锁不能跨越 60 秒模型调用

- **位置**：§10.7.1 L632-634（「执行入口在数据库事务中按『项目 → 会话』的固定顺序加锁」）。
- **问题**：句子没有限定锁的持有范围。按其字面实现（在请求 Session 上加 `Project.with_for_update()`，直到 `commit_execution` 才提交），项目行锁会横跨整个 Graph 执行。
- **证据**：
  - 会话消息路由的会话依赖 `OwnedAgentSessionDep` 在进入服务前已执行 PG 查询，请求事务在模型调用前就已开启（`app/routers/agent.py` L52-65、`app/dependencies.py` 中的所有权依赖）。
  - 上传路径对同一 `Project` 行加锁（`app/services/archive/documents.py` L64-66）。两者叠加后，同项目的一次上传会被一个最长 60 秒的助手轮次阻塞。
  - 现有单链路 P95 已记录为 `3670.83～9512.28 ms`（`FR-042-需求评审.md` §8.5），助手一轮还要叠加工具选择与证据判定调用，持锁时间不可忽略。
- **影响**：同项目上传、解析确认、清单变更等所有需要项目行锁的操作全部排队；并发轮次会长期占用连接池。这是比「删除与轮次交叉」更常见的故障路径。
- **建议**：把锁的粒度从「项目」改为「会话」，只在短事务内使用项目锁：
  1. **消息轮次**：开启轮次时对 **AgentSession 行**加锁并校验 `status=ACTIVE`、项目归属与类型；该行锁可以持有到轮次结束（同一会话本就应串行），不再触碰 Project 行。
  2. **项目删除**：短事务内锁 Project → 锁该项目全部 ARCHIVE 会话 → 置为 `DELETING` → 提交（立即释放）。后续删 Checkpoint、删业务记录不需要项目锁。
  3. **创建会话**：短事务内锁 Project（防删除窗口内新建会话），写会话后立即提交。
  这样同样能做到「删除与轮次不交叉完成」：轮次持会话行锁期间删除只能等到该行释放；删除先提交 `DELETING` 后，新轮次在校验阶段即被拒绝。**请在草案中把这三段锁范围显式写出。**

### A2 单次模型决策多个 Tool Call 的处置与需求口径冲突

- **位置**：§10.7.2 L655-657（「模型每次决策最多产生一个 Tool Call……若模型一次返回多个 Tool Call……统一转入 `complete_failure`」）、§16.1 L910（AC-13/AC-14 承接为「单次一个 Tool Call」）。
- **问题**：需求允许一次选择多个工具，架构禁止一次返回多个调用，两者不兼容。
- **证据**：
  - 需求 §正常流程 3 L801：「模型按问题选择以下**一个或多个**只读工具」。
  - 需求 §正常流程 7 L816-818：「单轮最多允许**两个**模型发起的工具调用；参数校验失败的调用也计入该上限」。
  - AC-13（需求 L884-885）只在「尝试发起**第三次**工具调用」或「达到 60 秒」时要求停止。
  - 因此「一条 AIMessage 携带 2 个并行 Tool Call」在需求口径下完全合法（恰好用满预算），在架构口径下却会整轮失败。
- **影响**：DeepSeek 并行工具调用是正常行为。按当前架构，模型一旦并行发起「目录 + 证据」两个调用（这正是本功能最自然的组合），用户会得到一个「助手不可用」的失败轮次，而不是答案。这会直接污染 §12.5 的真实固定集结果。
- **建议**（三选一，需你裁决）：
  1. **按剩余预算执行**：预算节点原子扣减剩余额度，只执行前 `剩余额度` 个调用，超出的调用以确定性拒绝结果返回给模型并计入计数（推荐：实现简单，语义与需求完全一致）。
  2. **需求改为「每次决策最多一个工具调用」**，把并行调用明确写为不支持，并同步修订 AC-13。
  3. 维持整轮失败，但必须在需求 §12.5 固定集中显式标注该路径为预期失败，以免被误判为质量回归。
  无论选哪个，§16.1 的 AC-13/AC-14 承接说明都要同步改写。

### A3 证据工具的结果投影未定义，持久化标识可能进入模型上下文

- **位置**：§10.7.3 L677-680 的工具表（证据工具「结果边界」列只写「FR-039 证据项」）。
- **问题**：「FR-039 证据项」既可以指 API 响应 DTO，也可以指送进提示的证据投影，两者字段集合完全不同。
- **证据**：
  - API DTO `ArchiveRetrievalItemRead` 含 `chunk_id`、`document_id`、`score`、`reranker_score`（`app/schemas/archive_retrieval.py` L20-31）。
  - 而 FR-039 的提示投影只保留请求内临时引用 `D1..Dn`、`filename`、`location`、`excerpt`，并明确声称「不包含持久化标识」（`app/services/archive/questions.py` L29-62）。
  - 架构对目录工具明确写了「不含 UUID、版本或正文」（L679），对证据工具却没有对应约束。
- **影响**：若证据工具的 `ToolMessage.content` 直接序列化 API DTO，模型可见 `document_id`/`chunk_id`，工具调用审计（`result_summary_json`）也会带上这些标识。这既与目录工具的隐私原则不一致，也与 §14 的脱敏要求冲突，且模型可能把 UUID 复述给用户。
- **建议**：在工具表的「结果边界」列显式写出证据工具的 DTO：仅 `请求内证据编号 + 文件名 + 位置类型/起止 + 摘录`，`document_id`/`chunk_id`/`score`/`reranker_score` 由服务端映射表持有，**不得进入 ToolMessage、Checkpoint 或审计摘要**。AC-07、AC-17 的承接点同步补充。

### A4 「复用 questions.py 的 D5/D6」在当前代码结构下不成立

- **位置**：§10.7.3 L687-690（「Graph 改用不绑定工具的结构化最终调用，复用 `questions.py` 的 D5/D6 JSON 判定、Top-8 文档绑定和引用编号解析」）。
- **问题**：`questions.py` 没有可复用的公共判定边界。
- **证据**：
  - `_build_archive_prompt`（L29-77）与 `_parse_model_decision`（L92-148）均为**模块私有**函数。
  - 唯一公共入口 `answer_archive_question`（L151-291）**自带检索**（L182-191）。若 Graph 直接调用它，就会「工具已检索一次 + 函数内再检索一次」，与 §10.7.3 开头「工具本身不调用第二个模型、也不出现双重事实生成」的意图不一致（重复的是检索与候选，不是事实生成，但同样浪费预算并可能返回与工具结果不同的候选集）。
- **影响**：实现者只能二选一——复制判定逻辑（产生第二套 D5/D6，日后 P14 路线调整必然漂移），或让 Graph 重新检索（预算与候选不一致）。两者都不可接受。
- **建议**：在架构中明确写出**服务边界的抽取方案**，例如在 `app/services/archive/questions.py` 中抽出公共函数
  `judge_archive_answer(*, question: str, candidates: list[ArchiveRetrievalItemRead]) -> ArchiveQuestionResponse`，
  由 `answer_archive_question` 与档案 Graph 的最终节点共同调用（前者内部先检索，后者直接用工具返回的候选）。
  `_REFUSAL_ANSWER` 与固定拒答文案保持单一来源。请把该抽取写入 §10.7.3，并同步 §12.5 的「不降低既有门槛」说明。

### A5 逐调用超时下传在当前基础设施上无法实现

- **位置**：§10.7.2 L665-666（「应用服务把 60 秒剩余预算下传为每次 DeepSeek、Chroma 和目录数据库调用的超时上限」）。
- **问题**：现有模型与向量客户端不支持逐调用超时。
- **证据**：
  - `get_chat_model()` 是 `@lru_cache` 且**不接受任何参数**，构造 `ChatOpenAI` 时未设置 `timeout` 或 `max_retries`（`app/services/infrastructure/ai_models.py` L41-77）。共享单例也意味着无法按请求注入不同超时。
  - 检索链路（`app/services/archive/retrieval.py`）通过 `langchain_chroma` 调用，当前没有传入超时参数。
  - 目录工具走的是同库 Session，数据库语句超时属于另一套机制（PostgreSQL `statement_timeout`），与「剩余预算」不是同一个量。
- **建议**：把该句拆成可执行的两种表述，并在架构中选一种：
  1. **仅外层截止**（推荐本期）：明确「60 秒是外层截止时间，进程内单调时钟在节点返回点强制判定；底层调用不设逐调用超时，超预算时按安全失败收尾」，并把「客户端超时参数化」列为后续改造项。
  2. **列入改造范围**：明确要改 `get_chat_model` 的缓存契约（例如改为 `get_chat_model(*, timeout: float | None)` 或提供带超时的请求级客户端工厂），并在实施计划中登记为独立任务。
  未选定前，「下传剩余预算」是一句无法验收的承诺。

### 10.3 新发现：数据库设计开工前必须补齐

#### D1 AgentTurn 与 Checkpoint 消息之间缺少关联键

- **位置**：技术架构 §7 L301-302、§10.7.2 L679-682 与 L687-688。
- **问题**：§7 把 `AgentTurn` 定义为「只保存轮次 UUID、会话归属、完成状态和时间」，**没有任何消息标识**；
  但 §10.7.2 同时要求
  1. 「只把最近 10 个已完成历史轮次的 User/Assistant 文本对投影给模型」——文本只存在于 Checkpoint，
     必须先知道哪些 Checkpoint 消息属于这 10 个轮次；
  2. 「历史投影只展示具有相同 `turn_id` 的 HumanMessage 与最终 AIMessage 成对出现的轮次」——
     这句话直接假定消息携带 `turn_id`，而 `turn_id` 在 §10.7.2 被定义为 **Graph State 字段**，不是消息属性。
- **为什么不能靠顺序推断**：设计中的失败分支恰好会打破 1:1 对应——Checkpoint 写失败可能留下
  半个轮次（只有 HumanMessage）；PG 提交失败会留下 Checkpoint 有完整对、PG 为 ABORTED 的轮次。
  按位置对齐在这两种情况下会错位，进而把不该可见的消息投影给模型。这正是 BR-037 要防止的情况。
- **建议**（二选一，写进 §7 与 §10.7.2）：
  1. 规定「轮次的 HumanMessage `id` 等于 `turn_id`，最终 AIMessage 的 `id` 记入 AgentTurn 的
     `assistant_message_id`」；或
  2. 在 AgentTurn 上增加 `user_message_id` / `assistant_message_id`（仍不保存正文）。
  两者都能同时支撑「历史可见性过滤」和「最近 10 轮投影」，且不违反「轮次元数据不保存消息正文」。

#### D2 AgentTurnCitation 与文档删除流程之间缺少联结点

- **位置**：技术架构 §10.7.3 L728-729、§14.2 L894-895 与 §10.6 L605-622、§12.1 L832。
- **问题**：前两处写明引用「随会话或关联档案删除」，后两处是现有的文档物理删除流程和一致性表，
  其中**只列出**原文件/快照、Final Chunk、字段/证据/关联/业务记录与审计，**没有 AgentTurnCitation**。
  项目删除（§10.7.5 L767）反而写了 `delete turn citations`。即：引用会随项目删除被清理，却不会随
  文档删除被清理。
- **影响**：文档删除后，历史响应会继续返回指向已删除文档的引用——与需求 L831-832「已删除档案不得
  出现在目录工具、原文工具或助手回答中」产生第二种读法。
- **建议**：
  1. 在 §10.6 的删除步骤与 §12.1 的「删除」行补上 AgentTurnCitation 清理；
  2. 同时在需求或 §10.7.3 明确：**历史回答正文不做回溯改写**，其引用按当前可见性过滤/随文档删除，
     因此历史可能呈现「有答案文本、无该条引用」。
  （第 2 条是把已有的两处表述固化为唯一口径，不是新增产品范围。）

## 11. MVP 收敛复审与最终结论（2026-09-14）

### 11.1 复审结论

原 §9～§10 的架构可以实现，但为了处理低频跨存储失败与并发删除，新增了两张业务表、一种会话
状态、动态截止适配器和工具批次规则，已经超过当前本地学习与作品集演示目标。用户确认按
DEC-019 收敛后，技术架构已改为：

- `AgentSession` 只新增 `agent_type` 和可空 `project_id`；
- 不新增 AgentTurn、AgentTurnCitation 或 `DELETING`；D1、D2、D3 因对应实体取消而不再成立；
- 档案助手使用独立 Graph/消息投影，但复用同一受保护 Checkpoint 文件；
- 一次决策最多一个 Tool Call，单轮最多顺序两个，不处理并行批次；
- 当前引用使用请求内映射，历史只返回正文；
- 最终基础设施失败统一返回 503，不设计完整失败轮次状态；
- 使用现有可配置超时并记录真实基线，不实现跨组件动态 60 秒预算；
- 项目删除按幂等线程清理后删除 PostgreSQL 记录，不承诺并发消息/删除强一致性。

### 11.2 不可降级边界

收敛没有放宽用户/项目/知识库隔离、CONFIRMED 与删除阻断过滤、服务端范围注入、Top-8+D5/D6、
当前回答引用、无依据拒答、会话类型隔离或审计脱敏。它删除的是非主链路的生产级保证，不是安全
主线。

因此，**FR-042 MVP 架构主审通过，并已由用户确认。** 可以继续数据库/API 设计；代码实现仍须等待
明确 Implementation Plan，并按 Multi-Agent Development Workflow 与逐行为 TDD 推进。本轮只做
文档静态审查和修订，没有运行代码测试或真实 PostgreSQL、Chroma、DeepSeek、SQLite 验证。
