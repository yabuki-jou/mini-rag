## 1. 不变量与范围

- PostgreSQL 是确认状态、项目授权和删除可见性的事实来源。
- Chroma 是唯一候选来源，查询必须包含服务端构造的 `user_id + project_id + kb_id + document_id`。
- 阶段 C 的唯一例外是本地 `BAAI/bge-reranker-base` 对已授权、已校验的 Chroma Top-20 重排。
- 不引入 BM25、混合检索、远程 Rerank、跨项目检索或无授权的 Chunk 修改。
- 引用继续使用原始 Final Chunk 的正文、文件名、定位和 Chunk ID。
- 未冻结任何 `retrieval_distance_threshold`、`archive_reranker_score_threshold` 或向量表示模式。

## 4. 决策门

1. `candidate_count=10` 且标准证据不在 dense 候选中：只能记录“召回缺失”，不得自动改 Chunk。
2. 标准证据在 dense Top-10 但 Reranker 排序或分数不可分：只能记录“重排不可分”，不得自动换模型或改查询表达。
3. 候选池不足 10 条：只能记录“候选池不完整”，不得据此断言召回缺失。
4. 出现 `OUT_OF_SCOPE` 候选：停止质量优化，优先修复授权或范围校验。
5. 只有同时达到 `>=7/8`、`2/2`、`2/2`，才允许冻结独立重排阈值并启动 P12。

以上第 1～3 项产生的 Chunk 调整、查询表达、换模型和评测集修改均属于产品/范围决策，
必须重新授权，不得视为当前 Reranker 例外的自然延伸。

## 6. 获授权后的统一 TDD 流程

1. 先写并实际运行可观察行为的 RED 测试。
2. 只实现使测试通过的最小行为，保持授权范围内的接口和数据事实。
3. 相关测试通过后再重构；所有新增注释和文档字符串使用中文。
4. 运行阶段定向测试、全量 `pytest` 和 `compileall`。
5. 复用健康本机 `8000`，运行同一固定 12 题；保存安全聚合结果并清理验收数据。
6. 只有质量门槛全部通过，才更新需求/架构/接口冻结状态并进入 P12。
