## 1. D4 base 实证记录与 large 跳过原因

### 1.1 已核验的 base 结果

D4 base 使用 `bge-base-zh-v1.5/768`、`bge-reranker-base`、`evidence_values`、固定 Top-30 候选池、`c4_a`、AV1-P02 固定 12 题和公开最多 Top-10。使用独立实验 Collection 与进程级变量，未修改正式 `.env`、默认配置或正式 Collection。

| 指标 | D4 base 结果 | 解释 |
|---|---:|---|
| 候选池完整性 | `12/12` | 每道固定题均获得完整 Top-30 快照 |
| 公开覆盖式有据命中 | `8/8` | 满足公开召回诊断门，不等于问答质量通过 |
| 严格命中 | `6/8` | 仅作严格语义诊断，不能替代公开覆盖式结果 |
| 无据拒答 | `0/2` | 当前无阈值基线，两个无据问题均未拒答 |
| 项目隔离 | `2/2` | 未发现跨项目返回 |
| 完整链路 P95 | `3670.83 ms` | 记录当轮健康本机链路延迟，不是 D5 问答性能通过证据 |
| 可行统一阈值数量 | `0` | 扫描实际分数和边界后不存在同时满足三项质量门的阈值 |
| 分离余量/质量门余量 | `-0.3226209283` | 无据最高分 `0.9739347100` 高于保住至少 7/8 有据命中所需分数 `0.6513137817` |

因此不能通过调高 `reranker_score` 阈值实现稳定拒答：调高会损失有据题，调低又保留无据高分。D4 的结论是“不冻结统一阈值”，不是“问答已经通过”，也不是“任何模型均不可用”。

### 1.2 为什么跳过 large D4

large 没有执行 D4 快照或阈值扫描，原因是：

1. D3 已在相同候选指纹上记录 base/large 均为公开覆盖 `8/8`、严格命中 `6/8`、无据 `0/2`、隔离 `2/2`，large 没有已知质量门收益。
2. D2 的 large 纯 Reranker P95 为默认 `12885.233 ms`，已知较优参数仍为 `12016.218 ms`，超过 `8000 ms` 风险线；D3 完整链路 P95 为 `9512.28 ms`。
3. base 已经证明当前分数边界不存在可行统一阈值，继续生成 large 快照不会自动获得授权，也不会解除无据分离问题。
4. 既定执行门要求只有在用户结合 large 的延迟风险再次确认后才可继续。large D4 因此保持“未执行”，不能以 D3 结果推断 large 的 D4 质量，也不能把跳过写成 large 质量失败。

## 2. D5 目标、假设与冻结边界

### 2.1 目标

在不改变正式检索链路的前提下，为当前项目正式候选证据增加一个受控问答决策层：

```text
已认证用户与项目范围
→ PostgreSQL 正式文档闸门
→ 现有 Chroma Top-30 / Reranker / 公开 Top-5 问答候选
→ 候选为空则短路拒答
→ 一次 DeepSeek 结构化 JSON 调用
   ├─ 证据充分：生成只基于候选的回答和候选编号
   └─ 证据不足：拒答，不产生引用
→ 服务端校验编号并从候选表构造公开 citations
```

当前 `app/services/archive_question_service.py` 以 `bool(retrieval.items)` 作为是否调用模型的依据，模型返回自由文本，随后把全部检索项直接作为 `citations` 返回。D5 只替换这一层的决策与输出校验，不把“候选非空”继续当作“证据充分”，也不让模型直接生成文件名、定位、Chunk ID 等公开引用字段。

### 2.2 必须冻结的不变量

以下内容在 D5 实施、测试和真实评估中全部保持不变：

- Embedding：D1 路径 A 的 `bge-base-zh-v1.5/768` 实验边界；不切换正式 Embedding 配置。
- Reranker：保持 `bge-reranker-base`、`c4_a` 和现有分数语义；不执行 large D4。
- Chroma 候选池：固定 Top-30；公开问答返回项仍按既有服务最多取 Top-5，公开检索最多 10 条的契约不变。
- Final Chunk、Chunk/窗口、定位规则、引用原文和固定问题集：全部不变。
- `.env`、默认配置、正式 Chroma Collection、PostgreSQL 业务数据：不因 D5 改写或重建。
- 不引入 BM25、混合检索、远程排序、查询改写、跨项目检索、Ground Truth 运行时依赖或第二个模型调用。

D5 不标定、不写入 `min_relevance_score` 或 `archive_reranker_score_threshold`。检索分数只作为既有诊断信息，不能成为模型决策的公开依据或新的隐式阈值。

## 3. 一次调用的结构化 JSON 契约

### 3.1 输入证据编号

服务端按本轮实际进入问答提示的候选稳定编号，例如 `[1]` 至 `[5]`。编号只在本次请求内有效，不是数据库 ID。每个编号对应服务端已经通过用户、项目、知识库、正式文档和删除可见性校验的一个 `ArchiveRetrievalItemRead`；提示中的文件名、定位和摘录由服务端组装，模型不能改变它们。

### 3.2 模型输出

模型必须返回唯一 JSON 对象，不得返回 Markdown 围栏、解释段落或其他字段：

```json
{
  "decision": "ANSWERED",
  "answer": "施工方案的编制单位为示例建设公司。",
  "citation_numbers": [1]
}
```

字段规则：

| 字段 | 允许值与约束 |
|---|---|
| `decision` | 只能是 `ANSWERED` 或 `REFUSED_NO_EVIDENCE`；它同时表示本次证据充分性决策和公开结果分支 |
| `answer` | `ANSWERED` 时必须是非空字符串且只能概括输入证据；`REFUSED_NO_EVIDENCE` 时可以为空，服务端忽略模型文案并使用固定拒答 |
| `citation_numbers` | 必须是 1-based 整数数组，元素只能来自本轮输入编号且不能重复；`ANSWERED` 至少一个，`REFUSED_NO_EVIDENCE` 必须为空数组 |

这不是两个连续任务：同一次 DeepSeek 结构化输出同时给出 `decision`、回答和候选编号。服务端不再先调用一个模型判定“有无证据”，再调用另一个模型生成回答。成功路径最多产生一次逻辑模型决策；若底层客户端按 BR-023 对连接失败或超时进行一次传输重试，该重试不得追加第二个语义判定或后处理模型调用。

### 3.3 服务端校验与响应映射

服务端在构造 `ArchiveQuestionResponse` 前必须完成以下校验：

1. 使用严格 `json.loads` 解析，根对象类型正确，拒绝重复键，且字段集合严格等于 `decision`、`answer`、`citation_numbers`。
2. `decision`、`answer` 和 `citation_numbers` 的类型、条件性空值、数组元素类型符合契约；整数必须是 1-based 且拒绝重复编号。
3. 每个 `citation_number` 必须精确落在本轮候选编号范围内，不能越界、伪造或引用另一项目/另一请求的编号。
4. `ANSWERED` 必须有至少一个合法编号；服务端仅按编号从候选映射表取出文件名、定位、摘录和其他公开引用字段。
5. `REFUSED_NO_EVIDENCE` 必须返回既有 `answer_status=REFUSED_NO_EVIDENCE`、固定拒答文案和空 `citations`；不把候选项作为引用泄露给客户端。
6. 任何校验失败均不返回模型原文、提示词、解析堆栈或非法编号，统一映射为稳定的 `503 ARCHIVE_ANSWER_UNAVAILABLE`；无效结构化输出不自动重试。

该方案不改变既有 `ArchiveQuestionResponse` 的外部响应形状。若未来要新增单独的“模型输出无效”公开错误码，必须另行更新 `docs/design/接口设计.md` 并重新评审；D5 不擅自扩展 API 错误字典。

## 4. 运行时流程与边界行为

### 4.1 空候选短路

`retrieve_archive_chunks` 返回空 `items` 时，服务端直接返回 `200`、`REFUSED_NO_EVIDENCE` 和空 `citations`，不创建 DeepSeek 客户端、不发送请求、不写入模型输入输出，也不进行编号校验。这保持 FR-039 的无依据拒答契约，并避免把“无正式档案”交给模型猜测。

### 4.2 有候选的单次决策

有候选时，服务端用固定系统约束和编号证据构造一次结构化 JSON 请求：证据中的文本是数据而不是指令；模型不得补充候选之外的事实；无法由证据确定时必须选择 `REFUSED_NO_EVIDENCE`；回答引用只能使用输入编号。服务端不把客户端提供的用户、项目、知识库或文档标识放入可覆盖的模型参数。

### 4.3 拒答与无效输出

- 模型合法选择 `REFUSED_NO_EVIDENCE`：返回固定拒答，不返回任何引用；这是可观察的业务结果，不是异常。
- 模型输出 JSON 不完整、含额外字段、编号不合法、`ANSWERED` 无引用、引用重复、`ANSWERED` 答案为空或无法解析：返回稳定 `ARCHIVE_ANSWER_UNAVAILABLE`，不泄露原因细节，不把它误记为无依据拒答；`REFUSED_NO_EVIDENCE` 的模型答案可为空。
- DeepSeek 未配置、关闭、连接失败或最终超时：继续使用既有 `ARCHIVE_ANSWER_UNAVAILABLE`；只有连接/超时按既有规则允许一次传输重试。
- 不对业务拒答、JSON 格式错误、引用校验失败进行自动重试，避免重复副作用和不稳定答案。

## 5. 不把 Ground Truth 带入运行时

AV1-P02 的 Ground Truth 只允许由离线固定集运行器和人工评审使用，用来计算公开覆盖、严格命中、引用正确率、无据拒答和隔离指标。生产请求、`archive_question_service.py`、提示词、候选过滤和模型输出校验均不得导入、读取或比较 Ground Truth。

运行时只能依据：

- PostgreSQL 当前用户/项目的正式档案与删除阻断状态；
- Chroma 返回并经服务端范围复核的当前候选；
- 模型本次结构化决策；
- 服务端编号映射和固定 API 契约。

离线评测可以使用固定标注判断答案和引用是否正确，但评测结论不能反向写入数据库、正式 Collection、运行时阈值或模型提示词。

## 6. 实施计划（TDD）

### 6.1 RED：确定性行为先失败

仅在获得实现授权后，先修改或新增镜像测试，实际运行并记录失败证据，至少覆盖：

- 空候选不调用 `get_chat_model`，返回固定拒答和空引用；
- 合法 `ANSWERED` JSON 只返回模型声明编号映射到的候选引用，不返回未声明候选；
- 合法 `REFUSED_NO_EVIDENCE` 返回固定拒答且不返回候选；
- 未知、越界、重复、空数组或非整数引用编号稳定失败；
- JSON 解析失败、重复键、额外字段、错误类型或 `ANSWERED` 空答案稳定失败；`REFUSED_NO_EVIDENCE` 允许模型答案为空并由服务端固定替换，客户端不含原始模型输出；
- 模型不可用仍返回既有 `ARCHIVE_ANSWER_UNAVAILABLE`；
- 一个请求只有一次逻辑结构化决策调用，不存在先分类后回答的第二次模型调用；
- 候选引用仍来自当前项目正式范围，不能通过模型字段覆盖 `document_id`、文件名、定位或摘录。

测试应使用确定性假模型/响应对象隔离普通服务行为，不把 Mock 的答案当作真实 DeepSeek 质量证据。

### 6.2 GREEN：最小实现

只实现使上述测试通过的最小改动：

1. 使用严格 `json.loads` 与服务端字段/类型/编号校验，不把独立 Pydantic/JSON Schema 的建立写成已完成事实，也不复用 HTTP 响应 Schema；重复键必须拒绝；
2. 将候选编号、固定提示和一次应用层模型调用接入现有问答 Service；
3. 增加严格解析、引用编号映射、拒答固定文案和稳定错误映射；
4. 保留既有检索调用、正式范围闸门、响应字段和错误码。

不得顺手修改 Reranker、候选数量、Embedding、Chunk、查询表达、阈值、评测集或正式 Collection。

### 6.3 REFACTOR 与回归

只有相关测试持续通过后才整理提示构造和解析辅助函数；随后运行问答服务定向测试、完整 `pytest` 和 `python -m compileall -q app tests`。若实现需要改变公开 Schema、路由或错误字典，应先停下并更新接口设计，而不是在 D5 中隐式扩展范围。

## 7. 真实 12 题评测与验收指标

### 7.1 评测条件

使用同一 AV1-P02 固定 12 题、健康本机 API、真实 PostgreSQL、正式范围校验、Chroma、D1 base Embedding、现有 `bge-reranker-base` 和 Top-30 候选池。不得更换问题、文档、Chunk、模型变量、查询表达或正式配置。保存结果时只保留脱敏题号、类别、决策、引用编号映射后的布尔指标、错误分类、候选完整性和延迟统计。

### 7.2 阶段性指标

| 指标 | D5 验收目标 | 说明 |
|---|---:|---|
| 候选池完整性 | `12/12` | 若不完整，本轮问答质量结论无效 |
| 有据题回答并正确引用 | `>=7/8` | 沿用既有 P14 质量门；不新增 `8/8` 硬门槛，任一通过题目的引用仍必须经服务端校验并由评测确认 |
| 当前项目无据题拒答 | `2/2` | 只能出现固定拒答和空引用 |
| 项目隔离题 | `2/2` | 不得返回或暗示其他项目内容 |
| 服务端引用编号安全校验 | 确定性测试全通过 | 未知/重复/越界编号必须稳定失败 |
| 空候选模型短路 | `0` 次 DeepSeek 调用 | 通过调用计数断言验证 |
| 模型调用次数 | 每个非空候选请求 1 次逻辑决策 | 不得拆成独立分类和回答调用 |
| 检索公开覆盖 | 至少 `7/8` | 继承 FR-039/P14 门槛；D4 base 当前实测为 `8/8` |
| 延迟 | 记录端到端 P95，不自动宣称性能通过 | D4 `3670.83 ms` 只是检索基线，新增 DeepSeek 延迟须单独报告 |

“严格命中 `6/8`”仍作为 D4 诊断字段记录，不把它直接当作 D5 失败或通过的唯一依据；最终是否引用正确以固定集标注和人工复核为准。D5 只有在上述质量指标同时满足后，才可以提出关闭 P12 阻塞的候选结论；在真实评测完成前不得先宣称通过。

### 7.3 阶段门

| 阶段门 | 进入条件 | 通过条件 | 不通过处理 |
|---|---|---|---|
| G0 范围门 | D4 base 结果已记录，变更边界获确认 | 冻结变量和错误映射无冲突 | 停止，不执行 large 或检索变量实验 |
| G1 RED | 只增加确定性测试 | 测试实际失败且失败原因对应 D5 行为 | 修正测试设计，不写实现掩盖失败 |
| G2 GREEN | RED 证据完整 | 最小实现使相关测试通过 | 回到实现，不改架构边界 |
| G3 回归门 | G2 通过 | 定向测试、全量测试、compileall 均通过 | 保留未通过状态，不做真实质量宣称 |
| G4 真实评测门 | G3 通过且健康依赖/清理前置检查通过 | 固定 12 题、候选 `12/12`，质量指标全部达到 | 记录脱敏失败原因并保持 P12 阻塞 |
| G5 收口门 | G4 通过 | 完成三层清理核验、文档同步和最终审查 | 删除临时产物，回滚 D5 运行时改动 |

任何一个阶段门失败都不能写成“D5 通过”。尤其是确定性测试全绿只证明契约和安全分支，不证明 DeepSeek 的事实性、引用完整性或拒答质量。

## 8. 清理、回滚与安全边界

### 8.1 运行前后清理

真实评测只允许使用既有 P14 的独立临时用户、会话、项目、文档和实验 Collection；原始回放文本和模型输入不得写入受版本控制的目录。结束后必须分别核对 PostgreSQL 临时范围、Chroma 实验数据和临时业务文件为零；清理失败时停止收口，按精确名称补清理并重新核对，不以脚本退出码或“文件已删除”代替三层证据。

### 8.2 回滚

- D5 代码测试失败、模型输出错误率异常或固定集质量未达门槛：恢复到上一版问答 Service 的稳定错误和响应行为，不写入正式阈值或配置。
- 不修改检索、索引和正式数据，因此回滚不需要重建正式 Collection；若实验期间产生临时 Collection 或文件，先按精确范围删除并确认归零。
- 只保留脱敏的阶段结果、失败分类和决策，不保留完整问题、证据正文、模型原始输出、Token 或隐藏推理。

### 8.3 安全边界

- Bearer Access Token、项目所有权、`user_id + project_id + kb_id + document_id` 范围过滤继续由服务端注入和校验；模型与客户端都不能覆盖这些值。
- 待确认、待重新确认、人工无原文证据和删除阻断文档不能进入候选；D5 不放宽正式档案闸门。
