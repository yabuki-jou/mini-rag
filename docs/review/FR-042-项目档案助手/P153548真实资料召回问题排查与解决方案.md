# P153548 真实资料召回问题排查与解决方案

> 历史状态（截至 2026-09-23）：召回问题已完成定位，正式修复当时尚未授权。后续决策、实施与验证进度以[当前交接快照](../../stage/handoff.md)、[世界银行贷款证据补充召回实施计划](../../implementation/FR039-FR042世界银行贷款证据补充召回实施计划.md)和[拒答边界与评测口径修正实施计划](../../implementation/FR039-FR042档案回答拒答边界与评测口径修正实施计划.md)为准。
>
> 适用范围：FR-042 项目档案助手使用 P153548 芦山地震项目公开资料进行的真实资料质量排查。
>
> 证据边界：本文只记录本轮真实持久层验收、检索排序诊断、PDF 解析检查和只读向量控制中已经得到的结果，不把候选方案写成已实现能力。

## 1. 问题现象

在真实 P153548 资料的隔离持久层验收中，资料可以完成上传、解析、人工确认和正式索引，但针对“世界银行贷款金额”等中文问题，目标标准证据没有稳定进入检索结果的前部。

当前已观察到的现象如下：

- 四份公开项目 PDF 均完成索引，Top-8 有据检索覆盖为 `2/3`。
- `LUSHAN-01` 的标准证据未进入 Top-30，因此后续重排和引用生成没有机会基于该标准证据工作。
- 同一页的标准证据实际存在于解析结果中，并非源文件缺失或解析为空。
- FR-039 的有据回答正文出现了目标事实，但缺少目标引用；无据拒答场景通过。
- FR-042 的多轮历史、消息和脱敏工具记录可以写入并读取，召回问题与持久层保存失败不是同一个故障。

因此，当前问题应表述为：

> P153548 真实资料已经被保存、解析并索引，但中文“世界银行”类问题与原文中的 `IBRD` 术语没有形成稳定的 dense 语义对齐，导致目标证据在召回阶段丢失。

## 3. 排查时间线

### 3.1 持久层 E2E 验收

首先使用真实 P153548 公开资料，在隔离的 PostgreSQL Schema、临时 Chroma Collection、临时文件目录和临时 SQLite Checkpoint 下执行完整链路：

```text
公开 PDF → 上传 → 解析 → 人工确认 → 正式索引
→ FR-039 / FR-042 查询 → 历史和工具记录读取 → 全层清理
```

结果显示四份资料均可以完成索引，且 PostgreSQL、Chroma、文件系统和 SQLite 均有真实写入。清理后各层归零，说明本次测试没有把残留业务数据混入后续诊断。

### 3.2 Top-8 结果复现

在相同的固定资料和查询下，Top-8 有据召回覆盖为 `2/3`。其中 `LUSHAN-01` 的标准证据没有进入 Top-30。

此处的定位意义是：问题已经发生在候选集形成阶段。若标准证据连 Top-30 都没有进入，就不能先把主要责任归因于 Reranker、引用映射或回答生成。

### 3.3 Top-30 双排序诊断

为区分 dense 召回与后续排序，针对同一查询同时观察 dense 排序和经过后续排序的候选结果。诊断结果显示，`LUSHAN-01` 的标准证据在 dense 候选阶段就没有进入 Top-30。

这一步将排查范围从“回答没有引用”收窄为“目标证据没有被召回”。同时也避免把后续引用卡片缺失误判为唯一根因。

### 3.4 PDF 解析检查

对 P153548 的解析结果进行页级检查：

- 全部解析结果包含 `66` 个页级 Chunk。
- 目标标准证据位于第 `16` 页。
- 第 `16` 页被解析为单个 `2370` 字符的 Chunk。
- 该 Chunk 内包含约 `300` 字符的标准摘录，证明标准证据确实存在于解析文本中。

因此可以排除“源 PDF 没有这段文字”以及“目标页完全没有被解析”的解释。

在不修改正式应用行为的前提下，对只读向量结果进行控制比较。控制集合包含 `190` 个向量，重点比较不同查询表达对目标页排名的影响：

| 去掉格式要求 | 110 |

## 4. 如何定位

本次定位遵循以下证据链：

```text
持久层 E2E
  → 确认资料确实写入并索引
Top-8
  → 复现真实用户可见的召回缺失
Top-30 双排序
  → 确认目标证据未进入候选集
解析检查
  → 确认第 16 页存在标准证据
只读向量控制
  → 比较术语替换对目标页排名的影响
```

每一层的判定作用如下：

1. 持久层 E2E 用来排除“数据没有保存”“索引流程没有完成”和“服务重启后记录丢失”等基础设施原因。
2. Top-8 用来确认问题确实影响实际问答，而不是只存在于内部诊断日志。
3. Top-30 双排序用来判断问题发生在 dense 召回、后续排序还是引用生成阶段。
4. 解析检查用来验证目标事实是否存在于进入索引的文本中。
5. 只读向量控制用同一批向量比较不同术语，判断查询表达与资料术语之间是否存在稳定对齐。

## 5. 已排除原因

基于现有证据，可以排除或暂时排除以下原因：

- **后端没有保存真实资料。** 四份资料完成上传、解析、确认和正式索引，且隔离持久层可观察到真实写入。
- **服务重启导致会话或资料消失。** 本轮持久层 E2E 验收中，历史消息和工具记录可以读取；清理是测试结束时主动执行的行为。
- **源文件缺少标准证据。** 第 `16` 页的解析文本中包含约 `300` 字符的标准摘录。
- **目标页没有进入索引文本。** 解析结果包含 `66` 个页级 Chunk，目标页对应的单 Chunk 已参与向量控制。
- **仅仅是回答阶段没有引用。** `LUSHAN-01` 的标准证据未进入 Top-30，说明在引用生成之前已经发生候选缺失。
- **仅仅是问题附带的格式要求导致失败。** 去掉格式要求后目标页排名仍为 `110`，问题没有消失。

以下事项不能从最初诊断单独推出：

- `2370` 字符页级 Chunk 可能让多个主题混在同一个向量中，但仅凭 Chunk 较长不能认定它就是主因。
- Reranker 无法补救没有进入 dense Top-30 的标准证据；只有先改善候选召回，重排排名才有意义。

## 6. 当前证据支持的根因解释（范围受限）

### 6.1 当前证据支持的解释

当前证据支持以下范围受限的解释：

> 在 P153548 的既有向量表示和已测问题表达下，用户问题中的“世界银行”与第 16 页标准证据的 `IBRD` 表达未稳定对齐，导致该指定页在原问题 dense 检索中排名靠后。这是相对固定标注页的召回问题，不等同于用户可见答案必然错误，也不证明所有 World Bank 资料均有相同问题。

### 6.2 证据

只读向量控制中，使用相同 190 个真实资料向量时，目标页在不同查询表达下的排名如下：

- 原始中文问题：`120`
- 去掉格式要求：`110`
- 短“World Bank”中文问题：`109`
- 英文 `World Bank`：`130`
- 中文 `IBRD` 问题：`1`
- 英文 `IBRD` 问题：`11`

这个对照说明，在当前 P153548 查询和 Embedding 配置下，问题不只是问题长度或输出格式，而是查询术语与文档术语之间的召回对齐问题。该结论限定于本固定集，不足以证明其他“世界银行”语料也会有相同行为。2026-09-23 的后续实验使用精确替换表达复核，目标页原问题 dense 排名为 `120`、补充表达排名为 `8`；旧记录中的补充表达排名 `6` 与本次 `8` 不一致，原因尚未查明，两个数值均保留，不推测差异来源。

### 6.3 页级 Chunk 的证据边界

第 `16` 页被压成单个 `2370` 字符的页级 Chunk，虽然包含约 `300` 字符的标准摘录，但较长 Chunk 可能稀释该摘录在向量表示中的权重。

后续 `800` 字符窗口、`300` 字符重叠的独立对照把 Chunk 数从 `190` 增加到 `857`，但 `LUSHAN-01` 的标准证据排名从 `120` 降到 `147`，原本通过的 `LUSHAN-02` 从 `9` 降到 `177`、`LUSHAN-03` 从 `2` 降到 `59`。因此，这一种统一固定窗口切分不仅没有解决问题，还造成三条有据题全部退化。

该结果只能否定本次固定窗口参数，不能证明所有页内切分都无效；但它足以阻止把“统一细切”作为当前问题的直接修复。

## 7. 解决方案对照实验

### 7.1 直接追加别名：拒绝

在完整原问题末尾追加“世界银行、World Bank、IBRD”后，目标页由第 `120` 提升到第 `46`，仍未进入 Top-30。追加多个近义词会同时保留原始不匹配术语并增加查询噪声，因此不能作为当前正式方案。

### 7.2 统一固定窗口切分：拒绝

`800/300` 固定窗口实验使 Chunk 数增加约 `4.5` 倍，并使三条有据题的 dense 排名全部下降。该方案会增加索引、Embedding 和候选竞争成本，同时破坏现有通过案例，因此本轮拒绝。

### 7.3 只用于检索的术语规范化：当前最有希望

保持原问题其他部分不变，只在检索表达中把“世界银行”替换为 `IBRD`，目标页 dense 排名升到第 `4`，Reranker 排名第 `2`，进入最终 Top-8。为避免把“世界银行”错误等同于单一融资机构，使用包容式 `IBRD IDA` 替换时，dense 排名第 `6`、Reranker 排名第 `3`，同样进入 Top-8。

如果同时保留 `World Bank` 并追加 `IBRD IDA`，目标页只到第 `43`，仍未进入 Top-30。这说明有效变量不是“词越多越好”，而是检索表达需要移除当前无法对齐的上位术语，换成原文常用的融资机构术语。

控制变量的单词替换结果为：原问题中的“世界银行”只替换为 `IBRD` 时 dense 第 `4`、Reranker 第 `2`；替换为 `IBRD IDA` 时 dense 第 `6`、Reranker 第 `3`；替换为 `World Bank IBRD IDA` 时 dense 第 `43`。在正式计算排名时，目标证据使用项目正式的空白归一化范围覆盖函数判断，而不是直接比较完整字符串。

建议的正式候选方案不是修改用户原问题，而是新增**检索专用、上下文门控的术语规范化**：仅在问题同时出现“世界银行/World Bank”和“贷款/融资”意图时，把检索侧表达规范为 `IBRD IDA`；D5/D6 判定、回答生成、历史消息和公开响应仍使用原始问题。

风险：

- 世界银行集团还包含 IFC、MIGA、ICSID；规则只能限定在贷款或主权融资语境，不能建立全局等价关系。
- 单个 P153548 案例不足以证明泛化，必须补充至少一个 IDA 资料正例以及不应改写的 World Bank 报告类反例。
- 规范化只能改变检索内部表达，不能写回用户消息、Checkpoint、工具审计或回答 Prompt，以免改变产品语义。
- FR-039 与 FR-042 共用候选入口，正式实验必须同时回归两条路径及无据拒答。

### 7.4 混合或词法兜底检索：暂不进入

将 `IBRD` 等明确术语作为词法或元数据过滤/补召回条件，与 dense 结果进行受控合并。

风险：

- 这会扩大正式检索架构范围，可能引入新的排序、去重和引用一致性问题。
- 词法兜底可能提升召回但降低相关性，不能只看是否命中目标页。
- 当前项目尚未授权把混合检索作为正式能力，必须先完成架构和需求评审。

当前不需要扩大到 BM25 或混合检索。只读实验已把最小候选变量收敛到检索专用术语规范化；正式实现仍需独立方案确认。

### 7.5 诊断口径一致性

本报告采用与正式验收一致的 `item_contains_expected_evidence` 判定语义，包括空白归一化和定位范围覆盖。与该契约不一致的子串探测结果不用于排名或质量结论，避免把度量口径差异解释为产品行为。

### 7.6 双路候选并集与证据等价性复核（2026-09-23）

本节记录后续只读对照结果，补充而不覆盖前述实验。实验没有修改正式代码、正式配置或冻结评估集；融合排序仅作离线对照，未接入正式检索路径，也没有据此授权实现。

#### 方法与数据边界

- 使用已核对 SHA256 清单的四份 P153548 PDF，共 `190` 个页级解析片段；对每个问题分别执行原问题和补充检索表达的 dense Top-30，按 `chunk_id` 合并，不截断并集。
- Q1 原问题为“芦山项目的世界银行贷款金额是多少？请保留原文货币格式。”补充表达只将“世界银行”精确替换为 `IBRD IDA`；没有把该表达追加到原问题末尾。
- 两路候选并集为 `44` 个片段，交集 `16` 个。全部候选的 dense rank/cosine 和两种重排表达的 rank/score 已保存于本地忽略文件 `tests/pytest_docs/public_projects/lushan_earthquake_p153548/acceptance/dual-rerank-scores-20260923.json`，供后续离线融合评估；该文件不属于 Git 交付物。
- 这次内存向量诊断以 `parse_archive_document` 的页级原文片段重建向量，未加入已确认的 `evidence_values` 上下文；它不是正式 Chroma 向量的逐字复刻，也不是持久层 E2E。不得将其结果表述成正式索引链路验证。
- 第 16 页目标片段在原始查询 dense rank 为 `120`、补充查询 dense rank 为 `8`。补充查询进入 Top-30，但这次 rank `8` 与先前报告中的 rank `6` 不一致；差异原因未确认，不合并成单一确定值。

| --- | ---: | --- |

金额证据不只存在于第 16 页：2016 appraisal 第 1、16 页，2022 restructuring 第 4 页，以及 2024 completion report 和 completion review 的第 1 页均支持原始/批准金额。2024 completion report 第 56 页另区分原批准 IBRD 贷款总额 `US$300.00 million` 与实际提款约 `US$296.83 million`。因此，“存在其他有效金额证据”“命中冻结标注页”和“命中指定页”是不同判定，不能相互替代。

## 10. 已确认的实现与评测工具缺陷修复记录（2026-09-26）

本节只记录经代码链路或确定性回归确认、且需要修改项目实现的缺陷。第 1–9 节保留检索证据、实验方法和方案比较，不作为逐条操作错误日志。命令参数、路径、Shell、环境、临时诊断脚本、测试替身错误及预期 RED 均不单独记录；同一根因引起的多次失败合并为一条。以下问题位于评测/验收工具链；本轮没有证据表明正式 app/ 业务代码存在缺陷。

### 10.1 贷款证据页与背景页的评测语义混淆

- **错误现象：** Belarus 贷款正例可能因 Top-8 中出现第 7 页项目背景而被判为有答案支持；另一处预检又要求所有预期页都进入 Top-8，导致第 7 页背景缺失时错误判负。
- **排查链路：** 对照评测计划中的“答案支持页”口径、案例页角色标注及原 PDF；确认第 7 页是项目背景，第 16 页才包含 IBRD 融资金额。
- **根因：** 评测数据和准备器没有一致地区分背景页与回答所需的主要支持页，把“任一标记支持”与“所有预期页必达”当成同一判定。
- **修复方案与结果：** 贷款金额正例明确要求第 16 页作为主要支持页；第 7 页只作背景；预检按主要支持页判定，不要求所有背景/参考页均进入 Top-8。
- **验证：** 对应准备器回归覆盖第 7 页不能替代第 16 页，以及只要求主要支持页的情形。该轮预检复核的 15 条有据样本均覆盖其主要支持页；这只是候选覆盖观察，不代表回答引用语义通过。

### 10.2 部分合格评测组被错误阻断

- **错误现象：** 某些条件组因缺少可验证支持证据而跳过时，其他合格组也不能继续评测。
- **排查链路：** 对照生成器与编排器：生成器允许跳过不合格组，编排器却要求最终条目数必须恰好为 21。
- **根因：** 将 21 条预算上限误用为最低样本数，导致合法的部分数据集被拒绝。
- **修复方案与结果：** 编排器现在允许 0 至 21 条并报告跳过数；零条时安全停止，不为凑足预算调用模型。
- **验证：** 部分合格组和零样本场景均有确定性回归覆盖；冻结评测集和模型预算规则未改变。

### 10.3 隔离资源清理没有以已确认所有权为前提

- **错误现象：** 预检发现同名隔离目标已存在时，原流程仍尝试核验清理并可能把既有目标误报为本轮清理失败；创建请求尚未成功返回时，流程也可能提前把同名资源记为本轮所有。
- **排查链路：** 逐项追踪空目标预检、各资源创建返回值、所有权标记和失败清理分支。
- **根因：** 清理资格曾由目标名称或“发起过创建”推断，而不是由成功创建后取得的明确所有权决定。
- **修复方案与结果：** 预检冲突即停止，不执行创建、清理或残留核验；资源仅在创建成功返回后标记为本轮所有。创建结果不确定时不删除无法确认归属的资源。
- **验证：** 回归覆盖预存目标冲突及 PostgreSQL Schema、Chroma Database、运行目录创建失败分支；确认冲突路径不会触发清理，创建失败路径不会删除未确认归属的目标。没有证据表明此前实际删除过外部资源。

### 10.4 Engine 释放顺序可能重新打开数据库连接

- **错误现象：** 隔离验收清理中，释放 Engine 后又执行残留核验，核验可能重新创建连接池，使随后删除 Schema 时仍有连接占用。
- **排查链路：** 沿清理调用顺序检查 dispose、PostgreSQL 残留核验及 DROP SCHEMA 的先后关系。
- **根因：** 共用 Engine 在最终核验完成前被释放，之后又被核验逻辑复用。
- **修复方案与结果：** 调整为停止 API、清理检索资源并完成核验、释放 Engine，最后才允许删除 Schema；清理或释放失败时采取保护性停止，不继续执行有风险的删除。
- **验证：** 顺序断言和失败分支回归确认先后次序、Engine 释放尝试及失败时禁止 DROP。

### 10.5 准备器的安全失败诊断在多层传播中丢失或互相覆盖

- **错误现象：** 隔离准备失败时，外层摘要曾只显示通用失败阶段；主体失败与清理失败并发时，阶段或清理信息可能被覆盖；残留探针失败时也可能没有完整的四层布尔结果。
- **排查链路：** 从空目标预检、内层检索验收、残留核验、异常包装直到 CLI 摘要输出逐层检查；确认阶段保护、异常合并优先级和白名单字段透传存在缺口。历史运行的底层数据库或 Chroma 失败原因无法仅凭旧摘要还原，本记录不据此推定其根因。
- **根因：** 安全诊断字段缺少统一的允许值与传播契约，也没有明确区分主体失败阶段和最终清理失败信息的优先级。
- **修复方案与结果：** 为关键阶段和残留探针增加固定白名单码；只透传受控清理步骤及严格布尔残留值；主体有效阶段优先于清理阶段、再优先于外层回退阶段；清理诊断由最终清理结果提供；CLI 输出仅保留白名单字段，不输出异常正文或任意类名。
- **验证：** 回归覆盖 Chroma 比较异常、主体与清理复合失败、阶段优先级、四层残留信息及 CLI 白名单透传。相关脚本测试和本轮后端全量测试通过，最终验证汇总见第 11 节。该修复提升的是诊断可定位性，不等于确认了此前每次隔离运行失败的底层原因。

### 10.6 隔离运行时仍使用持久化验收模块的旧配置

- **错误现象：** 隔离运行的 PostgreSQL 空目标计数被数据库安全规则拒绝，准备和清理摘要均指向计数阶段；只读核验确认隔离目标为空。
- **排查链路：** 沿函数导入和模块全局变量查找路径检查：检索验收模块导入了持久化验收模块的计数函数；隔离配置只更新了检索模块的 Engine/Settings。
- **根因：** 被导入的函数仍从其定义模块的全局命名空间读取旧 Engine/Settings，未使用隔离运行配置。
- **修复方案与结果：** 配置隔离运行时同步更新持久化验收模块的 Engine/Settings，并移除重复检索分支；测试清理时恢复模块状态，避免污染同进程其他测试。
- **验证：** 旧配置与隔离配置不相同的回归确认计数使用隔离配置；修复后目标测试和后端全量测试通过。事后只读核验确认本轮专属持久资源不存在。

### 10.7 Pixie 数据集缺少顶层 Runnable

- **错误现象：** 评测数据条目虽然包含 evaluator，仍不能通过 Pixie Dataset 的运行结构校验。
- **排查链路：** 对照当前安装版本的 Dataset schema 与数据集构造器，确认缺少必需的顶层 runnable 字段。
- **根因：** 数据集适配器只生成 name 和 entries，没有实现 Pixie 要求的 Runnable 入口。
- **修复方案与结果：** 增加项目问题 Runnable，并由数据集构造器声明该入口。
- **验证：** 构造器回归和本地 Dataset schema 校验通过；该结构验证不调用模型。

### 10.8 Pixie 注入的检索响应不符合生产 Schema

- **错误现象：** Step 5 在进入回答模型前即因输入校验失败，候选数据不能驱动真实回答评测。
- **排查链路：** 逐字段对照生产 ArchiveRetrievalResponse 与注入数据；确认候选项缺少 ID/分数等必需字段、位置类型不匹配，响应级 requested_top_k 和 returned_count 也缺失。
- **根因：** 离线数据适配器使用了简化的自定义候选形状，而生产入口严格校验正式响应契约。
- **修复方案与结果：** 注入生产契约要求的候选字段、合法位置类型及响应计数字段；保留输入与正式检索响应的一致性。
- **验证：** 21/21 条输入通过生产 Schema 校验；按调用顺序，原 Step 5 的模型调用为 0/21。适配修复后的后续真实模型调用数量和结果见第 11 节。

### 10.9 evaluator 使用了与生产不一致的 PDF 位置类型

- **错误现象：** 离线统计把冻结页及扩展页全部报为未命中，但候选与 Trace 中存在相应页位置。
- **排查链路：** 对照生产 Archive 数据模型、解析结果、候选字段及 Trace，确认生产枚举值为 PDF_PAGE，而 evaluator 与原测试夹具使用 PDF_PAGE_RANGE。
- **根因：** evaluator 的页码匹配契约与生产 Schema 不一致，测试仅对错误夹具自洽，未用生产枚举值验证。
- **修复方案与结果：** evaluator 按生产 PDF_PAGE 位置比较，并增加错误文件与越界页拒绝校验。
- **验证：** 使用生产位置枚举的 evaluator/Runnable 定向测试通过；离线修正评分为 12/21，冻结页命中 3/6，扩展页位置诊断 9/9。扩展页语义支持仍未完成评估。
