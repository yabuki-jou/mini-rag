## 2. 结论摘要

四个项目嵌套端点、空对象创建请求、五要素会话查找、轮次内单调 `S/D` 编号、`citations=[]` 的历史投影，这几项选择方向都对，而且能把 DEC-019 延期的东西（轮次表、历史引用表、删除状态机、动态预算）挡在契约之外。第 13 节没有偷偷把延期项带回来。

本轮我逐条核了四类容易踩空的前提，全部成立：

- `ArchiveAnswerStatus`（`app/schemas/archive_question.py` L10～L14）确实只有 `ANSWERED / REFUSED_NO_EVIDENCE`，§13.3 与 §13.8 的复用声明成立，`CATALOG` 未泄漏成公开枚举。
- `ArchiveRetrievalItemRead`（`app/schemas/archive_retrieval.py` L20～L31）确实**必含** `chunk_id / document_id / score / reranker_score`，§13.8 声明"不复用它"是必要且正确的选择，AC-03 改后的措辞与之一致。
- `AgentToolCallLog` 上 `uq_agent_tool_logs_session_call`（`app/models/agent.py` L71～L77）真实存在，§13.5「每个 `(agent_session_id, tool_call_id)` 最多一条日志」不是纸面约定。
- `AgentToolCallLogRead.tool_name` 是 `str` 而非枚举（`app/schemas/agent.py` L115），新增两个工具名不会被既有约束挡住。

§4.4 的 FR-039 引用示例修正已核验：示例现在是 64 位十六进制 `chunk_id` + `document_id` + `filename` + 位置 + `excerpt` + `score` + `reranker_score`，与 `ArchiveRetrievalItemRead` 逐字段一致，`citation_id` 已从示例中移除（全文检索确认 `citation_id` 现只出现在第 13 节）。

AC-01～AC-19 共 19 条在 §13.9 全部有落点，无遗漏项。

但契约里有四处"看起来写完了、实现时会立刻分叉"的地方，其中第一处会直接违反 AC-16。

## 3. 必须修改

### API-1 公共判定层的失败映射未定义，FR-042 会返回 FR-039 的错误码（违反 AC-16）

三层要求叠在一起时必然冲突：

| 层 | 要求 | 位置 |
|---|---|---|
| FR-039 冻结契约 | 判定层"任何校验失败均统一映射为稳定的 `503 ARCHIVE_ANSWER_UNAVAILABLE`" | `P14-D5-…方案.md` L113、L130、L131 |
| 现有实现 | 模型不可用或 JSON 不合法一律 `raise AppError(503, "ARCHIVE_ANSWER_UNAVAILABLE", …)` | `app/services/archive/questions.py` L245～L261 |
| FR-042 架构 | `judge_archive_answer` 是**唯一实现**，FR-039 与 FR-042 共用 | 技术架构 L706～L710 |
| FR-042 契约 | 模型、工具、Checkpoint、PostgreSQL 最终失败返回 `503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE` | 接口设计 §13.6 L988～L991、AC-16 L901～L903 |

如果实现照技术架构 L706～L710 抽出公共函数、并保留现有 `AppError(503, "ARCHIVE_ANSWER_UNAVAILABLE")` 语义，FR-042 的证据回答路径在模型失败时会泄出 FR-039 的错误码，AC-16 与 §10 错误码表（L735）同时不成立；反之若在公共函数里改成 `ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`，FR-039 的既有契约（`docs/design/接口设计.md` L297、L632、L731 与 P14-D5 L113）会被破坏。

**建议补一句**（写入 §13.6 或 §13.8）：

```
judge_archive_answer 只返回判定结果或抛出与调用方无关的中性错误；
answer_archive_question 将其映射为 ARCHIVE_ANSWER_UNAVAILABLE（FR-039 契约不变），
档案 Graph 将其映射为 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE。
FR-042 的任何响应都不得出现 ARCHIVE_ANSWER_UNAVAILABLE。
```

### API-2 两次证据调用时「传给判定层的候选集合」与 `S` 编号的对应基准未定义

判定层的编号基准是**传入列表的位置**，这一点在代码里是硬事实：

- `_build_archive_prompt`（`questions.py` L44～L53）用 `enumerate(candidates, start=1)` 生成 `[S{index}]`；
- `_parse_model_decision(content, candidate_count)`（L92～L148）按 `candidate_count = len(candidates)` 校验编号范围（L145）；
- `answer_archive_question` 用 `retrieval.items[number - 1]` 反查（L274～L278）。

而契约只说"若同一轮发生两次证据调用，`S` 编号按该轮结果出现顺序单调增加"（§13.6 L977～L978），技术架构只说"直接**把本轮证据工具对应的**受控候选映射传给同一函数"（L708），没有说两次调用取**并集**还是**最后一次**，也没说去重时如何重编。

两种读法都会产生静默错误：若 Graph 只把第二次调用的 8 条传给判定层，而服务端按 16 条并集反查 `S` 编号，`S9..S16` 的引用会整体错位到别的 Chunk；若传并集但列表顺序与 `S` 编号不一致（例如按分数重排），同样错位。这类错误不会报错，只会返回**看起来正常但指向错误原文的引用**。

**建议补一句**：

```
传给 judge_archive_answer 的候选列表 = 本轮全部证据调用结果，按 S 编号升序拼接；
必要时去重并同步重编 S 编号。citation_number 与 citation_id 都以下发前该列表的
1-based 位置为唯一基准，服务端不重新排序。
```

### API-3 模型未调用工具时「是否在陈述档案原文事实」没有判别机制，AC-06 后半句不可判定

需求 L838～L839 与 AC-06 都要求：模型没有调用本轮证据工具却试图陈述档案原文事实时，服务端必须改为无依据拒答。技术架构 L670～L671 也用"统一走拒答投影"承接了这条。

但 §13.3 的分支枚举给出了一条逃逸路径：

- 走 D5/D6 的只有"证据事实回答"，前提是本轮存在证据工具结果；
- "目录回答或不涉及档案事实的普通回答：`ANSWERED`，`answer` 非空，`citations=[]`"（§13.3 L914～L915）；
- 模型一次决策允许产生**零个** Tool Call（技术架构 L657、需求 L804）。

于是"零工具调用 + 模型直接陈述档案事实"这条路径，按现有文字既不属于目录回答，也不属于证据回答，落进"普通回答"分支并返回 `200 ANSWERED`，恰恰是 AC-06 要拒绝的情形。判别"这句话是否涉及档案原文事实"目前没有任何服务端机制，AC-06 的后半句因此无法写成测试。

**建议二选一并写进 §13.3**：

```
方案一（更省）：本轮未产生证据工具结果时，不区分文本内容，一律投影为 REFUSED_NO_EVIDENCE；
方案二：保留普通回答分支，但要求该分支仅在模型零工具调用且回答被判定为不涉及档案事实时成立，
        并明确判定由哪一层、用什么输入完成。
```

方案一更符合"安全边界不降级"的既定口径，代价是寒暄类问题也会被拒答。

### API-4 当前回答正文与写入 Checkpoint 的助手消息是否同一份文本未定义

§13.4 的历史示例把助手 content 写成 `"施工方案的编制单位为示例建设公司。[S1]"`（L930），即默认「历史正文 = 用户当时看到的回答」。AC-01（第二轮可读取第一轮用户可见上下文）与 AC-07（历史与模型输入同一投影）也依赖这个等式。

但证据路径的可见回答来自 `judge_archive_answer`（技术架构 L669～L671），而工具循环里模型自己也产出了一条最终 AIMessage。没有任何一处写明：

- 写回 Checkpoint 的最终 AIMessage 是**判定层文本**还是**工具循环文本**；
- 被投影替换或改写掉的模型原始文本是否进入 Checkpoint。

如果写回的是工具循环的自由文本，下一轮模型输入与历史接口就会带着一段**未经过 D5/D6 判定**的"助手断言"，既与 AC-01/AC-07 的意图不符，也正是 BR-032 想防的情形。

**建议补一句**（写入 §13.4）：

```
最终返回的 answer 即写入 Checkpoint 的最终 AIMessage 正文；
被拒答投影替换掉的模型原始文本不进入 Checkpoint，也不进入下一轮模型输入。
```

### 10.2 最终复核当时发现的契约缺口（已在 §11 闭环）

### 12.2 遗留点（不违反任何 AC，建议在 Implementation Plan 冻结前定调）

**W-1｜目录正文模板没有分页信息，且计数措辞可被读成总数**

模板首行为「当前目录结果共 {当前页条目数} 份：」，`page/page_size` 是模型可控参数
（§13.6 L1004～L1006，`page_size ≤ 20`），底层目录服务同时返回 `page`、`page_size` 与 `total`
（`app/services/archive/catalog.py` L102～L104）。因此模型取 `page=2` 时，正文仍只写本页条目数，
用户既不知道这是第几页，也不知道项目里还有多少份正式档案；编号还会从 `1` 重新开始。

AC-02 只约束返回内容的范围（「只包含 `CONFIRMED` 且未被可见性阻断的档案摘要」），不约束完整性，
所以这不构成本次确认的阻塞项。但模板已是冻结的正文契约，三种收口方式都需要一句话定调：

1. 模板补全分页信息：首行改为「第 {page} 页，本页 {当前页条目数} 份，共 {total} 份」；
2. 只改措辞避免全域断言（如「本页共 {当前页条目数} 份」），保留模型翻页能力；
3. 收紧行为：目录工具固定 `page=1` 且只允许模型控制 `page_size`，模板同步声明为「最多前 N 份」。

**W-2｜`request_id` 只以示例形式出现**

`ArchiveAgentResponse` 的示例含 `request_id`（§13.3 L902），与现有 `AgentResponse.request_id`
（`app/schemas/agent.py` L80）一致，但 §13.8 的 DTO 清单只列类型名不列字段，而 §13.2/§13.4 的示例
又不含该字段。建议在 §13.8 为 `ArchiveAgentResponse` 补一份字段清单（或注明「字段以 §13.3 示例为准」），
避免实现时对字段集合产生分歧。
