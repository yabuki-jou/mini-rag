## 2. 结论摘要

最小方案本身选得对：`agent_sessions` 只加两列、用 CHECK 隔离会话类型、用复合外键把「项目—知识库」绑定交给数据库、删除通过级联而不是新增状态机。它没有把 DEC-019 延期的东西偷偷带回来，也没有为了表格好看而引入冗余列。

核验中还发现一处**这套设计最容易踩空但已经满足的前提**：复合外键 `(project_id, kb_id) → projects(id, kb_id)` 要求 `projects` 上存在 `UNIQUE (id, kb_id)`，该约束在真实迁移 `0005_archive_v1_schema.py` L81 已存在（`uq_projects_id_kb_id`），不是只在文档里写着。这一点成立，方案才成立。

但草案把三件事当成"细节"跳过了，它们在实现时都会立刻变成红灯：

- `down_revision` 写了一个**不存在的 revision 标识**；
- 要替换的工具日志外键是**匿名创建**的，草案没说 drop 谁；
- 新增两列会**让一个既有测试必然失败**，而草案只写了"补齐注释"。

## 3. 必须修正

### DB-1 `down_revision` 指向不存在的 revision（确定的错误）

- **位置**：`docs/design/数据库设计.md` L595～L597；`docs/stage/handoff.md` L692。
- **现状文字**：「`down_revision` 指向 `0010_account_password_authentication`」。
- **事实**：`0010` 的 **revision id 是 `0010_account_auth`**，不是文件名主干。
  - `migrations/versions/0010_account_password_authentication.py` L10：`revision: str = "0010_account_auth"`。
  - 同文件 L9 的注释明确写：「Alembic 默认把 revision 写入 VARCHAR(32)；标识必须控制在 32 字符以内。」
  - 仓库其他位置一致使用 `0010_account_auth`：`docs/implementation/智慧档案V1实施计划.md` L198、`docs/review/验收报告.md` L112、`docs/archive/stage/handoff-2026-09-17.md` L116。
  - `tests/test_migration_service.py` L77 断言升级后 `revision == "0010_account_auth"`。
- **后果**：照现文书写入 `down_revision` 时，`alembic upgrade` 会直接以
  `Can't locate revision identified by '0010_account_password_authentication'` 失败。
  `docs/design/数据库设计.md` L16、L593 与 handoff L699 在散文里用文件名指代迁移，容易被抄进代码，建议一并规范化。


### DB-2 工具日志外键的 drop 目标名未指定

- **位置**：`docs/design/数据库设计.md` §11 第 9 步（L615～L617）。
- **事实**：现有外键在 `migrations/versions/0003_agent_api.py` L57 是**匿名**创建的：
  `sa.ForeignKeyConstraint(["agent_session_id"], ["agent_sessions.id"])`，没有 `name=`。
  PostgreSQL 会为它生成 `agent_tool_call_logs_agent_session_id_fkey`。
- **后果**：0011 若按一个假定的名字执行 `op.drop_constraint(...)`，迁移在第一步就失败；
  SQLite 的 batch 重建同样需要明确引用原约束。
- **建议**：在第 9 步补一句「先按 PostgreSQL 默认名 `agent_tool_call_logs_agent_session_id_fkey`
  或运行时 introspection 结果 drop 旧外键，再以具名约束 `fk_agent_tool_logs_session_cascade`
  重建；不得假定自定义名」。

### DB-3 新增两列会让既有注释契约测试必然失败，且该测试文件本身必须改

- **位置**：`tests/models/test_schema_comment_contract.py` L24～L50，对应 `docs/design/数据库设计.md` §11 第 10 步（L618）。
- **事实**：该测试断言「合并后的注释映射键集合」与 SQLModel 元数据**完全相等**：

```python
assert set(table_comments) == set(business_tables)
for table_name, table in business_tables.items():
    assert set(column_comments[table_name]) == {column.name for column in table.columns}
```

  而 L32～L38 只把 `0006`、`0008`、`0010` 三个迁移的注释映射合并进来。
  `agent_sessions` 的既有 6 列注释来自 `0008_legacy_business_comments.py` L67～L74。
- **后果**：只要 `AgentSession` 增加 `agent_type` 与 `project_id`，该测试立即变红；
  仅"在 0011 里写注释"不够——**测试文件必须同时改为把 0011 并入合并**。
- **建议**：§11 第 10 步改为显式两步：
  1. `0011.COLUMN_COMMENTS["agent_sessions"]` 提供 `agent_type`、`project_id` 两列说明；
  2. `tests/models/test_schema_comment_contract.py` 增加加载 `0011_archive_agent_scope.py`
     并把其结果并入 `column_comments`。
  这是本期唯一一处"必须修改既有测试"的数据库改动，应写进 Implementation Plan。

## 4. 建议

| 编号 | 位置 | 问题 | 建议 |
|---|---|---|---|
| DB-4 | §12 L638～L646；`tests/test_migration_service.py` | SQLite 默认不启用外键，而该文件未设 `PRAGMA foreign_keys=ON`（其他 SQLite 测试如 `tests/routers/test_projects.py` L29～L31 已有显式启用的先例）。因此"`(project_id, kb_id)` 不匹配时插入失败""级联与显式删除得到相同可观察结果"这两条在该链路上**不会成立**（CHECK 约束在 SQLite 是强制的，不受影响） | 把这两条明确挂到启用 PRAGMA 的 SQLite 测试或标注为 PostgreSQL 集成门；不要让"SQLite 也过了"掩盖未验证的级联 |
| DB-5 | §6.11 L442～L444 | 复合外键的 `MATCH SIMPLE` 是承载「制度会话 `project_id` 为空」的关键语义，草案只在说明文字里解释，未写进约束本身。若将来有人改成 `MATCH FULL`，`project_id IS NULL + kb_id NOT NULL` 的制度行会被整体拒绝，直接摧毁全部存量会话 | 在约束写法上显式写出 `MATCH SIMPLE`，使其成为结构而不是注释 |
| DB-6 | §11 L595 | `0011_archive_agent_session_scope` 恰为 **32 字符**，正好等于 Alembic 默认 `version_num` VARCHAR(32) 上限（`tests/test_migration_service.py` L81～L85 有 `<= 32` 断言）。能通过但零余量，且与仓库既有短 id 风格（`0010_account_auth` 17、`0007_project_version_comment` 27）不一致 | 建议缩短为 `0011_archive_agent_scope`（24 字符） |
| DB-7 | §6.11 L459～L462 对 技术架构 §10.7.5 L708～L722 | 草案写「锁定 Project…但在外部 Checkpoint 清理前不提交项目删除」，即 PG 事务与 Project 行锁**跨越外部文件删除**。架构的流程文字可读为同一事务，但没有写明锁持有窗口与代价 | 在任一处显式写明「Project 行锁持有至 PostgreSQL 提交，期间同项目的会话创建与上传阻塞，属本地单实例 MVP 接受的代价」，避免实现者把锁范围又放大或缩小 |

## 5. 核验成立（可作确认依据）

| 项 | 证据 |
|---|---|
| 复合外键的引用目标合法 | `0005_archive_v1_schema.py` L81 已建 `uq_projects_id_kb_id`；不需要为 FR-042 补唯一约束 |
| `MATCH SIMPLE` 下 NULL `project_id` 不受约束 | PostgreSQL 默认语义；制度会话因此既不被校验也不被级联 |
| 级联删除有仓库先例 | `0005` L107 `archive_documents.document_id` 已用 `ondelete="CASCADE"` |
| 「绝不清理制度 Agent 线程」由结构保证 | 制度会话 `project_id IS NULL`，不进入 `projects` 的级联路径；比服务层约定更强（架构 L721～L722） |
| VARCHAR + CHECK 而非新 PG Enum 合规 | §5 L96～L97 明确允许「PostgreSQL Enum 或等价的数据库 CHECK 约束」；`app/models/project.py` L33～L34 等已有 `CheckConstraint` 先例 |
| 迁移顺序可执行 | 先加 `agent_type NOT NULL DEFAULT 'POLICY'`，存量行回填为 `POLICY`；此时 `project_id` 尚未加入（第 8 步才加），加 CHECK 时全表满足 `POLICY + NULL` |
| 新增列范围与 DEC-019 一致 | 只有 `agent_type` 与可空 `project_id`；无 AgentTurn、无历史引用表、无 `DELETING`、无第二份 Checkpoint |
| 工具日志不加冗余列 | `project_id`/`agent_type` 均不加，读取时经已验证的 AgentSession 限定，与最小方案一致 |
| 存量制度接口不受影响 | §12 L638～L639 要求 `0011` 后存量会话全为 `POLICY + project_id NULL`，与架构 L296～L297 的入口过滤一致 |

## 6. 评审结论

DB-1 修正是**必须的**，它不是措辞问题而是会让迁移直接失败的错误；DB-2 决定迁移能否写成；
DB-3 决定既有测试是否会在第一步就红。三项都能用几句话或几行改动收敛，不改变方案本身。

修正这 3 项后，**FR-042 数据库设计通过，可以进入 API 契约设计**。DB-4～DB-7 可与 API 设计并行，
但 DB-4 必须在 Implementation Plan 的测试分层里被显式安排，否则"删除级联"会以未验证的状态
进入实现。

本轮为纯文档核验：未修改 SQLModel，未创建 `0011`，未运行迁移、数据库、Chroma、DeepSeek 或
Checkpoint 验证。
