## 4. 逻辑完整性评审

### ✅ 已确认决策(2026-08-06):重新生成建议接口,采用方案 B

#### 决策内容(用户确认)

> 采用"重新生成建议"接口:它只允许草稿中**尚无人工填写/确认的字段**时执行;一旦已有人工修改则返回 `409`,由用户保留手工结果或自行清空后再生成。既避免覆盖人工输入,也补上"纯手工归档可切回 AI 建议"的路径。

#### 落地契约(需同步修订 `接口设计.md`)

1. **接口形态**:复用 `POST /projects/{project_id}/documents/{document_id}/suggestions`(不新增路由),允许初始状态扩展为 `PARSED`、`SUGGESTION_FAILED`、`PENDING_CONFIRMATION`;其中从 `PENDING_CONFIRMATION` 发起即"重新生成建议"。`suggestions/retry` 保持仅 `SUGGESTION_FAILED`。
2. **"人工内容"判定(允许/拒绝条件)**:草稿中七个字段的 `review_status` 全部为 `PENDING_CHECK` **且**不存在 `source = MANUAL` 的值或证据时允许重新生成(空白人工草稿、纯 AI 草稿均满足);任一字段已人工确认(`VALUE_CONFIRMED`/`EMPTY_ACCEPTED`)或含人工值(`source = MANUAL`)时返回 `409 SUGGESTION_WOULD_OVERWRITE_MANUAL_DRAFT`,草稿与状态保持不变。
3. **成功/失败语义**:重新生成成功后,以新 AI 草稿整体替换旧草稿,状态保持 `PENDING_CONFIRMATION`;失败(连接失败/超时/模型不可用)时状态保持 `PENDING_CONFIRMATION`,保留现有草稿,返回 `503 ARCHIVE_SUGGESTION_UNAVAILABLE`,不破坏草稿。
4. **状态机补充**(架构 §11.1):增加边 `PENDING_CONFIRMATION --> PENDING_CONFIRMATION: regenerate suggestion (no manual content)`;`PARSED`/`SUGGESTION_FAILED` 既有边不变。
5. **审计**:建议新增审计类型 `SUGGESTION_REGENERATED`(区别于失败重试 `SUGGESTION_RETRIED`),写入 §9 审计枚举。
6. **AC-FR-034-03 测试用例(现可构造)**:
   - 用例 1:Given 空白人工草稿(七字段 `PENDING_CHECK`),When 调用 `suggestions`,Then 返回 AI 草稿,状态保持 `PENDING_CONFIRMATION`;
   - 用例 2:Given 草稿任一字段已人工确认或含人工值,When 调用 `suggestions`,Then `409 SUGGESTION_WOULD_OVERWRITE_MANUAL_DRAFT`,草稿与状态不变。
7. **可粘贴修订文本**:见交付文件 `接口设计补丁.md`,按章节覆盖 `接口设计.md` 对应小节即可。

### 🟡 建议优化

#### 建议 1:`CONFIRMED` 状态下重复调用 `confirm` 的响应语义需明确

- **涉及位置**:§3.2("同一内容的重复确认返回当前确认结果")与 §10(`CONFIRM_NOT_ALLOWED`)
- **说明**:§3.2 声明重复确认幂等返回,但接口前置条件描述与 `CONFIRM_NOT_ALLOWED` 的错误定义未说明 `CONFIRMED` 状态下的行为。实现者可能实现为 409,与 §3.2 冲突。
- **优化方案**:明确"文档已 `CONFIRMED` 且 `expected_version` 匹配时,`confirm` 幂等返回当前档案(`200`),不重新生成 Chunk、不产生新审计;仅版本不匹配时返回 `409 VERSION_CONFLICT`"。在 §7 确认小节补一句。

#### 建议 2:字段 `PUT` 与 `archive_documents.version` 的递增规则需明确

- **涉及位置**:§7 `PUT .../fields/{field_name}`;数据库设计 §6.5(字段行无独立 version)
- **说明**:数据库层乐观锁版本只存在于 `archive_documents.version`,但 API 文档未说明"每次字段更新是否使聚合版本 +1"。若不明确,连续编辑多个字段时客户端无法预判 `expected_version` 的取值,且"已确认档案改字段 → 转 PENDING_RECONFIRMATION"后版本跳变规则未知。
- **优化方案**:写明"每次成功写入任一字段草稿/证据,`archive_documents.version` 原子 +1,响应 `ProcessDocument.version` 返回新值;客户端下次提交必须使用最新版本"。

#### 建议 3:列表排序需固定稳定 tie-breaker

- **涉及位置**:§5(项目列表 `updated_at DESC`)、§8(目录 `confirmed_at DESC`)、§9(审计 `created_at DESC`)
- **说明**:NFR-019 要求"默认顺序必须稳定"。仅按 `updated_at`/`confirmed_at`/`created_at` 排序,时间戳相同(同事务批量操作)时顺序不确定;数据库审计索引已用 `id DESC` 兜底,但项目列表索引 `(owner_id, updated_at DESC)` 未带兜底列。
- **优化方案**:所有列表排序统一追加 `id DESC` 作为 tie-breaker,并在 API 文档排序说明中写明。

#### 建议 4:`Idempotency-Key` 的实现契约需在实施计划中定义

- **涉及位置**:§3.2 [ASK USER] 第 2 项
- **说明**:文档已声明"相同项目、路径、方法与键重试时返回第一次的结果",但未定义:幂等键的存储位置(数据库表?内存缓存?)、保留期限、与 `expected_version` 的交互(重试时版本已变,应返回首次结果而非版本冲突——文档语义已暗示,但需显式写明)、以及首次请求进行中收到相同键的并发处理。
- **优化方案**:若确认启用,在实施计划中单列"幂等键存储与过期策略"任务;若确认不启用,删除该节避免契约歧义。

#### 建议 5:问答内部检索参数需固定,保证验收可复现

- **涉及位置**:§8 `archive-questions`
- **说明**:`archive-retrieval` 的 `top_k` 已定义,但 `archive-questions` 内部检索的 `top_k`、相似度阈值等未定义。需求 12.3 要求"12 个问题引用正确率 100%",若不固定内部检索参数,同一问题在不同实现/参数下结果不可复现,验收无法判定。
- **优化方案**:在实施计划中固定问答内部检索 `top_k`(建议与 `archive-retrieval` 默认一致)与证据截断策略,并写入验收说明。

#### 建议 6:取消确认对 `checklist_links` 的处理需在 API 文档补一句

- **涉及位置**:§7 `cancel-confirmation`;数据库设计 §6.8
- **说明**:取消确认转 `PENDING_RECONFIRMATION` 后,档案不再满足清单(清单满足 = 档案 CONFIRMED ∧ 关联 CONFIRMED),但 `checklist_links.status` 保持不变;重新确认后自动恢复满足。该行为合理,但 API 文档未说明,实现者可能误解为"取消确认应同时失效关联"。
- **优化方案**:在 `cancel-confirmation` 小节补充:"取消确认不改变 `checklist_links.status`,清单满足性由档案状态与关联状态共同派生;重新确认后清单状态自动恢复。"

#### 建议 7:补充正式档案详情与检索结果的响应 Schema 示例

- **涉及位置**:§4(公共响应对象)、§8(`archives/{document_id}`、`archive-retrieval`)
- **说明**:`Project`、`ProcessDocument`、`FieldDraft`、`Citation`、`ArchiveAnswer` 均有示例,但正式档案详情(`GET .../archives/{document_id}`)与 `archive-retrieval` 的 Chunk 列表响应未给出 JSON 示例。Swagger 契约完整度略欠。
- **优化方案**:补充两个响应示例(档案详情含七字段 + 证据;检索结果含 Chunk 引用数组)。

#### 建议 8:Swagger/README 免责声明要求写入 API 文档

- **涉及位置**:§1 文档信息、§3 通用约定
- **说明**:NFR-020 要求"Swagger 与 README 必须展示外部模型数据提示和虚构清单免责声明",API 文档全文未提;`archive-questions`/`suggestions` 会外发数据,该提示应在 OpenAPI 描述(description)层落实。
- **优化方案**:在 API 文档通用约定中增加"所有调用 DeepSeek 的接口,其 OpenAPI 描述必须包含外部模型数据提示;Swagger 首页必须展示虚构清单免责声明"。
