## 2. 🔴 必须修改

### R1 持久化方案与技术架构基线直接冲突

- **涉及位置**：FR-042 L788、L795；BR-033（L857）；`技术架构.md` L52、L101、L193～L196
- **问题描述**：FR-042 要求会话消息与 Graph 状态由 SQLite Checkpoint 持久化（BR-033 已明确），但当前架构基线三处写明相反约束：2.2 决策 6「LangGraph Checkpoint 只保留给旧 Agent」、3.4「LangGraph Checkpoint：只保存旧 Agent 运行状态」、§5 架构图注「新业务不依赖 `LegacyAgent` 或 `Checkpoint SQLite`」。同时 2.2 决策 7 明确「不为单一检索动作额外引入 Tool Calling Agent」，而 FR-042 恰恰引入了一个 Tool Calling Agent。
- **为什么必须改**：这不是措辞差异，而是需求已改变架构前提。若需求不显式声明「本条要求修订架构基线相应条款」，架构阶段只能二选一：要么违反已确认的架构决策，要么推翻 FR-042 的持久化前提。二者都必须由产品/范围决策确认，不能由下游设计自行解释。
- **修改建议**：二者择一，并在文档中写明：
  1. 在 FR-042 前置条件或 §16 增加一条：「FR-042 的持久化会话与工具调用编排要求修订《技术架构》2.2 决策 6/7、3.4 与 §5 图中注，架构阶段必须先完成该修订再设计。」
  2. 或改变需求方案：会话消息改由 PostgreSQL 保存，助手不使用 LangGraph Checkpoint。

### R2 质量验收缺失，`NFR-022` 的承诺在 §12 无落点

- **涉及位置**：NFR-022（L887）、§12 质量验收（L889～L925）、AC-FR-042-01～07（L813～L826）
- **问题描述**：NFR-022 声明「工具选择和回答质量另以固定资料评估」，但 §12.1～§12.4 只覆盖验收资料准备、AI 分类字段建议、FR-039 单次检索问答与业务闭环，没有任何一节定义档案助手的评测资料、指标或门槛。现有固定集 `question-ground-truth.json`（`archive-v1-fictional-evaluation-v1`）只含单轮 `expected_answer` + `expected_evidence`，没有「该题应走目录工具还是证据工具」的标注，也没有多轮用例。
- **为什么必须改**：AC-01（跨轮上下文）、AC-02（目录工具）、AC-03（原文引用）、AC-05/06（拒答）目前都没有可执行的质量证据来源，验收时无法判定通过，只能回到「主观评价」。
- **修改建议**：新增 §12.5「项目档案助手质量」，至少定义：
  - 固定评测集构成（目录类问题 / 原文事实类问题 / 无据拒答问题 / 跨项目隔离问题 / 多轮追问问题各若干条）；
  - 每题期望的工具路径与期望引用，明确哪些题必须调用目录工具、哪些必须调用证据工具、哪些必须拒答；
  - 门槛（例如工具路径正确率下限、引用正确率 100%、拒答 100%、跨轮上下文 N/N），并声明与 §12.3 一样「不得凭空指定」，需按 `docs/review/验证冻结清单.md` 的流程标定后冻结。

### R3 拒答判定依据未与既有 P14 结论对齐

- **涉及位置**：AC-FR-042-06（L823～L824）、§12.3 末条（「检索阈值…冻结流程见 `docs/review/验证冻结清单.md`」）
- **问题描述**：AC-06 只写「原文工具没有充分依据」，未定义判定者、判定规则与依据来源。§12.3 仍指向「标定并冻结检索阈值」的路线，而 P14 已判定该路线不可行：D4 结论为「不存在可行统一 Reranker 阈值」，D5 改为「一次 DeepSeek 结构化调用同时判断证据充分性并生成回答」，D6 在此基础上改为文档绑定 + Top-8。
- **为什么必须改**：拒答是 FR-042 唯一的安全底线条款，判定依据不明会把「阈值冻结」与「判定层」两套路线同时压给下游，直接复现 P14 的反复返工。
- **修改建议**：在 FR-042 异常与边界中写明证据充分性判定沿用哪条路线（当前应为 D5 判定层 + D6 文档绑定/Top-8），并同步修订 §12.3 中「冻结阈值」的表述，使其与 P14-D4/D5/D6 的实际结论一致。

### R4 幂等与自动重试未定义

- **涉及位置**：FR-042 异常与边界（L798～L809）、AC-FR-042-01/07
- **问题描述**：BR-023 规定连接失败和超时自动重试一次；FR-041 AC-02 已明确「自动重试不得重复记录成功审计」。FR-042 完全没有对应条款：自动重试时是否会重复写入用户消息、助手消息、工具调用审计，Checkpoint 是否会重复提交同一轮状态，均未规定。
- **为什么必须改**：AC-07 要求「工具记录只包含脱敏参数和结果摘要」，一旦重试产生重复记录，该条验收即不可判定。
- **修改建议**：在异常与边界补一条：「连接失败或超时自动重试一次；重试不得产生重复的用户可见消息或重复的工具调用审计记录，同一轮次只保留一次成功结果。」

### R5 客户端侧范围字段与消息长度约束缺少验收标准

- **涉及位置**：前置条件 L782、AC-FR-042-04（L819～L820）
- **问题描述**：L782 要求「客户端不得提交、覆盖或切换 `user_id`、`project_id`、`kb_id`」，但 AC-04 只覆盖模型工具参数，客户端请求体携带这些字段时的行为（忽略还是拒绝）没有验收标准，也没有语义定义。同理「消息 1～2000 个字符」没有任何 AC，空消息、纯空白消息、超长消息的行为均未规定。
- **为什么必须改**：两条都是可被第三方直接构造的输入边界，缺少验收标准等于把口径留给实现者。
- **修改建议**：
  - 明确客户端提交范围字段时是「静默忽略并按服务端绑定执行」还是「返回参数错误」，并补对应 AC；
  - 补充空/纯空白/超长消息的稳定结果与对应 AC；同时说明长度计数口径（见 S8）。

### R6 「可见性阻断删除中」在需求层没有定义

- **涉及位置**：FR-042 L802～L803、AC-FR-042-02（L815～L816）；§7.5 文档状态（L262～L274）
- **问题描述**：§7.5 只定义 7 个用户可见状态，并明确「删除是操作结果，不保留为用户可见状态」。AC-02 却要求返回「未被可见性阻断的档案」，FR-042 也以「正处于可见性阻断删除中」作为排除条件——该术语在需求层没有定义，只在实现（P13）中存在。
- **为什么必须改**：AC-02 的可判定性直接依赖这个术语。测试人员只能按各自理解构造「正在删除中」的场景。
- **修改建议**：在 §7.5 或 FR-042 中给出可判定口径，例如「删除已受理但尚未完成跨存储清理的文档，其档案不进入正式目录、检索与问答，直至删除完成或失败回滚」，并明确失败回滚后是否恢复可见。

### R7 会话生命周期与项目/文档删除的联动缺失

- **涉及位置**：FR-042（无相关条款）、FR-030 L320～L321、FR-040、`接口设计.md` L344/L743
- **问题描述**：FR-030 规定「项目没有任何未删除文档记录时可以删除项目，删除项目不删除其绑定的内部知识库」；接口设计进一步说明保留知识库是为了保护旧 RAG/Agent 数据。FR-042 未规定：项目被删除后，其档案助手会话、Checkpoint 线程与工具审计如何处理；项目删除后旧会话再发消息应返回什么；文档处于删除流程中时助手应拒绝还是返回空目录。
- **为什么必须改**：项目删除会影响 `project_id` 绑定的有效性，而会话归属与项目绑定又是 PostgreSQL 事实来源（BR-033），两者必须给出确定结论，否则数据会出现「会话指向已删除项目」的悬挂状态。
- **修改建议**：明确三件事——(a) 项目删除对既有会话的处置（保留但拒绝继续执行 / 一并失效）；(b) 项目已删除时会话接口的稳定结果；(c) 文档删除进行中时目录与证据工具的行为。

## 3. 🟡 建议优化

### S1 两个工具的参数契约边界未定

- **涉及位置**：正常流程 L791～L792
- **说明**：`list_formal_archives` 只写「受控的目录筛选条件」，没有列明条件白名单、默认条数与最大条数；`search_confirmed_archive_evidence` 只写「以查询词检索」，没有查询词长度、返回条数上限。
- **优化方案**：目录筛选维度直接对齐 FR-038 的正式目录契约（资料类型、项目阶段、日期区间、分页），并写明默认/最大条数；证据工具写明查询词长度上限与返回条数上限。

### S2 目录摘要的字段白名单与来源标注未定

- **涉及位置**：BR-032（L856）、正常流程 L793～L794
- **说明**：BR-032 只禁止「人工无证据字段作为原文依据」，未说明目录摘要是否展示人工填写值、是否标注 AI/人工来源。若摘要含人工填写值而助手以陈述句输出，仍会形成「无原文依据的事实结论」。
- **优化方案**：列出目录摘要的字段白名单，并要求人工来源、无原文证据状态随行返回，使模型与验收都能区分「原文事实」与「人工登记值」。

### S3 单轮工具调用次数与总超时上限缺失

- **涉及位置**：正常流程 L790、异常与边界 L806～L807
- **说明**：没有规定单轮最多工具调用次数/循环轮数/总超时，存在无限循环与成本、延迟失控风险。
- **优化方案**：给出上限（或明确标注「由设计阶段固定并在验收中记录」），并按 NFR-021 的日志要求保证超限可观察。

### S4 单个工具失败的语义未拆分

- **涉及位置**：异常与边界 L806～L807
- **说明**：现表述把「工具调用失败」直接归入「客户端只接收稳定错误码」，未区分「整轮失败」与「工具失败后降级拒答」。这决定用户看到的是 5xx 还是「无法回答」。
- **优化方案**：拆分两类失败并分别给出用户可见结果；明确工具失败时是否允许模型基于失败信息继续作答。

### S5 会话管理动作范围未声明

- **涉及位置**：AC-FR-042-07（L825～L826）
- **说明**：现有 `app/routers/agent.py` 只有创建会话、发送消息、读取消息、读取工具记录四类端点，没有列表与删除。FR-042 未声明本期是否需要会话列表/删除/重命名。
- **优化方案**：显式声明「本期仅创建、发送、读取」，或将列表/删除纳入范围并补 AC。

### S6 会话类型隔离缺少显式条款与 AC

- **涉及位置**：DEC-015（`decisions.md` L179）、FR-042 异常与边界
- **说明**：DEC-015 要求「旧制度会话与项目档案会话必须以受控会话类型区分」，需求正文与 AC 均未体现。若二者共用 `agent_sessions` 表与同一 Checkpoint，缺少条款会给「用制度会话 ID 读取档案会话消息」留下解释空间。
- **优化方案**：补一条「制度会话与档案会话不得互相读取消息、Checkpoint 或工具记录」，并增加对应 AC。

### S7 术语混用

- **涉及位置**：L774（项目档案助手）、L776（该能力）、L788（档案助手会话）、L782（会话）等
- **说明**：同一对象在四处使用不同称呼。
- **优化方案**：在 §7 词表登记统一对象名，正文统一使用。

### S8 消息长度计数口径未定义

- **涉及位置**：前置条件 L782
- **说明**：「1～2000 个字符」未说明是否含空白与换行、按 Unicode 码点还是字节计数。
- **优化方案**：写明计数口径与首尾空白处理规则。

## 4. 📋 风险提示

- **K1 Checkpoint 作为消息历史唯一来源**：BR-033 让 SQLite Checkpoint 承担会话消息持久化，但「持久化档案会话」在文件损坏、迁移、备份与多实例部署下的边界未声明；Checkpoint 也没有清理/保留策略，长期增长会与 §15 的 2 vCPU / 2 GB 目标资源冲突（该规格实测尚未进行）。
- **K2 工具审计写放大**：每次工具调用写一次 PostgreSQL；叠加多轮追问后，写压力与延迟都会累积。P14 已记录完整链路 P95 处于 3.6～9.5 s 量级（D4 base 3670.83 ms、D3 9512.28 ms），助手多轮会在此之上叠加。
- **K3 前置依赖存在文档状态不一致**：AC-03/AC-06 的可达性取决于正式检索链路，而 `P14-D6-文档绑定与Top8证据保留方案.md` 文档头仍写「正式配置切换未授权」，与《需求说明》《智慧档案V1实施计划》的「正式配置已切换、D6-B 已完成」不一致。建议先校订该文档状态，避免以过期状态作为助手验收依据。
- **K4 继承 Q-01 的安全漏答**：§16 已确认 Q-01 为「安全漏答，不能把门槛通过解释为所有有据问题均可回答」。FR-042 复用同一链路会继承该限制，而 AC-03 未声明这一已知例外口径，验收时易产生争议。
- **K5 需求范围声明未同步**：《技术架构》L7 的「对应需求」仍写 FR-019～FR-041、BR-008～BR-029、NFR-011～NFR-021，未包含 FR-042、BR-030～BR-033、NFR-022；《接口设计》《数据库设计》文档头更新日期仍为 2026-09-11。属于本次需求确认后的必然待办，建议列入下游设计的前置同步清单。

## 6. 评审结论

FR-042 的功能目标、服务端绑定范围、只读工具边界与安全条款方向是清晰的，AC 也覆盖了绑定不可覆盖、目录范围、原文引用、拒答和脱敏五类关键点；但 **R1（架构前提冲突）、R2（质量验收缺失）、R3（拒答判定依据）、R4～R7（幂等、客户端边界、术语定义、删除联动）** 属于必须补齐后才能进入架构、数据库与 API 设计的问题。

请先就第 5 节的问题逐项确认并修订需求，再按 §18 的顺序进入架构设计。

### 8.3 复审新增问题

#### 🔴 N1 失败轮次的持久化语义未定义

- **涉及位置**：L827～L830、L831～L833；AC-FR-042-09、AC-FR-042-13
- **问题描述**：条款只规定「整轮返回稳定不可用结果」，未规定该轮的用户消息是否留在 Checkpoint、失败的工具调用是否写一条 `FAILED` 审计、会话 `updated_at` 是否更新。现有实现先例（`app/services/agent/execution.py` L161～L165）在失败时会记录失败观测量并提交，需求未说明 FR-042 是沿用该口径还是「失败不落任何记录」。
- **为什么必须改**：AC-09（重试后只保留一轮消息与每个 `tool_call_id` 一条记录）与 AC-13（超限即停止）都依赖这条语义才能判定；否则实现与测试各自解释失败轮次的可见状态。
- **修改建议**：补一条明确三项——(a) 失败轮次的用户消息是否保留及下一轮上下文是否包含它；(b) 失败工具调用是否写 `FAILED` 审计（若写，需与 AC-09 的「一条记录」口径协调）；(c) 失败轮次是否更新会话时间。

#### 🔴 N2 目录工具的 `document_ref` 没有消费路径

- **涉及位置**：L806～L808（返回 `document_ref`）对比 L802～L803（证据工具仅接受查询词）与 AC-FR-042-03
- **问题描述**：目录工具向模型返回「本次调用的临时 `document_ref`」，但两个工具的入参白名单里没有任何地方接收它；证据工具只接受查询词，引用又全部由服务端映射。同时该字段是「本次调用临时」，跨轮不可复用。
- **为什么必须改**：DEC-015 的立项场景是「先找到验收资料，再核对原文」。当前契约下模型无法把第二次检索限定到刚查到的某份档案，只能把文件名写进查询词；`document_ref` 成为死参数，也让「跨轮上下文」的价值打折。
- **修改建议**：二选一并在需求中写明——(a) 允许模型把 `document_ref` 作为证据工具的受控范围提示，服务端必须重新校验其属于会话绑定项目，且不作为引用来源；(b) 删除该字段，并在 §12.5 的目录题标注中明确「第二轮检索以文件名等自然语言线索表达」。

#### 🔴 N3 目录摘要字段枚举与「每个档案字段」自相矛盾

- **涉及位置**：L806～L809、AC-FR-042-15 对比 §7.4 正式档案字段（L233～L243）
- **问题描述**：L806～L807 枚举的字段值是标题、资料类型、文档日期、编制单位、项目阶段（5 个），但同段又要求返回「每个档案字段的 `source` 与 `has_source_evidence`」。§7.4 定义的 7 个字段中，**版本号**与**关键词**未出现在枚举里。
- **为什么必须改**：AC-15 的「规定字段」因此没有唯一清单，实现与验收会各自补全或裁剪；若「每个档案字段」按 §7.4 字面执行，摘要又会多出两个字段。
- **修改建议**：明确目录摘要的字段白名单（含或明确排除版本号、关键词），并把措辞改为「白名单内每个字段的 `source` 与 `has_source_evidence`」。

### 8.4 复审新增建议

- **N4 无效工具调用是否计入上限未定义**（L810 对比 AC-FR-042-14）：若计入，模型两次参数错误即整轮失败；若不计入，需要给出重试次数上限。建议明确其中一种。

- **影响**：按 AC-03 字面实现必然违反 BR-038；按 BR-038 实现必然形成与 FR-039 不同的结构，

- **建议（二选一，推荐第 1 种）**：

     不新增第二套文件/位置/摘录字段；持久化文档/Chunk 标识与检索分数按 BR-038 排除」；
  2. 或明确 FR-042 引用是 FR-039 结构的**脱敏子集**，并在 BR-038 旁注明「子集不算第二套结构」。
