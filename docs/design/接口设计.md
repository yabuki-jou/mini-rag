## 3. 通用约定

### 3.1 身份、所有权与请求头

| 项目 | 约定 |
|---|---|
| 身份 | 除 `/auth/register`、`/auth/login`、`/auth/refresh` 和 `/health` 外，接口必须携带 `Authorization: Bearer <Access Token>` |
| 所有权 | 服务先验证用户存在，再验证项目归属；资源必须属于路径中的项目 |
| 请求追踪 | 服务返回 `X-Request-ID`；客户端可传入合法 UUID，否则服务生成 |
| 内容类型 | JSON 接口使用 `application/json`；上传接口使用 `multipart/form-data` |
| 时间格式 | RFC 3339 UTC，例如 `2026-08-06T09:30:00Z` |
| UUID | 所有资源 ID 使用 UUID 字符串 |

用户身份仅来自已验证的 Access Token；`X-User-ID` 不再是受支持的身份头。客户端不得提交 `owner_id`、`user_id`、`kb_id`、
`confirmed_by`、`actor_id`、`file_hash`、`snapshot_hash`、`visibility_blocking` 或内部
操作状态；这些值必须由服务端计算或注入。
项目档案助手请求还不得在 JSON 中提交 `project_id`、`thread_id`、`agent_type`
或其他未声明字段；该类字段一律返回 `422 VALIDATION_ERROR`，不静默忽略。

Chroma 不提供面向客户端的 API 路径或鉴权边界：它只位于部署内部网络，由 FastAPI 服务端
调用。`VECTOR_UNAVAILABLE` 是向量后端不可用的稳定业务错误，不暴露 Chroma 地址、
配置或内部异常。

### 3.1.1 账号密码认证（FR-019～FR-021）

`POST /auth/register` 接受 `username`、`name` 和 `password`，返回不含密码或哈希的用户信息。
用户名规范化为小写，必须全局唯一；GET /auth/me 必须携带 Bearer Access Token，返回当前用户的 UserRead，不包含密码或密码哈希。

`POST /auth/login` 接受 `username` 和 `password`，成功时返回 Access Token（30 分钟）、
Refresh Token（7 天）及其秒数。`POST /auth/refresh` 的 JSON 请求体仅含 `refresh_token`，
成功时仅返回新的 Access Token。`POST /auth/logout` 必须携带当前会话的 Access Token，
成功时返回 `204` 并撤销对应认证会话。

| 接口 | 是否需要认证 | 请求体 | 成功响应 | 业务边界 |
|---|---|---|---|---|
| `POST /auth/register` | 否 | `username`、`name`、`password` | `201 UserRead` | 用户名规范化为小写；密码、密码哈希不在响应中出现 |
| `POST /auth/login` | 否 | `username`、`password` | `200 {access_token, refresh_token, token_type, access_expires_in, refresh_expires_in}` | 创建一条可撤销认证会话；`GET /auth/me` 必须携带 Bearer Access Token，返回当前用户的 `UserRead`，不返回密码或密码哈希 |
| `POST /auth/refresh` | 否 | `refresh_token` | `200 {access_token, token_type, access_expires_in}` | 只接受 Refresh Token；只签发新的 Access Token，不轮换 Refresh Token |
| `POST /auth/logout` | Bearer Access Token | 无 | `204` | 撤销当前 Access Token 所属会话；重复注销保持幂等 |

`username` 允许 3～50 位小写字母、数字、下划线或连字符；`name` 为 1～100 位显示名；注册密码为
8～128 个字符。Access Token 的有效期为 30 分钟，Refresh Token 与认证会话的有效期为 7 天。
服务器未配置有效 `AUTH_JWT_SECRET` 时，涉及 Token 签发或验证的请求返回受控的
`503 AUTH_NOT_CONFIGURED`，不得使用示例默认值签发 Token。

### 3.2 并发、幂等与分页

- 修改项目、清单项、字段、确认和关联时，请求体必须传对应资源的 `expected_version`。
  与服务器当前版本不一致时返回 `409 VERSION_CONFLICT`，不覆盖新数据。
- 创建清单项必须携带项目当前 `expected_project_version`；创建成功后项目版本原子加一。
- Parse、suggest、confirm 和 delete 的并行请求返回 `409 DOCUMENT_OPERATION_IN_PROGRESS`。
- 文件上传由同项目 `file_hash` 去重；不同项目同哈希不互相暴露信息。
- 列表使用 `page`（从 1 开始）和 `page_size`，默认 `page=1`、`page_size=20`、最大
  `100`。项目、文档处理、正式目录、清单项和审计列表均以各自主要时间字段倒序、`id DESC`
  作为次级排序，保证稳定分页。
- 第一版不启用 `Idempotency-Key`。版本锁、单 RUNNING 操作锁、重复确认业务幂等、
  `file_hash` 去重和未完成删除恢复共同防止关键副作用重复；不承诺客户端因响应丢失重发
  POST 时返回第一次响应。清单项创建、上传和关联创建分别由项目版本、文件哈希、
  文档/清单项版本约束防止重复成功结果。
- FR-042 不提供会话列表、重命名或用户主动删除；历史按 Checkpoint 消息顺序、工具日志按
  `created_at ASC` 一次返回，都不接受分页参数。当前是本地短会话 MVP，客户端必须顺序发送同一会话的消息；
  两个读取接口的响应条数也不设置独立上限，属于已登记的短会话限制，不声称支持长会话或同会话并发。
  客户端主动重发消息按新轮次处理。

### 3.3 统一成功与错误响应

列表响应：

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0
}
```

错误响应保持 `AppError` 契约；预期业务错误仅在已明确约定且可安全返回时包含可选的
`details`：

```json
{
  "error": {
    "code": "PROJECT_NOT_FOUND",
    "message": "项目不存在或无权访问。"
  }
}
```

参数格式或类型错误返回 `422 VALIDATION_ERROR`，并可包含 Pydantic 校验 `details`。业务
`details` 不得包含存储路径、密钥、原文件内容、模型提示词或其他项目资源。
未知异常只在服务端日志记录，客户端固定接收 `500 INTERNAL_ERROR`，不返回堆栈、
数据库地址、文件路径、模型提示词或外部服务原始异常。

### 3.4 固定字典的 API 值

| 字段 | API 值 |
|---|---|
| `document_type` | `CONTRACT`、`DESIGN`、`CONSTRUCTION`、`MEETING_MINUTES`、`ACCEPTANCE`、`OTHER` |
| `project_stage` | `PREPARATION`、`DESIGN`、`CONSTRUCTION`、`ACCEPTANCE`、`CROSS_STAGE`、`OTHER_STAGE` |
| `field_name` | `TITLE`、`DOCUMENT_TYPE`、`DOCUMENT_DATE`、`AUTHORING_ORGANIZATION`、`VERSION_NUMBER`、`PROJECT_STAGE`、`KEYWORDS` |
| `review_status` | `PENDING_CHECK`、`VALUE_CONFIRMED`、`EMPTY_ACCEPTED` |
| `field_source` | `AI`、`MANUAL` |
| `location_type` | `PDF_PAGE`、`DOCX_PARAGRAPH`、`TEXT_LINE_RANGE` |
| `answer_status`（FR-039/FR-042） | `ANSWERED`、`REFUSED_NO_EVIDENCE` |

Swagger 的字段说明同时展示中文名称。资料类型和项目阶段不接受自由字符串；人工更正
也只能从上述字典选择。

### 3.5 免责声明与数据提示

## 5. 项目接口（FR-030）

### `POST /projects`

请求：

```json
{
  "name": "示例工程",
  "description": "可选",
  "use_demo_checklist": true
}
```

- `name` 必填，服务去除首尾空格后校验同一用户唯一；项目名称区分大小写。
- 客户端不提交 `kb_id`；服务创建项目专属知识库范围。
- 选择演示清单时复制五个虚构规则为该项目独立清单项。
- 成功返回 `201 Project`。
- 同名返回 `409 PROJECT_NAME_CONFLICT`。

### `GET /projects` 与 `GET /projects/{project_id}`

只返回当前用户项目。列表默认按 `updated_at DESC, id DESC`，使用公共分页响应。

### `PATCH /projects/{project_id}`

请求只允许修改 `name`、`description` 与 `expected_version`：

```json
{
  "name": "已更名工程",
  "description": null,
  "expected_version": 1
}
```

空字符串名称返回 `422 VALIDATION_ERROR`；同名和旧版本分别返回稳定 `409` 错误。

### `DELETE /projects/{project_id}`

仅项目没有任何未删除文档时返回 `204`，并级联删除项目清单与项目审计。存在任意
`UPLOADED`、失败、待确认、已确认或待重新确认文档时返回
`409 PROJECT_HAS_DOCUMENTS`；不提供“删项目即删全部文档”接口。空项目删除成功前，服务必须
幂等清理该项目的 ARCHIVE Agent Checkpoint 线程，再删除档案助手会话和工具日志。
任一层失败返回 `503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`，不返回虚假 `204`；删除成功后旧会话 ID
在项目档案助手入口统一按不存在处理。

项目删除不得删除其内部 `knowledge_bases` 记录。该记录与历史兼容数据一并保留，但不再通过旧
`/knowledge-bases` 路由公开；V1 的 `/projects` 不再显示已删除项目。

## 6. 清单接口（FR-031、FR-037）

### `GET /projects/{project_id}/checklist-items`

返回项目清单与实时派生状态：

```json
{
  "items": [
    {
      "id": "uuid",
      "name": "施工方案",
      "document_type": "CONSTRUCTION",
      "is_required": true,
      "project_stage": "CONSTRUCTION",
      "description": "每个施工阶段至少一份",
      "fulfillment_status": "MISSING",
      "confirmed_document_count": 0,
      "version": 1
    }
  ]
}
```

`fulfillment_status` 仅为 `SATISFIED`、`MISSING`、`NOT_PROVIDED`：必需项未满足为
`MISSING`，可选项未满足为 `NOT_PROVIDED`。无清单时返回空数组，不输出项目级
缺失结论。

### `POST /projects/{project_id}/checklist-items`

请求除 `name`、`document_type`、`is_required`、`project_stage`、可选 `description` 外，
必须携带 `expected_project_version`。服务在同一事务中校验项目版本、创建清单项、写审计并
使 `projects.version` 原子加一；旧版本返回 `409 VERSION_CONFLICT`。

成功 `201` 返回新清单项和新的项目版本：

```json
{"item": {"id": "uuid", "name": "施工方案", "document_type": "CONSTRUCTION", "is_required": true, "project_stage": "CONSTRUCTION", "fulfillment_status": "MISSING", "version": 1}, "project_version": 2}
```

### `PATCH` / `DELETE /projects/{project_id}/checklist-items/{item_id}`

`PATCH` 必须携带 `expected_version`。修改名称、资料类型或项目阶段时，服务使既有
关联变为 `INVALIDATED` 并立即重算状态；仅修改说明不使关联失效。删除成功返回 `204`
并删除关联、写审计。上述接口不提供用户自定义模板创建、保存或复用能力。

### 档案—清单关联

`GET /projects/{project_id}/documents/{document_id}/checklist-link-suggestions` 只依据
资料类型和项目阶段返回建议，不会自动创建或满足清单项。

创建关联请求：

```json
{
  "checklist_item_id": "uuid",
  "expected_document_version": 4,
  "expected_checklist_item_version": 1
}
```

`POST .../checklist-links` 只接受 `CONFIRMED` 档案，成功创建 `CONFIRMED` 关联并返回
`201`。一份档案可关联零到多个清单项，一个清单项可由多份档案满足。不同项目资源、
待确认文档、重复关联或旧版本分别返回 `403/404`、`409`、`409`、`409`。

## 7. 文档上传、处理与字段草稿（FR-032～FR-036）

### `POST /projects/{project_id}/documents`

使用 `multipart/form-data`，唯一文件字段为 `file`。不接收客户端声明的资料类型、
阶段、哈希、状态或归属。

上传前校验：

- 仅 PDF（有有效文本）、DOCX、TXT、MD；扩展名不支持返回 `415 FILE_TYPE_UNSUPPORTED`。
- 文件最大 20 MB；超限返回 `413 FILE_TOO_LARGE`。
- 当前项目最多 100 份未删除文档；超限返回 `409 PROJECT_DOCUMENT_LIMIT_REACHED`。
- 同项目原文件 `file_hash` 已存在时返回 `409 DUPLICATE_FILE`，仅返回当前项目已有
  文档的 `id`、`filename`、`status`，位置为 `error.details`；不保存文件、不建记录、不写向量或审计。

成功创建原文件和 `UPLOADED` 归档记录，返回 `201 ProcessDocument`。上传不会自动解析
或调用 DeepSeek。

### Parse 与 parse retry

| 接口 | 允许初始状态 | 成功状态 | 失败行为 |
|---|---|---|---|
| `POST .../parse` | `UPLOADED` | `PARSED` | 无有效文本转 `PARSE_FAILED`，返回 `422 PARSE_TEXT_UNAVAILABLE` |
| `POST .../parse-retry` | `PARSE_FAILED` | `PARSED` | 仍失败保留最新受控失败摘要 |

扫描 PDF 使用稳定错误 `SCANNED_PDF_UNSUPPORTED` 与“暂不支持扫描件，请上传文本版资料”。
已解析文档再次调用普通 `parse` 返回 `409 PARSE_NOT_ALLOWED`，不重复生成快照、向量或
档案数据。连接失败和超时仅自动重试一次；最终失败返回稳定 `503`，不暴露解析器堆栈。

### Suggest 与人工草稿

| 接口 | 允许初始状态 | 成功结果 |
|---|---|---|
| `POST .../suggestions` | `PARSED` | AI 草稿、字段证据，转 `PENDING_CONFIRMATION` |
| `POST .../suggestions/retry` | `SUGGESTION_FAILED` | AI 草稿、字段证据，转 `PENDING_CONFIRMATION` |
| `POST .../suggestions/regenerate` | `PENDING_CONFIRMATION` 且无人工编辑 | 原子替换 AI 草稿，状态保持不变 |
| `POST .../manual-draft` | `PARSED`、`SUGGESTION_FAILED` | 七字段空草稿，全部 `PENDING_CHECK`，转 `PENDING_CONFIRMATION` |

`POST .../suggestions/regenerate` 请求：

```json
{"expected_version": 4}
```

`suggestions/regenerate` 必须携带文档当前 `expected_version`。“无人工编辑”固定为：七个
字段均为 `PENDING_CHECK`，且没有 `source = MANUAL` 的字段或人工修改的字段证据。请求
到达时发现人工内容，立即返回 `409 SUGGESTION_WOULD_OVERWRITE_MANUAL_DRAFT`，不调用模型。
字段保存接口不得允许客户端伪造 `source = AI`；只要用户保存字段或证据修改，服务必须将其
标记为人工修改。

重新生成时服务先在内存中完成模型调用、字典和证据校验；随后在同一事务中再次校验版本和
人工内容。版本变化返回 `409 VERSION_CONFLICT`；人工内容出现返回
`409 SUGGESTION_WOULD_OVERWRITE_MANUAL_DRAFT`；两者均保持原草稿、版本和状态。校验通过
才原子替换现有草稿并递增版本。模型未配置、关闭、连接失败或超时返回
`503 ARCHIVE_SUGGESTION_UNAVAILABLE`；模型输出不合格返回 `422 SUGGESTION_INVALID_OUTPUT`；
两种情况均保留现有草稿与 `PENDING_CONFIRMATION`。首次建议或失败后重试遇到上述错误时，
文档进入或保持 `SUGGESTION_FAILED`；用户仍可调用 `manual-draft` 完成纯手工归档。

### `GET .../draft` 与 `PUT .../fields/{field_name}`

草稿详情返回 `ProcessDocument`、七个 `FieldDraft`、当前快照元数据和允许的下一步动作。
只要文档已解析，就可以读取草稿；编辑只允许 `PENDING_CONFIRMATION` 或
`PENDING_RECONFIRMATION`。

字段更新请求：

```json
{
  "text_value": "施工方案",
  "date_value": null,
  "json_value": null,
  "review_status": "VALUE_CONFIRMED",
  "source": "MANUAL",
  "no_source_evidence": true,
  "evidences": [],
  "reason": "原文未写标题，依据项目资料目录补充",
  "expected_version": 4
}
```

规则：

- `DOCUMENT_DATE` 只使用 `date_value`；资料类型为 `CONTRACT` 时，该日期表示合同签订日期，
  其他资料类型表示文档自身日期。`KEYWORDS` 只使用字符串数组 `json_value`；
  其他字段只使用 `text_value`。
- `EMPTY_ACCEPTED` 时所有值为空；`VALUE_CONFIRMED` 时值必须存在。
- AI 非空字段必须带当前快照、当前文档的至少一条证据；否则 `422 AI_FIELD_EVIDENCE_REQUIRED`。
- 人工无证据值必须设置 `source = MANUAL`、`no_source_evidence = true`，证据列表为空。
- `source = AI` 仅由建议服务写入；客户端更新字段或证据时，服务必须记录人工来源，不能
  让客户端自行声明 AI 来源以绕过重新生成保护。
- 编辑已确认档案的任何正式字段或证据时，服务先转为 `PENDING_RECONFIRMATION` 并从
  正式范围排除，再返回更新后的草稿。
- 每次字段或证据保存、首次建议成功、建议重试成功、人工草稿创建、重新生成替换、确认或
  取消确认成功，均使 `archive_documents.version` 原子加一；解析和解析重试不递增。
  所有声明 `expected_version` 的接口必须使用响应返回的最新版本。

### 确认与取消确认

`POST .../confirm` 请求：

```json
{"expected_version": 4}
```

确认前服务校验七个字段均非 `PENDING_CHECK`、标题和资料类型为非空
`VALUE_CONFIRMED`、AI 非空字段有当前文档证据、并发版本一致。成功时生成 Final Chunk、
更新 `CONFIRMED`、写确认审计并返回正式档案；索引/外部依赖失败时不返回成功确认。

文档已为 `CONFIRMED` 且 `expected_version` 等于当前版本时，重复确认以 `200` 幂等返回
当前档案，不重建 Final Chunk、不新增成功审计。该规则是业务幂等而非传输重放幂等；旧版本
（包括响应丢失后的旧请求）返回 `409 VERSION_CONFLICT`。

`POST .../cancel-confirmation` 请求也携带 `expected_version`，仅 `CONFIRMED` 可调用。
它转为 `PENDING_RECONFIRMATION`、立即退出正式目录与问答，并清理 Final Chunk；若外部
清理失败，返回稳定失败结果但仍保守排除该档案。
取消确认不改变 `checklist_links.status`；清单满足性由档案与关联均为 `CONFIRMED` 派生，
因此取消后立即变为“缺失/未提供”，再次确认后自动恢复满足。

## 8. 处理列表、正式目录与问答（FR-038、FR-039）

### 文档处理列表

`GET /projects/{project_id}/documents` 从 `documents INNER JOIN archive_documents` 查询
当前项目全部未删除归档文档。文件名、原文件哈希和上传时间来自 `documents`；归档状态、
确认时间、字段检查汇总和受控失败摘要来自 `archive_documents`。它不查询 Chroma，也不
返回内部操作状态。

支持可选 `status` 筛选和公共分页，默认 `updated_at DESC, id DESC`。

### 正式档案目录与详情

`GET /projects/{project_id}/archives` 只查询：

```text
archive_document.status == CONFIRMED
AND no visibility-blocking operation exists
```

支持以下可选筛选：

| 参数 | 说明 |
|---|---|
| `document_type` | 固定资料类型 |
| `project_stage` | 固定项目阶段 |
| `document_date_from` / `document_date_to` | `DOCUMENT_DATE` 日期闭区间；合同资料按合同签订日期筛选，其他资料按文档自身日期筛选 |
| `document_date_is_null` | `true` 时仅返回日期为空资料，不能与日期区间同时使用 |
| `authoring_organization` | 编制单位精确匹配；大小写语义由数据库排序规则决定 |

默认 `confirmed_at DESC, id DESC`。`GET .../archives/{document_id}` 仅允许读取正式档案；待确认、
待重新确认或删除阻断文档返回 `404 ARCHIVE_NOT_FORMAL`，不通过详情泄露草稿字段。

### `POST /projects/{project_id}/archive-retrieval`

请求：

```json
{"query": "施工方案的编制单位是什么？", "top_k": 5}
```

该接口只用于 Swagger 中核对正式检索证据，返回当前项目、当前正式档案范围内的 Chunk
引用；`top_k` 默认 `5`、最大 `10`。当前固定以 Chroma Top-30 作为候选池，完成范围复核后才
本地重排。兼容字段 `score` 仍为 `1 - Chroma cosine distance`；`reranker_score` 是最终排序和独立
重排阈值使用的分数。当前未设置独立 Reranker 分数阈值，证据充分性由问答决策层判断；没有依据返回
`200` 与空 `items`。不得引用待确认、
待重新确认、人工无证据字段或其他项目资料。

```json
{"items": [{"chunk_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "document_id": "00000000-0000-0000-0000-000000000001", "filename": "施工方案.docx", "location_type": "DOCX_PARAGRAPH", "location_start": 3, "location_end": 3, "excerpt": "编制单位：示例建设公司", "score": 0.62, "reranker_score": 0.87}], "requested_top_k": 5, "returned_count": 1}
```

这是 Top-K 结果，不使用分页；在 P14 阶段 C 中 `reranker_score` 的比较方向是“越大越相关”，而
`score` 仅保留为兼容的 Chroma 分数。固定集通过前，客户端不得把任何分数当作已冻结的质量阈值。

### `POST /projects/{project_id}/archive-questions`

请求与 `archive-retrieval` 相同，但不需要 `top_k`：

```json
{"question": "施工方案的编制单位是什么？"}
```

服务先用 PostgreSQL 获取正式 `document_id` 集合（单项目最多 100 个），再以服务器注入的
`user_id + project_id + kb_id + document_id` 过滤 Chroma，并按现有正式检索链路取得内部前 8 个候选。
问答层不再把“冻结后的 `min_relevance_score` 过滤为空”作为证据充分性判定：候选为空时直接返回
`REFUSED_NO_EVIDENCE`，短路且不调用 DeepSeek；候选非空时仅进行一次结构化 DeepSeek 调用，由模型
同时返回证据充分性决策和回答：

```json
{
  "decision": "ANSWERED",
  "answer": "施工方案的编制单位为示例建设公司。",
  "citation_numbers": [1]
}
```

其中 `decision` 只能是 `ANSWERED` 或 `REFUSED_NO_EVIDENCE`，`citation_numbers` 是本轮输入证据的
1-based 整数编号；服务端必须用严格 JSON 解析拒绝重复键，并校验编号范围、类型和重复性，再从已
校验候选映射文件名、定位和摘录。模型不能直接生成或覆盖引用对象。`ANSWERED` 时 `answer` 必须
非空且至少有一个合法引用；`REFUSED_NO_EVIDENCE` 时模型 `answer` 可以为空，服务端忽略其文案并
返回固定拒答和空 `citations`。JSON 无效、编号不合法或 `ANSWERED` 没有引用时返回稳定 `503
ARCHIVE_ANSWER_UNAVAILABLE`。该结构化输出是内部模型契约，外部 `ArchiveAnswer` 响应形状保持不变。

问题长度为 `1..2000` 个字符；模型关闭、未配置或最终连接失败
返回 `503 ARCHIVE_ANSWER_UNAVAILABLE`，目录、结构化筛选、清单与重复检查不受影响。

## 9. 删除与审计（FR-040、FR-041）

### `DELETE /projects/{project_id}/documents/{document_id}`

删除可从任一稳定用户可见文档状态发起。服务先创建内部
`DELETE + RUNNING + visibility_blocking = true`，使档案立即退出正式目录、检索和问答，
随后依次清理 Final Chunk、原文件、快照、字段、证据和清单关联。

- 全部成功：返回 `204 No Content`，保留脱敏删除审计。
- 解析、建议、确认或另一删除操作运行中：返回 `409 DOCUMENT_OPERATION_IN_PROGRESS`。
- 外部清理失败：返回 `503 DOCUMENT_DELETE_INCOMPLETE`，文档保持正式范围外；再次调用
  同一 `DELETE` 恢复未完成删除，不创建重复文件、记录、向量或成功审计。
- 越权或不同项目文档：返回 `404` 或 `403`，不得泄露文件名、状态或哈希。

### `GET /projects/{project_id}/audit-logs`

只返回当前用户项目的审计，默认 `created_at DESC, id DESC`，支持公共分页和可选
`operation_type` 筛选。响应不包含原文、完整字段、模型提示词、模型输入输出、内部操作
堆栈或文件路径。

```json
{
  "items": [
    {
      "id": "uuid",
      "operation_type": "ARCHIVE_CONFIRMED",
      "actor_id": "uuid",
      "resource_type": "DOCUMENT",
      "resource_id": "uuid",
      "redacted_summary": {"status": "CONFIRMED"},
      "created_at": "2026-08-06T09:30:00Z"
    }
  ],
  "page": 1,
  "page_size": 20,
  "total": 1
}
```

为保持 Swagger 筛选稳定，审计 API 固定接受：

```text
ARCHIVE_CONFIRMED
ARCHIVE_CONFIRMATION_CANCELLED
ARCHIVE_FIELD_UPDATED
CHECKLIST_ITEM_CREATED
CHECKLIST_ITEM_UPDATED
CHECKLIST_ITEM_DELETED
CHECKLIST_LINK_CONFIRMED
CHECKLIST_LINK_DELETED
PARSE_RETRIED
SUGGESTION_RETRIED
SUGGESTION_REGENERATED
DOCUMENT_DELETED
```

这些是业务审计类型，不等同于 `archive_operations.operation_type` 的内部
`PARSE/SUGGEST/INDEX/DELETE`。数据库当前以受控字符串保存审计类型；实现时必须由
Pydantic Enum 约束上述 API 值，不能接受自由字符串。

## 10. 稳定业务错误码

| HTTP | 错误码 | 触发条件 |
|---|---|---|
| 401 | `AUTHENTICATION_REQUIRED` | 缺失或格式错误的 Bearer Token |
| 401 | `INVALID_CREDENTIALS` | 用户名不存在、密码错误或旧用户无凭据 |
| 401 | `TOKEN_EXPIRED` | Access 或 Refresh Token 已过期 |
| 401 | `INVALID_TOKEN` | Token 伪造、声明/用途错误、会话不存在、已撤销或 Refresh Token 摘要不匹配 |
| 409 | `USERNAME_CONFLICT` | 规范化后的用户名已存在 |
| 503 | `AUTH_NOT_CONFIGURED` | 未配置有效 JWT 签名密钥，认证服务拒绝签发或验证 Token |
| 403 | `PROJECT_FORBIDDEN` | 当前用户无项目所有权 |
| 404 | `PROJECT_NOT_FOUND` | 项目不存在 |
| 404 | `DOCUMENT_NOT_FOUND` | 文档不存在或不属于项目 |
| 404 | `ARCHIVE_NOT_FORMAL` | 请求正式详情但档案未正式确认 |
| 404 | `ARCHIVE_AGENT_SESSION_NOT_FOUND` | 项目范围内不存在匹配当前用户、项目、知识库和 ARCHIVE 类型的会话 |
| 404 | `CHECKLIST_ITEM_NOT_FOUND` / `CHECKLIST_LINK_NOT_FOUND` | 目标资源不存在或不属于项目 |
| 409 | `PROJECT_NAME_CONFLICT` | 同一用户项目名重复 |
| 409 | `PROJECT_HAS_DOCUMENTS` | 非空项目请求删除 |
| 409 | `PROJECT_DOCUMENT_LIMIT_REACHED` | 项目已有 100 份未删除文档 |
| 409 | `DUPLICATE_FILE` | 同项目 `file_hash` 重复 |
| 409 | `VERSION_CONFLICT` | 版本陈旧 |
| 409 | `DOCUMENT_OPERATION_IN_PROGRESS` | 文档已有运行中内部操作 |
| 409 | `PARSE_NOT_ALLOWED` / `SUGGESTION_NOT_ALLOWED` | 当前状态不允许该动作 |
| 409 | `SUGGESTION_WOULD_OVERWRITE_MANUAL_DRAFT` | 重新生成建议将覆盖人工草稿 |
| 409 | `CONFIRM_NOT_ALLOWED` / `CHECKLIST_LINK_NOT_ALLOWED` | 状态或前置条件不满足 |
| 413 | `FILE_TOO_LARGE` | 文件超过 20 MB |
| 415 | `FILE_TYPE_UNSUPPORTED` | 扩展名不在允许范围 |
| 422 | `VALIDATION_ERROR` | JSON、路径、枚举或字段值校验失败 |
| 422 | `PARSE_TEXT_UNAVAILABLE` | 支持格式但未提取到有效文本 |
| 422 | `SCANNED_PDF_UNSUPPORTED` | 扫描 PDF 无可提取文本 |
| 422 | `PARSE_TEXT_TOO_LARGE` | 归一化可提取文本超过 1,000,000 字符快照上限 |
| 422 | `AI_FIELD_EVIDENCE_REQUIRED` | AI 非空字段缺少有效证据 |
| 422 | `SUGGESTION_INVALID_OUTPUT` | 模型输出无法解析为固定字段和证据结构，不自动重试 |
| 503 | `ARCHIVE_SUGGESTION_UNAVAILABLE` | DeepSeek 建议不可用 |
| 503 | `ARCHIVE_ANSWER_UNAVAILABLE` | DeepSeek 问答不可用 |
| 503 | `PARSER_UNAVAILABLE` / `VECTOR_UNAVAILABLE` | 外部解析、Embedding 或 Chroma 依赖不可用 |
| 503 | `DOCUMENT_DELETE_INCOMPLETE` | 跨存储删除未完全完成 |
| 503 | `ARCHIVE_AGENT_MODEL_OUTPUT_INVALID` | 模型一次返回多个 Tool Call、调用未注册工具或尝试第三次工具调用 |
| 503 | `ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE` | 档案助手的模型、工具、Checkpoint 或 PostgreSQL 最终失败，包括项目删除联动失败 |
| 500 | `INTERNAL_ERROR` | 未知异常，隐藏内部细节 |

其中 `SCANNED_PDF_UNSUPPORTED` 是 PDF 无可提取文字时的具体原因；有少量可提取文字但
未达到有效文本阈值时返回 `PARSE_TEXT_UNAVAILABLE`。实现时响应只返回一个稳定代码，
不得把短文本 PDF 误报为扫描件。阈值与快照上限见 `docs/design/智慧档案V1解析器设计.md`。

## 13. 项目档案助手 API（FR-042 MVP）

### 13.1 路由、身份与会话范围

FR-042 MVP 当前包含五个项目嵌套端点：

| 方法与路径 | 请求 | 成功响应 |
|---|---|---|
| `POST /projects/{project_id}/agent-sessions` | `ArchiveAgentSessionCreate` | `201 ArchiveAgentSessionRead` |
| `GET /projects/{project_id}/agent-sessions/latest` | 无 | `200 ArchiveAgentSessionRead | null` |
| `POST /projects/{project_id}/agent-sessions/{session_id}/messages` | `ArchiveAgentMessageCreate` | `200 ArchiveAgentResponse` |
| `GET /projects/{project_id}/agent-sessions/{session_id}/messages` | 无 | `200 list[ArchiveAgentMessageRead]` |
| `GET /projects/{project_id}/agent-sessions/{session_id}/tool-calls` | 无 | `200 list[AgentToolCallLogRead]` |

五个端点都必须携带 Bearer Access Token。服务先从路径项目构造已验证的
`ProjectContext(user_id, project_id, kb_id)`，再以
`session_id + user_id + project_id + kb_id + agent_type=ARCHIVE` 整体查找会话。在已授权项目下，
任一条件不匹配均返回 `404 ARCHIVE_AGENT_SESSION_NOT_FOUND`，不暴露该 ID 是否属于其他项目、
其他用户或历史 `POLICY` 会话。项目本身不存在或不属于当前用户时，仍分别使用既有
`404 PROJECT_NOT_FOUND` 和 `403 PROJECT_FORBIDDEN`。

只有上述双重范围校验通过后才能使用会话的 `thread_id` 打开 Archive Graph 或
Checkpoint。反向也必须收紧：既有 `/agent-sessions` 制度入口只能匹配 `POLICY`，传入
ARCHIVE 会话 ID 时按既有 `AGENT_SESSION_NOT_FOUND` 处理，不读取其 Checkpoint 或工具日志。

### 13.2 创建会话

`ArchiveAgentSessionCreate` 是一个 `extra="forbid"` 的空对象 Schema。客户端必须发送：

```json
{}
```

不把创建接口设计成“无请求体”，因为那会使客户端偷偷附带的 `user_id`、`project_id`、
`kb_id`、`thread_id` 或 `agent_type` 无法由 Pydantic 空 Schema 稳定拒绝。未声明字段、缺少 JSON
请求体或非对象 JSON 均返回 `422 VALIDATION_ERROR`，不创建会话。

成功响应示例：

```json
{
  "id": "uuid",
  "project_id": "uuid",
  "created_at": "2026-09-15T09:30:00Z",
  "updated_at": "2026-09-15T09:30:00Z"
}
```

`ArchiveAgentSessionRead` 不返回 `user_id`、`kb_id`、`thread_id` 或 `agent_type`。客户端仅保存
业务会话 `id`，后续始终与同一 `project_id` 路径组合使用。`updated_at` 初始等于
`created_at`，只在形成可见完整轮次后更新。创建会话不调用 DeepSeek、Chroma 或
Checkpoint，因此模型不可用时仍可返回 `201`。不返回 `agent_type` 是因为项目嵌套路由已经把
会话类型固定为 `ARCHIVE`，同时避免客户端把该响应误用为历史 `POLICY` 会话 DTO。

#### 13.2.1 恢复最近会话

`GET /projects/{project_id}/agent-sessions/latest` 不接收请求体。服务必须先完成
`ProjectContext(user_id, project_id, kb_id)` 授权，再只查询同一范围内的 `ARCHIVE` 会话，按
`updated_at DESC`、`created_at DESC`、`id DESC` 稳定排序并最多返回一条。该顺序把最近一次成功
完整轮次更新过的会话视为最近活动会话；刚创建但还没有消息的会话仍以创建时间参与排序。

存在会话时返回既有 `ArchiveAgentSessionRead`；不存在时返回 `200` 和 JSON `null`。空结果不是
资源错误，不自动创建会话，也不读取 Checkpoint、工具日志或调用模型。数据库读取失败映射为
`503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`，不得返回内部异常。客户端拿到会话后继续通过既有
消息历史和工具记录端点加载持久内容。该接口不是通用会话列表，不接受分页、排序、会话 ID、
用户 ID 或知识库 ID 参数。

### 13.3 发送消息与当前回答

`ArchiveAgentMessageCreate` 仅允许 `message`：

```json
{"message": "施工方案的编制单位是什么？"}
```

Schema 必须在校验长度前先完成 `CRLF/CR → LF`，再去除首尾 Unicode 空白；规范化后按
Python 字符串 Unicode 码点计数为 `1..2000`，每个 `LF` 计一个码点。空、纯空白、
超长、非字符串或任何额外字段均返回 `422 VALIDATION_ERROR`；校验失败不执行 Graph、
不写 Checkpoint 或工具日志。

`ArchiveAgentResponse` 固定形状：

```json
{
  "session_id": "uuid",
  "answer_status": "ANSWERED",
  "answer": "根据正式档案，施工方案的编制单位为示例建设公司。",
  "citations": [
    {
      "filename": "施工方案.docx",
      "location_type": "DOCX_PARAGRAPH",
      "location_start": 3,
      "location_end": 3,
      "excerpt": "编制单位：示例建设公司"
    }
  ],
  "request_id": "00000000-0000-0000-0000-000000000001"
}
```

`ArchiveAgentCitationRead` 只含 FR-039 已有的 `filename`、`location_type`、
`location_start`、`location_end`、`excerpt` 字段名称与语义。
`location_start/location_end` 从 1 开始且结束不早于开始。响应禁止包含
`document_id`、`chunk_id`、`score`、`reranker_score`、`document_ref` 或其他持久化/检索内部字段。
`answer` 正文不由服务端注入 `[Sn]` 标记；判定层的请求内 `S` 编号只用于校验和映射，
最终 `citations` 按模型返回且经校验的编号顺序生成，并拒绝重复编号。为保持 FR-039 的公共
判定层输出不变，服务端也不剥离或拒绝模型正文自行产生的 `[Sn]` 文本；客户端不得解析该文本
或把它当成公开引用标识，结构化 `citations` 数组是唯一可信引用来源。

结果之间的不变式：

- 证据事实回答：最后一次成功工具调用必须是证据工具；服务端只把该次调用的原始 Top-8
  候选按原顺序传给公共判定层，并以该列表位置重新建立内部 `S1..S8` 映射。判定通过时返回
  `ANSWERED`、非空 `answer` 和至少一条脱敏 Citation；不得把两次调用结果取并集、去重或重排。
- 传给公共判定层的 `question` 固定为本轮用户消息按本节规则规范化后的文本；模型为证据工具
  生成或改写的检索 `query` 只影响候选获取，不得替代判定层看到的用户问题。
- 证据工具返回 0 个候选时，不调用公共判定层，直接短路为 `REFUSED_NO_EVIDENCE`、固定拒答文案
  和空引用；公共判定层只处理至少 1 个候选的情况。
- 目录回答：最后一次成功工具调用必须是目录工具；服务端只根据该次调用的安全投影和下述模板
  确定性生成 `ANSWERED` 正文与 `citations=[]`，内部 `document_ref` 只校验该次目录来源，不返回客户端。
- 原文证据不足：`REFUSED_NO_EVIDENCE`，服务端固定返回
  `正式档案中没有足够依据。` 和 `citations=[]`，忽略模型自行生成的拒答文案。
- 目录工具结果为空：不视为依赖失败，返回 `ANSWERED`、
  `当前项目没有可见的正式档案。` 和 `citations=[]`。
- 本轮没有任何成功工具调用时，不区分寒暄或普通问题，统一返回上述固定无依据拒答；
  不保留“模型零工具调用后直接自由回答”的成功分支。

在正常完成且存在两次成功工具调用时，只有最后一次成功调用决定最终回答类型与来源；较早的
ToolMessage 仅可帮助模型选择下一步工具或调整查询，不能成为最终正文、目录来源或 Citation 的依据。
任一工具最终失败或模型输出越界时仍按 §13.6 返回稳定 `503`，不进入上述成功投影。

非空目录结果的正文模板固定如下，条目顺序与该次目录查询的既有稳定顺序完全一致，不二次排序：

```text
第 {page} 页，本页 {当前页条目数} 份，共 {total} 份：
1. 文件名：{filename}；标题：{value|未登记}（source={source|null}, has_source_evidence={true|false}）；资料类型：{value|未登记}（source={source|null}, has_source_evidence={true|false}）；文档日期：{value|未登记}（source={source|null}, has_source_evidence={true|false}）；编制单位：{value|未登记}（source={source|null}, has_source_evidence={true|false}）；项目阶段：{value|未登记}（source={source|null}, has_source_evidence={true|false}）
```

`page`、当前页条目数和 `total` 必须直接取自最后一次成功目录工具结果；每页记录均从 `1`
重新连续编号，该编号不表示全局序号。每条记录占一行；枚举、日期、`source` 与布尔值使用工具安全投影中的 JSON
字面值，字段值为空时只把 `value` 显示为 `未登记`，仍保留其 `source` 与
`has_source_evidence`。正文不得出现调用内 `A{n}`、`document_ref`、`confirmed_at`、UUID、版本、
分数或未列入模板的字段。目录为空时仍使用上文固定空目录文案，不套用该非空模板。

当前 HTTP 响应的引用与回答是同一请求内的结果；不持久引用，不支持通过历史接口恢复。

### 13.4 历史消息

`GET .../messages` 新会话返回空数组。有历史时按 Checkpoint 顺序返回：

```json
[
  {"role": "USER", "content": "施工方案的编制单位是什么？", "citations": []},
  {"role": "ASSISTANT", "content": "施工方案的编制单位为示例建设公司。", "citations": []}
]
```

`ArchiveAgentMessageRead.role` 只能是 `USER` 或 `ASSISTANT`。每个可见轮次必须从一条非空
HumanMessage 开始，跳过中间 AI Tool Call 与 ToolMessage，且在下一条 HumanMessage 前存在一条
非空最终 AIMessage；否则该不完整轮次整体忽略。模型下一轮输入必须使用同一投影结果。

当前 HTTP 响应的 `answer` 必须与写入 Checkpoint 的最终 AIMessage 正文完全一致。该最终消息只能
来自服务端可信投影：证据路径使用公共判定层文本，目录路径使用确定性目录正文，无成功工具时使用
固定拒答。工具选择循环产生的自由文本和被投影替换的文本一律丢弃，不写入 Checkpoint，也不进入
历史接口或下一轮模型输入。

本期不保存历史引用，所以用户和助手历史项的 `citations` 均固定为空数组；它不表示
当时回答没有证据，只表示 MVP 不恢复引用。历史项不返回 ToolMessage、模型工具调用、
范围字段、内部状态或消息 ID。历史接口不分页且不设置响应条数上限，属于短会话 MVP 已知限制。

### 13.5 工具调用日志

`GET .../tool-calls` 复用既有 `AgentToolCallLogRead` 顶层形状，按 `created_at ASC`
返回。`tool_name` 只允许 `list_formal_archives` 或
`search_confirmed_archive_evidence`。安全摘要白名单如下：

| 工具 | `arguments_summary` | `result_summary` |
|---|---|---|
| `list_formal_archives` | `filter_names`、`page`、`page_size`；`filter_names` 只记录实际提交的业务筛选名，不记录筛选值 | `found`、`result_count` |
| `search_confirmed_archive_evidence` | `query_provided`、`query_length`；不记录查询原文 | `found`、`result_count` |

`filter_names` 元素只能是 `document_type`、`project_stage`、`document_date_from`、
`document_date_to`、`authoring_organization`；`page/page_size` 只记录实际生效的正整数。上述摘要之外不得返回或持久
查询文本、筛选值、文件名、登记字段值、摘录、回答、`user_id`、`project_id`、`kb_id`、
`document_id`、`chunk_id`、分数、Token、提示词或异常原文。

自动重试的耗时在同一 `tool_call_id` 下累加，且每个
`(agent_session_id, tool_call_id)` 最多一条日志。失败记录使用 `status=FAILED`、安全
`error_code`，并允许两个摘要为 `null`；禁止把 `str(exc)` 写入响应或日志摘要。已注册工具的
参数校验失败视为已实际发起，计入工具调用额度并写一条 `FAILED` 记录。`error_code` 只允许
`ARCHIVE_AGENT_TOOL_ARGUMENT_INVALID`、`ARCHIVE_AGENT_TOOL_CONNECTION_FAILED`、
`ARCHIVE_AGENT_TOOL_TIMEOUT` 或 `ARCHIVE_AGENT_TOOL_FAILED`；未注册工具、多 Tool Call 或第三次
调用在执行前由 Graph 拒绝，不伪造工具执行日志。日志接口不分页且不设置响应条数上限，属于
短会话 MVP 已知限制。

### 13.6 工具边界、重试与失败响应

两个工具不是公开 HTTP 端点，但其进入 ToolMessage 和 Checkpoint 的安全投影必须固定：

- `list_formal_archives` 只返回当前项目 `CONFIRMED` 且无可见性阻断的目录项。每项只含
  当前轮次临时 `document_ref`、`filename`、`confirmed_at`，以及 `TITLE`、
  `DOCUMENT_TYPE`、`DOCUMENT_DATE`、`AUTHORING_ORGANIZATION`、`PROJECT_STAGE`
  五个字段的 `value/source/has_source_evidence`。不含文档 UUID、并发版本、
  `VERSION_NUMBER`、`KEYWORDS` 或原文摘录。工具结果顶层同时保留实际 `page`、`page_size`、
  `total`，用于生成不误导的分页正文。`document_ref` 不进入最终 HTTP 响应，
  也不能被下一轮或证据工具作为资源 ID 使用。每次目录调用独立按结果顺序使用调用内
  `A1..A20`；该命名空间不传给证据判定层，也不同于判定层 Prompt 内部按证据文档分组的 `D` 编号。
- `search_confirmed_archive_evidence` 每次调用只把调用内 `S1..S8`、`filename`、可空
  `document_title`、`location_type`、`location_start`、`location_end`、`excerpt` 写入
  ToolMessage。`document_title` 只来自当前正式档案已确认的 `TITLE`，用于同一 `document_ref`
  的文档身份绑定；缺失时为 `null`，不得推断，也不得替代原文摘录证明其他事实。
  原始候选的 `document_id/chunk_id/score/reranker_score` 仅存在当前请求内存映射，
  不进入模型上下文、Checkpoint、HTTP 响应或工具日志。`document_title` 不进入当前 HTTP 引用 DTO
  或工具日志。每次证据调用固定只取 Top-8，
  每个 ToolMessage 的编号均从 `S1` 重新开始并由 `tool_call_id` 隔离；工具选择模型不负责生成
  最终 Citation。正常结束时公共判定层仅接收最后一次成功证据调用的原始候选，并基于同一顺序
  重新构造 `S1..S8`，因此不依赖此前 ToolMessage 的编号。

- 模型每次决策最多产生一个 Tool Call，每轮最多顺序执行两个。一次返回多个、
  调用未注册工具或尝试第三次时，不部分执行，统一返回
  `503 ARCHIVE_AGENT_MODEL_OUTPUT_INVALID`。
- 工具参数无效也占用一次调用额度。目录工具仅接受 FR-038 的五类筛选及
  `page/page_size`，`page_size` 最大 20；证据工具只接受规范化后 `1..2000` 码点的
  `query`，不接受 `top_k`、`document_ref` 或任何范围字段。服务端固定使用 Top-8。
- 模型和工具仅对连接失败或超时额外尝试一次。内部传输重试不增加模型工具调用计数，
  也不得重复追加用户/助手消息或工具日志。参数、权限、拒答和模型输出结构错误不自动重试。
- 模型、工具、Checkpoint 或 PostgreSQL 最终失败返回
  `503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`。该错误不含部件名、内部地址、异常正文、提示词或部分回答。
- 公共证据判定函数只返回结果或抛出不含 HTTP 错误码的中性失败；FR-039 入口继续映射为既有
  `ARCHIVE_ANSWER_UNAVAILABLE`，FR-042 入口映射为 `ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`。
  FR-042 的任何响应不得泄出 FR-039 的错误码。
- 初次模型决策最终失败时尚未产生可执行 Tool Call，因此不调用任何工具，直接返回
  `503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`。
- 最终 503 可能已产生一条脱敏 `FAILED` 工具日志，但不构成可见完整轮次。客户端主动重发
  会形成新轮次，本期不接受 `Idempotency-Key`。

### 13.7 项目删除联动

`DELETE /projects/{project_id}` 路径与成功响应保持不变。项目有任何未删除文档时仍先返回
`409 PROJECT_HAS_DOCUMENTS`。空项目删除时，服务必须按数据库与架构设计幂等清理其
ARCHIVE 会话 Checkpoint，再删除会话、工具日志和 Project；全部完成后才返回 `204`。

Checkpoint 或 PostgreSQL 联动失败返回 `503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`，不返回成功。
项目删除成功后，旧路径中的 `project_id` 返回 `404 PROJECT_NOT_FOUND`；即使后续又创建同名项目，
原 `session_id` 也不能恢复。KnowledgeBase 和 POLICY 会话不在该删除范围。

### 13.8 实现 Schema 边界与非目标

实施时在独立模块 `app/schemas/archive_agent.py` 定义：

- `ArchiveAgentSessionCreate`、`ArchiveAgentSessionRead`；
- `ArchiveAgentMessageCreate`、`ArchiveAgentMessageRead`；
- `ArchiveAgentCitationRead`、`ArchiveAgentResponse`。

`ArchiveAgentResponse` 字段集合固定为：

| 字段 | 类型与约束 |
|---|---|
| `session_id` | UUID；当前已验证的 ARCHIVE 会话 ID |
| `answer_status` | `ArchiveAnswerStatus` |
| `answer` | 非空字符串；符合 §13.3/§13.4 的可信最终投影 |
| `citations` | `list[ArchiveAgentCitationRead]`；目录与拒答为空，证据回答至少一条 |
| `request_id` | UUID；当前请求标识，与既有 `AgentResponse` 字段语义一致 |

不得增加 `user_id`、`project_id`、`kb_id`、`thread_id`、`agent_type`、内部工具结果或检索分数。

复用既有 `ArchiveAnswerStatus`、`EvidenceLocationType`、`MessageRole`、`AgentToolCallStatus` 和
`AgentToolCallLogRead`，但不复用要求客户端提交 `kb_id` 的 `AgentSessionCreate`、含制度引用的
`AgentResponse/AgentMessageRead`、或含持久化标识和分数的 `ArchiveRetrievalItemRead`。

本期不新增通用会话列表、任意旧会话详情或选择、重命名、用户删除、历史引用恢复、流式响应、
WebSocket、批量消息、跨项目会话迁移或面向客户端的工具直调接口。
