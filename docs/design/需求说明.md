标书解析生成或投标合规审查方向。

## 2. 项目背景

工程项目资料可能分散在不同文件和目录中，存在分类不统一、关键字段难查、
资料缺失难发现、重复文件难识别，以及检索结果缺少原文证据等问题。

本项目不是普通的“上传文件后聊天”，而是将工程项目资料整理为经过人工确认、
可以按结构化字段查询、能够追溯原文证据的正式档案。

## 3. 产品目标

第一版需要通过相邻 Vue 工作台演示以下最小业务闭环；Swagger/OpenAPI 用于逐接口诊断和验收：

```text
创建工程项目并选择演示清单
→ 上传项目资料并检查同项目重复
→ 手动解析文档
→ AI 给出分类、字段和证据建议
→ 用户检查、修改或手工补充
→ 人工确认正式入档
→ 人工确认档案与清单项的关联
→ 查看缺失资料
→ 在当前项目内进行结构化查询和带证据问答
→ 在持久化项目档案会话中查询正式目录或原文证据
```

目标达成的判断依据：

- 未确认资料不能进入正式检索和问答。
- AI 建议不会未经人工确认成为正式档案事实。
- 正式回答能够追溯到当前项目、当前文档的原文位置。
- 项目档案助手在跨轮对话中只能访问其创建时绑定项目的正式档案。
- 缺失结论只来自用户维护的清单及人工确认关联。
- 重复、失败、越权、并发冲突和无依据问题均有可验证结果。

## 4. 用户与使用场景

### 4.1 用户角色

第一版只有一种普通用户角色。同一用户完成项目创建、资料上传、整理、确认、
查询和删除，不拆分上传者、审核者或管理员。

系统提供账号密码注册和登录。注册用户使用全局唯一、统一小写的 `username` 作为登录标识，
`name` 仅为显示名称。所有受保护接口从 Bearer Access Token 获取当前用户；不再接受
`X-User-ID` 作为身份来源。所有项目和项目资源的读取、修改及删除都必须校验用户所有权。

虽然第一版通常由同一用户操作，系统仍需记录确认人和操作人，以便后续扩展。

### 4.2 典型场景

1. 用户为一个工程项目创建独立档案库。
2. 用户上传合同、设计、施工、会议纪要和验收资料。
3. 系统解析文本，AI 提出资料分类、字段和证据建议。
4. 用户逐字段检查，必要时修改或接受空值，然后确认入档。
5. 用户将档案与项目清单项建立人工确认关联。
6. 用户查看正式档案目录、缺失项和带原文证据的问答结果。
7. 用户在同一项目档案会话中先了解有哪些正式资料，再继续要求查找某项原文依据。

## 5. 第一版范围

### 5.1 本期实现

- 单用户角色下的工程项目创建、查询、修改和受限删除。
- 一个工程项目对应一个知识库，项目作为数据隔离边界。
- 文本型 PDF、DOCX、TXT、MD 上传和解析。
- 同一项目内基于文件哈希的完全重复判断。
- AI 分类、字段和原文证据建议，以及无 AI 时的纯手工归档。
- 字段人工检查、确认、取消确认和修改后重新确认。
- 项目清单维护、档案关联确认、缺失与未提供提示。
- 文档处理列表、正式档案目录、结构化筛选。
- 仅基于已确认档案的项目内检索和带证据问答。
- 持久化的项目档案助手：在正式目录导航与正式原文证据检索之间选择只读工具。
- 文档物理删除、跨存储清理、缺失结果重算和脱敏审计。
- AI 质量与检索问答质量的固定验收集。
- P14 将 `mini-rag-milvus-vue` 作为本地联调界面：只通过 FastAPI 的 `/api` 代理调用，并以真实后端响应展示，不新增客户端身份或资源授权后门。

### 5.2 本期不实现

- 扫描 PDF、OCR、图片理解和所有 Excel 文件。
- 跨项目检索、跨项目问答和企业公共资料库。
- 上传者、审核者、管理员等多角色体系。
- 企业级 SSO、OAuth 第三方登录、多角色权限体系和账号找回流程。
- 用户自定义清单模板的保存、复用、权限和版本管理。
- 文件名或内容相似度的疑似重复判断。
- 档案完整版本管理、软删除、恢复和项目一键级联删除全部文档。
- 公开部署的多用户前端、多 Agent、复杂审批流、第三方系统对接。

- 知识图谱构建、实体/关系抽取、图谱存储、图谱可视化和图谱查询。这些属于业务

- AI 在没有清单或规则来源时自行判断项目资料是否齐全。

P14 的相邻 Vue 工作台只承担本地联调与验收，不改变单用户角色、后端服务端授权和非公开部署边界。

### FR-019 账号注册与旧用户凭据初始化

#### 功能目标

用户可以使用全局唯一的 `username`、显示名称和密码创建账号。现有无凭据用户的数据记录
保留，但不能通过登录获得访问权限；仅允许受控本地命令为指定旧用户初始化用户名和密码。

#### 业务规则

- `username` 统一转换为小写后校验全局唯一；仅允许 3～50 位小写字母、数字、`_` 和 `-`。
- `name` 为显示名，不是登录标识；密码长度为 8～128 个字符。
- 系统只保存密码哈希，不保存、记录或返回明文密码。
- 公开的模拟用户创建接口 `/users` 在本需求实施后移除。

#### 验收标准

- **AC-FR-019-01**：Given 未被占用的用户名，When 用户提交合法注册信息，Then 创建可登录用户，
  响应不包含密码或密码哈希。
- **AC-FR-019-02**：Given 大小写不同但规范化后相同的用户名，When 注册，Then 返回稳定冲突，
  不创建第二个用户。
- **AC-FR-019-03**：Given 迁移前的旧用户，When 尝试登录，Then 返回通用认证失败，不泄露其
  是否存在或缺少凭据。

### FR-020 账号密码登录与 Token 刷新

#### 功能目标

用户可以以用户名和密码登录，获得用于访问 API 的 Access Token 与用于续期的 Refresh Token。

#### 业务规则

- Access Token 的有效期为 30 分钟；Refresh Token 的有效期为 7 天，二者携带不同用途声明。
- 登录创建一条认证会话；PostgreSQL 只保存 Refresh Token 的单向哈希、有效期与撤销状态。
- 刷新接口仅接受有效的 Refresh Token，且只签发新的 Access Token；在 Refresh Token 有效且
  未撤销期间不轮换 Refresh Token。
- 用户名不存在、密码错误、过期或无效 Token 均返回不泄露账号状态的稳定认证错误。

#### 验收标准

- **AC-FR-020-01**：Given 合法账号密码，When 登录，Then 返回不同用途的 Access/Refresh Token，
  数据库不保存明文 Token。
- **AC-FR-020-02**：Given 有效 Refresh Token，When 刷新，Then 仅返回新的 Access Token；使用
  Access Token 调用刷新接口被拒绝。
- **AC-FR-020-03**：Given 错误密码或不存在的用户名，When 登录，Then 返回相同的通用认证失败响应。

### FR-021 Bearer 身份认证与注销

#### 功能目标

受保护接口仅使用已验证的 Bearer Access Token 识别当前用户；用户可以注销当前认证会话。

#### 业务规则

- 认证后服务从 Access Token 的已验证用户与会话声明注入当前用户，不信任客户端 `X-User-ID`。
- 注销撤销当前 Access Token 对应认证会话；已撤销会话的 Refresh Token 不能再次刷新。
- 业务资源仍按已验证用户执行原有所有权校验；认证替换身份来源，不放宽资源授权。

#### 验收标准

- **AC-FR-021-01**：Given 有效 Access Token，When 调用受保护接口，Then 仅返回该 Token 用户的资源。
- **AC-FR-021-02**：Given 缺失、过期、伪造或 Refresh 类型 Token，When 调用受保护接口，Then 返回 401，
  且 `X-User-ID` 不能绕过认证。
- **AC-FR-021-03**：Given 已登录用户，When 注销并使用原 Refresh Token 刷新，Then 请求被拒绝。

## 7. 核心业务对象和字典

### 7.1 项目与资料归属

- 一个工程项目对应一个知识库。
- 项目是文档、向量、档案字段、清单、关联、重复判断和问答的隔离边界。
- 第一版不支持跨项目查询。

### 7.2 资料分类

```text
合同资料
设计资料
施工资料
会议纪要
验收资料
其他资料
```

“其他资料”是兜底分类。“制度模板”不进入第一版，因为它属于企业公共资料，
会引入另一套归属和权限规则。

### 7.3 项目阶段

```text
前期准备
设计阶段
施工阶段
验收阶段
跨阶段
其他阶段
```

AI 和用户都只能使用上述固定值，不能创建新的阶段名称。

### 7.4 正式档案字段

| 字段 | 是否必须非空 | 来源 | 确认要求 |
|---|---:|---|---|
| 资料标题 | 是 | AI 建议或人工填写 | 必须人工检查 |
| 资料类型 | 是 | AI 建议或人工选择 | 必须人工检查 |
| 文档日期 | 否 | AI 建议或人工填写 | 有值或明确接受为空 |
| 编制单位 | 否 | AI 建议或人工填写 | 有值或明确接受为空 |
| 版本号 | 否 | AI 建议或人工填写 | 有值或明确接受为空 |
| 项目阶段 | 否 | AI 建议或人工选择 | 有值或明确接受为空 |
| 关键词 | 否 | AI 建议或人工填写 | 有值或明确接受为空 |

项目 ID、原文件名、文件哈希和上传时间由系统生成，不属于 AI 提取字段。原文件名
不能冒充资料标题或 AI 提取结果。

字段语义规则：资料类型为合同资料（`CONTRACT`）时，`DOCUMENT_DATE` 表示合同签订日期；
其他资料类型的 `DOCUMENT_DATE` 表示该文档自身日期。字段名保持统一为
`DOCUMENT_DATE`，不因资料类型重命名；目录日期筛选也按该字段的上述业务语义执行。

字段检查状态独立于字段值，业务语义至少区分：

```text
待检查
有值且已确认
接受为空
```

具体 API/数据库枚举名称在后续设计中确定，不在需求阶段自行固定。

### 7.5 文档状态

| 状态 | 含义 |
|---|---|
| `UPLOADED` | 已上传，尚未解析 |
| `PARSE_FAILED` | 解析失败 |
| `PARSED` | 解析完成，尚未生成建议 |
| `SUGGESTION_FAILED` | 建议生成失败 |
| `PENDING_CONFIRMATION` | 已生成 AI 草稿，或已通过“开始人工草稿”动作创建空白草稿，待人工确认 |
| `CONFIRMED` | 已正式入档 |
| `PENDING_RECONFIRMATION` | 修改后待重新确认 |

删除是操作结果，不保留为用户可见状态。删除请求一旦受理，服务端即建立可见性阻断；
在跨存储清理完成前，该文档不得进入正式目录、检索、问答或项目档案助手工具。删除失败时
保留失败操作与可见性阻断，不自动恢复正式可见性；用户重试并完成物理删除后清理该文档。

与人工草稿相关的允许转换如下：

| 起始状态 | 明确动作 | 目标状态 | 结果 |
|---|---|---|---|
| `PARSED` | 开始人工草稿 | `PENDING_CONFIRMATION` | 创建七个字段均为“待检查”的空白草稿 |
| `SUGGESTION_FAILED` | 开始人工草稿 | `PENDING_CONFIRMATION` | 保留解析结果，创建空白草稿 |
| `PARSED` | AI 建议成功 | `PENDING_CONFIRMATION` | 保存 AI 建议字段和证据草稿 |
| `SUGGESTION_FAILED` | 重试 AI 建议成功 | `PENDING_CONFIRMATION` | 保存新的 AI 建议字段和证据草稿 |
| `PENDING_CONFIRMATION` | 重新生成 AI 建议 | `PENDING_CONFIRMATION` | 仅未发生人工编辑时，以新的 AI 草稿原子替换现有草稿 |

### 7.6 字段证据

每条证据至少包含原文摘录、定位类型和定位值，定位值从 1 开始计数：

| 文件类型 | 定位方式 |
|---|---|
| PDF | 页码 |
| DOCX | 段落序号 |
| TXT、MD | 行号范围 |

同一字段可以关联多条证据。AI 建议的非空字段必须有证据。人工填写或更正可以
没有证据，但必须标记为人工来源和“无原文证据”。

## 8. 功能需求

### FR-030 工程项目管理

#### 功能目标

用户可以创建、列出、查看和修改自己的工程项目，并在符合条件时删除空项目。

#### 前置条件与输入

- 请求携带有效 Bearer Access Token，且其 `sub` 对应真实存在的用户。
- 创建输入：项目名称、可选项目说明、是否使用演示清单模板。
- 修改输入：项目名称或项目说明，以及并发校验版本。

#### 正常流程

1. 系统去除项目名称首尾空格。
2. 系统校验同一用户范围内名称唯一。
3. 系统创建项目 ID、创建人和创建时间。
4. 用户选择演示模板时，系统复制独立的项目清单。
5. 用户可以查询和修改自己的项目。
6. 项目没有任何未删除文档记录时，用户可以删除项目及项目清单。
7. 删除项目不删除其绑定的内部知识库；旧知识库接口与项目生命周期解耦，避免误删旧资料。

#### 异常与边界

- 无效用户、项目不存在或越权时返回稳定业务错误。
- 同一用户名称重复或旧版本修改时返回业务冲突。
- 项目存在任意文档状态的记录时禁止删除。
- 不支持删除项目时级联删除全部文档。

#### 验收标准

- **AC-FR-030-01**：Given 用户不存在同名项目，When 创建项目并选择演示模板，
  Then 创建成功且获得独立项目清单。
- **AC-FR-030-02**：Given 同一用户已有去除首尾空格后的同名项目，When 再次
  创建或重命名，Then 返回业务冲突。
- **AC-FR-030-03**：Given 项目存在任意未删除文档，When 删除项目，Then 删除
  被拒绝且原有资源不变。
- **AC-FR-030-04**：Given 另一用户的项目，When 当前用户读取、修改或删除，
  Then 请求被拒绝且不泄露项目数据。

### FR-031 项目清单管理

#### 功能目标

用户可以使用固定演示模板初始化项目清单，并维护项目自己的清单项。

#### 前置条件与输入

- 当前用户拥有目标项目。
- 清单项输入至少包含名称、资料类型、是否必需、项目阶段和说明。
- 修改请求携带并发校验版本。

#### 正常流程

1. 系统可从唯一的内置演示模板复制项目清单。
2. 用户可通过 API 新增、修改和删除项目清单项。
3. 必需项未满足时显示“缺失”；可选项未满足时显示“未提供”。
4. 必需或可选属性变化后立即重新计算结果。

#### 异常与边界

- 第一版不支持创建、保存或复用用户自定义模板。
- 修改名称、资料类型或阶段会使已有档案关联失效。
- 只修改说明不影响已有确认关联。
- 旧版本更新返回业务冲突，不能覆盖新修改。

#### 验收标准

- **AC-FR-031-01**：Given 新项目选择演示模板，When 项目创建完成，Then 项目
  获得五个独立清单项，后续修改不影响系统模板或其他项目。
- **AC-FR-031-02**：Given 必需项没有已确认关联，When 查询清单，Then 显示
  “缺失”；可选项显示“未提供”且不计入缺失数量。
- **AC-FR-031-03**：Given 清单项已有确认关联，When 修改名称、资料类型或阶段，
  Then 关联失效并按必需属性重新计算结果。

### FR-032 文档上传与重复校验

#### 功能目标

用户可以向自己的项目上传受支持文件，系统在保存前完成容量和同项目重复校验。

#### 前置条件与输入

- 当前用户拥有目标项目。
- 支持扩展名为 PDF、DOCX、TXT、MD。
- 单文件不超过 20 MB；项目未删除文档记录少于 100 份。

#### 正常流程

1. 系统先校验所有权、文件类型、大小和项目文档数量。
2. 系统计算文件哈希，并仅在当前项目内检查重复。
3. 校验通过后保存原文件并创建 `UPLOADED` 文档记录。
4. 上传不自动解析，也不调用 AI。

#### 异常与边界

- 超过大小或数量限制时，不保存文件、不创建记录。
- 同项目相同哈希返回冲突及已有文档的标识、名称和状态。
- 重复时不得创建文件、文档、档案或向量。
- 不同项目允许相同哈希，且不得互相泄露文件信息。
- 已有重复文档解析失败时，引导重试原记录。

#### 验收标准

- **AC-FR-032-01**：Given 合法且不重复的 TXT 文件，When 上传，Then 原文件和
  `UPLOADED` 记录被创建，但没有解析结果或 AI 调用。
- **AC-FR-032-02**：Given 当前项目已有同哈希文件，When 再次上传，Then 返回
  已有文档摘要且不产生任何重复数据。
- **AC-FR-032-03**：Given 另一项目存在相同哈希，When 上传到当前项目，Then
  上传可以成功且响应不包含另一项目信息。
- **AC-FR-032-04**：Given 文件超过 20 MB 或项目已有 100 份文档，When 上传，
  Then 请求在保存前被拒绝。

### FR-033 文档解析与重试

#### 功能目标

用户可以显式触发文档解析，并对失败记录执行明确的重新解析。

#### 前置条件与输入

- 普通解析只允许从 `UPLOADED` 执行。
- 重新解析只允许从 `PARSE_FAILED` 通过专用重试操作执行。

#### 正常流程

1. 系统提取文本，并生成 PDF 页码、DOCX 段落序号或 TXT/MD 行号定位。
2. 提取到有效文本后状态变为 `PARSED`。
3. 解析失败时保留原记录、失败分类和可重试信息。
4. 用户可以对原记录重试，不需要重新上传。

#### 异常与边界

- 扫描 PDF 或无法提取有效文本的 PDF 不得标记成功，应提示“暂不支持扫描件，
  请上传文本版资料”。
- 已解析文档再次调用普通解析时不得重复写入结果。
- 解析失败不自动重试。
- 重试不得产生重复解析结果或向量。

#### 验收标准

- **AC-FR-033-01**：Given 文本型 PDF，When 解析成功，Then 状态为 `PARSED`
  且文本能够按从 1 开始的页码定位。
- **AC-FR-033-02**：Given 扫描 PDF 无有效文本，When 解析，Then 状态为
  `PARSE_FAILED`，返回稳定提示且不生成 AI 建议。
- **AC-FR-033-03**：Given 已解析文档，When 再次调用普通解析，Then 结果保持
  幂等且不重复写入。

### FR-034 AI 分类、字段与证据建议

#### 功能目标

用户可以在解析完成后显式请求 AI 生成资料分类、档案字段和原文证据草稿。

#### 前置条件与输入

- 首次建议的文档状态为 `PARSED`，失败后的专用重试状态为 `SUGGESTION_FAILED`。
- 重新生成建议只允许状态为 `PENDING_CONFIRMATION`，且当前七个字段均为
  `PENDING_CHECK`、不存在人工来源字段或人工证据修改。
- DeepSeek 已配置且启用。
- 输入只能来自当前项目的当前文档。

#### 正常流程

1. 系统将必要的当前文档片段发送给 DeepSeek。
2. AI 只能从固定资料类型和项目阶段字典中选择。
3. AI 为非空字段返回一条或多条当前文档证据。
4. 建议成功后状态变为 `PENDING_CONFIRMATION`。
5. AI 建议只保存为草稿，不成为正式档案事实。
6. 用户可对尚未人工编辑的草稿显式请求“重新生成 AI 建议”；系统先生成并校验完整
   新草稿，再原子替换原 AI 草稿，状态保持 `PENDING_CONFIRMATION`。

#### 异常与边界

- 原文无依据时字段值必须为空，不能猜测。
- 模型概括关键词也必须关联摘录；否则只能作为非正式检索辅助标签。
- 连接失败或超时只自动重试一次；模型格式错误不自动重试。
- 失败后状态为 `SUGGESTION_FAILED`，用户可重试建议，或调用独立的“开始人工
  草稿”动作转为手工填写。
- 重新生成不得静默覆盖用户已编辑草稿；存在人工字段或人工证据修改时必须拒绝，原草稿
  保持不变。
- 重新生成过程中模型不可用或输出不合格时，不得丢弃现有草稿、不得转为
  `SUGGESTION_FAILED`。

#### 验收标准

- **AC-FR-034-01**：Given 已解析文档且模型可用，When 生成建议，Then 获得固定
  字典内的分类、字段草稿和当前文档证据。
- **AC-FR-034-02**：Given 原文缺少编制单位，When 生成建议，Then 该字段为空，
  不得生成推测值。
- **AC-FR-034-03**：Given 状态为 `PENDING_CONFIRMATION` 且草稿尚未人工编辑，When
  用户请求重新生成建议，Then 系统以新的、已校验证据的 AI 草稿替换原 AI 草稿，状态保持
  不变并记录一次脱敏审计。
- **AC-FR-034-04**：Given 用户已编辑字段或字段证据，When 请求重新生成建议，Then
  系统返回业务冲突，原草稿保持不变且不得静默覆盖人工内容。

### FR-035 人工草稿启动、字段草稿编辑与人工检查

#### 功能目标

用户可以查看、修改或完全手工填写七个正式字段，并逐项记录检查结果。

#### 前置条件与输入

- “开始人工草稿”只允许状态为 `PARSED` 或 `SUGGESTION_FAILED` 的文档执行。
- 字段编辑允许状态为 `PENDING_CONFIRMATION` 或 `PENDING_RECONFIRMATION` 的文档执行。
- 字段输入包含值、来源、证据、检查状态和并发校验版本。

#### 正常流程

1. 用户可对 `PARSED` 或 `SUGGESTION_FAILED` 文档调用独立的“开始人工草稿”动作。
2. 系统创建七个字段均为“待检查”、无 AI 值和无证据的空白草稿，并将状态更新为
   `PENDING_CONFIRMATION`。
3. 用户查看 AI 建议草稿或空白草稿。
4. 用户确认有值字段，或对允许为空字段明确选择“接受为空”。
5. 用户可以修改 AI 值、证据或完全手工填写。
6. 人工无证据值标记为人工来源和“无原文证据”。
7. 系统记录修改人、时间、前后摘要；操作原因可选填。
8. 用户对尚未编辑的空白人工草稿可改为请求 AI 重新生成建议；一旦保存任一人工字段或
   人工证据修改，则该动作不再允许。

#### 异常与边界

- 资料标题和资料类型不得为空。
- 资料标题不能用原文件名自动冒充。
- 七个字段中仍有“待检查”状态时不得正式入档。
- 未开始 AI 或人工草稿的 `PARSED/SUGGESTION_FAILED` 文档不得直接编辑正式字段；
  系统应提示先执行“开始人工草稿”动作。
- 客户端提交旧版本草稿时返回业务冲突。

#### 验收标准

- **AC-FR-035-01**：Given 状态为 `PARSED` 的文档，When 用户执行“开始人工草稿”，
  Then 系统创建七个字段均为待检查的空白草稿，并将文档变为 `PENDING_CONFIRMATION`。
- **AC-FR-035-02**：Given 状态为 `SUGGESTION_FAILED` 的文档，When 用户执行“开始
  人工草稿”，Then 系统保留解析结果，创建空白草稿并进入 `PENDING_CONFIRMATION`。
- **AC-FR-035-03**：Given AI 不可用但解析成功，When 用户开始人工草稿、手工填写
  标题和类型、检查其他字段并接受必要空值，Then 文档具备确认条件。
- **AC-FR-035-04**：Given 任一字段仍待检查，When 用户请求确认，Then 确认被拒绝。
- **AC-FR-035-05**：Given 人工填写字段无原文证据，When 保存，Then 来源和无证据
  状态清晰可见，且不伪装为 AI 或原文事实。

### FR-036 正式入档、取消确认与重新确认

#### 功能目标

用户通过明确确认使文档成为正式档案，并在正式数据变化后重新确认。

#### 前置条件与输入

- 资料标题和资料类型非空。
- 七个正式字段均已人工检查。
- 请求携带当前版本。

#### 正常流程

1. 用户确认后，状态变为 `CONFIRMED`。
2. 系统记录确认人和确认时间，并将档案纳入正式检索范围。
3. 修改任一正式字段或字段证据后，状态变为 `PENDING_RECONFIRMATION`。
4. 待重新确认期间，档案退出正式检索和问答。
5. 用户再次确认后恢复 `CONFIRMED`。

#### 异常与边界

- AI 建议成功不是入档前提，人工检查才是前提。
- 内容未变化时重复确认保持幂等，不重复记录成功结果。
- 取消确认后应退出正式范围并重新计算清单结果。
- 第一版不保存完整档案版本，只保留脱敏修改摘要和确认记录。

#### 验收标准

- **AC-FR-036-01**：Given 所有字段已检查且必填字段非空，When 用户确认，Then
  档案状态为 `CONFIRMED` 并记录确认人和时间。
- **AC-FR-036-02**：Given 已确认档案，When 修改字段或证据，Then 状态变为
  `PENDING_RECONFIRMATION` 且立即退出正式问答。
- **AC-FR-036-03**：Given 内容未变化的已确认档案，When 重复确认，Then 结果
  不变且不产生重复成功审计。

### FR-037 档案—清单关联与缺失计算

#### 功能目标

系统提出关联建议，由用户确认档案与清单项的多对多关系，并据此计算缺失。

#### 前置条件与输入

- 档案已处于 `CONFIRMED`。
- 清单项属于同一项目。
- 关联确认请求携带当前版本。

#### 正常流程

1. 系统可以依据资料类型和项目阶段提出匹配建议。
2. 用户确认或拒绝建议，也可以主动建立关联。
3. 只有已确认档案和已确认关联共同存在时，清单项才被满足。
4. 一个清单项可关联多份档案，一份档案可关联多个清单项。
5. 删除档案、取消档案确认或删除关联后立即重算。

#### 异常与边界

- 档案存在但关联未确认时，清单项仍为“缺失”或“未提供”。
- 系统不得只凭资料类型或项目阶段自动判定满足。
- 项目没有清单时不输出缺失结论。
- 不允许跨项目建立关联。

#### 验收标准

- **AC-FR-037-01**：Given 已确认施工方案但未确认清单关联，When 查询清单，
  Then “施工方案”仍显示缺失。
- **AC-FR-037-02**：Given 用户确认同项目档案与必需项关联，When 查询清单，
  Then 该项显示已满足。
- **AC-FR-037-03**：Given 已满足清单项，When 档案取消确认或关联被删除，
  Then 立即恢复为“缺失”或“未提供”。
- **AC-FR-037-04**：Given 另一项目的档案，When 尝试建立关联，Then 请求被拒绝
  且不泄露档案信息。

### FR-038 文档处理列表与正式档案目录

#### 功能目标

用户可以分别查看处理工作队列和正式档案目录。

#### 前置条件与输入

- 当前用户拥有目标项目。
- 正式目录筛选条件包括资料类型、项目阶段、文档日期和编制单位。

#### 正常流程

1. 文档处理列表返回所有未删除文档及其处理状态。
2. 正式档案目录只返回 `CONFIRMED` 档案。
3. 正式目录默认按确认时间倒序。
4. 文档日期支持空值筛选和指定日期区间。
5. 查询直接访问结构化档案数据，不调用大模型。

#### 异常与边界

- 已删除记录不出现在两个列表中。
- 待确认和待重新确认文档不出现在正式档案目录中。
- 所有列表均受项目所有权和分页约束。

#### 验收标准

- **AC-FR-038-01**：Given 项目同时存在失败、待确认和已确认文档，When 查询处理
  列表，Then 返回全部未删除状态；查询正式目录只返回已确认档案。
- **AC-FR-038-02**：Given 多份已确认档案，When 按阶段和日期区间筛选，Then
  只返回匹配记录并按确认时间倒序。
- **AC-FR-038-03**：Given 用户筛选文档日期为空，When 查询，Then 仅返回已确认
  且文档日期为空的档案。
- **AC-FR-038-04**：Given 资料类型为合同资料，When 读取或筛选
  `DOCUMENT_DATE`，Then 该值按合同签订日期解释；Given 其他资料类型，Then
  该值按文档自身日期解释。

### FR-039 项目内检索与带证据问答

#### 功能目标

用户可以在当前项目的正式档案中检索原文，并获得带来源证据的回答。

#### 前置条件与输入

- 当前用户拥有目标项目。
- DeepSeek 问答需要模型已配置并启用。
- 检索范围只能包含当前项目的 `CONFIRMED` 档案。

#### 正常流程

1. 系统使用用户 ID 与项目 ID 限定 Chroma 检索范围。
2. 检索只返回正式档案的原文片段。
3. 有充分依据时，DeepSeek 仅依据检索结果回答。
4. 回答返回文件、页码或文本位置和原文摘录。
5. 结构化字段筛选通过正式档案目录完成，不调用模型。

#### 异常与边界

- 无充分依据时明确拒答。
- 待确认和待重新确认档案不得参与。
- 人工录入且无证据字段不得作为问答依据。
- 模型关闭时问答不可用，但目录、筛选和缺失计算仍可用。
- 不得泄露其他项目内容。

#### 验收标准

- **AC-FR-039-01**：Given 当前项目有已确认依据，When 用户提问，Then 回答仅使用
  当前项目原文并返回正确引用。
- **AC-FR-039-02**：Given 当前项目没有依据，When 用户提问，Then 系统拒答且
  不生成伪造引用。
- **AC-FR-039-03**：Given 依据只存在于待确认档案，When 用户提问，Then 系统
  不得使用该依据。
- **AC-FR-039-04**：Given 依据只存在于其他项目，When 用户提问，Then 系统
  不得返回或暗示其他项目内容。
- **AC-FR-039-05**：Given 当前项目已确认的合同资料，其 `DOCUMENT_DATE` 有原文证据，
  When 用户询问合同签订日期，Then 系统按该字段语义回答，并返回该合同的正确引用。

### FR-040 文档与档案删除

#### 功能目标

用户可以物理删除自己项目中的文档，并同步清理正式档案、文件、向量和关联。

#### 前置条件与输入

- 当前用户拥有目标项目和文档。
- 删除请求明确指定项目和文档。

#### 正常流程

1. 系统先将文档移出正式检索与问答范围。
2. 系统删除当前项目、当前文档对应的 Chroma 向量。
3. 系统删除原始文件、业务文档、档案字段、证据和清单关联。
4. 系统重新计算项目清单结果。
5. 系统只保留脱敏删除审计。

#### 异常与边界

- 不保留软删除记录、原文、完整字段或可恢复副本。
- 跨存储清理失败不得静默标记全部成功。
- 删除范围必须同时包含用户、项目和文档标识。
- 越权删除不得泄露目标文档信息。

#### 验收标准

- **AC-FR-040-01**：Given 已确认档案满足必需清单项，When 删除文档，Then 原文件、
  向量、档案和关联被清理，清单重新显示缺失。
- **AC-FR-040-02**：Given 删除过程中外部存储失败，When 操作结束，Then 系统
  返回稳定失败结果且不虚假宣称全部删除成功。
- **AC-FR-040-03**：Given 另一用户项目中的文档，When 当前用户删除，Then 请求
  被拒绝且目标数据不变。

### FR-041 业务审计查询

#### 功能目标

系统记录关键写操作，并允许用户通过 Swagger 查询自己项目的脱敏审计记录。

#### 审计范围

- 档案确认与取消确认。
- 正式字段人工填写或修改。
- 清单项增删改。
- 档案与清单项关联确认和删除。
- 手动重试解析或 AI 建议。
- 对尚未人工编辑草稿重新生成 AI 建议。
- 文档删除。

查询、列表和普通证据问答不写业务操作审计。

#### 正常流程

1. 成功业务操作写入一次审计。
2. 手动重试可以写一次操作审计，网络自动重试不得重复成功记录。
3. 用户按时间倒序、分页查询自己项目的记录。
4. 返回操作类型、操作人、时间、资源标识和脱敏摘要。

#### 异常与边界

- 不返回原文、完整档案字段、模型提示词、模型输入输出、Token 或内部堆栈。
- 第一版不提供审计删除和保留期限配置。
- 用户不能查询其他项目的审计。

#### 验收标准

- **AC-FR-041-01**：Given 用户完成档案确认，When 查询项目审计，Then 返回一条
  包含操作人和时间的脱敏记录。
- **AC-FR-041-02**：Given 连接超时触发一次自动重试并最终成功，When 查询审计，
  Then 同一成功结果只记录一次。
- **AC-FR-041-03**：Given 另一用户项目的审计，When 当前用户查询，Then 请求
  被拒绝且不泄露摘要。

### FR-042 项目档案助手

#### 功能目标

本文统一使用“项目档案助手”表示该 Agent，使用“项目档案助手会话”表示其持久化会话。
用户可以在自己项目的持久化项目档案助手会话中连续提问。项目档案助手根据问题在“正式档案目录”与
“正式原文证据检索”两个只读工具之间选择，并在涉及档案原文事实时返回可追溯引用。
该能力补充而不替代 FR-039 的单次直接问答。

本期目标是完成可在本地 Vue 工作台和 Swagger 演示的最小闭环，不为极少发生的跨存储故障提前
引入生产级事务协调、轮次业务表或分布式超时预算。隔离、正式档案范围、证据引用和无依据拒答
仍是不可降级的安全边界。

#### 前置条件与输入

- 当前用户拥有目标项目；创建会话时，服务端从项目上下文确定并固定该会话的
  `user_id`、`project_id`、`kb_id` 与 `thread_id`。
- 会话消息先将 `CRLF` 和单独 `CR` 规范化为 `LF`，再去除首尾 Unicode 空白；规范化后的
  Python 字符串按 Unicode 码点计数必须为 1～2000，每个 `LF` 计一个码点。空字符串、纯空白
  或超长消息统一作为请求参数错误拒绝。
- 创建会话和发送消息的请求体不接受 `user_id`、`project_id`、`kb_id`、`thread_id` 或
  会话类型等服务端范围字段；客户端提交任何未声明字段时返回参数错误，不能静默忽略。
- DeepSeek 可用时才执行模型判断和回答；正式目录、FR-039 直接问答与其他归档能力的
  既有可用性边界保持不变。
- FR-042 复用现有 SQLite Checkpoint 机制保存可序列化对话状态；档案业务事实仍以 PostgreSQL、
  文件系统和 Chroma 为准，FR-039 仍保持非 Agent 的直接问答入口。

#### 正常流程

1. 用户在项目范围内创建项目档案助手会话，服务端保存该会话的项目绑定、受控会话类型和
   稳定 Graph 线程标识。
2. 用户发送消息后，系统先校验当前用户、目标项目与会话绑定完全一致。
3. 模型每次决策最多选择一个只读工具，单轮最多实际发起两个工具调用：
   - `list_formal_archives`：筛选条件只允许 FR-038 的资料类型、项目阶段、文档日期区间和
     编制单位，以及 `page` 与 `page_size`；默认每页 20 条，单次最多 20 条；
   - `search_confirmed_archive_evidence`：模型只提交去除首尾空白后 1～2000 个 Unicode
     码点的查询词；候选数量由服务端固定为 D6 Top-8，模型不得覆盖。候选可携带当前正式档案
     已人工确认的可空 `document_title`，只用于把问题中的文档称呼绑定到同一 `document_ref`。
4. 目录导航类结论只基于目录工具返回的正式档案摘要；涉及文档内容、日期、单位或其他
   原文事实的回答必须基于原文证据工具的服务端引用映射。
5. 目录工具仅返回本次调用的临时 `document_ref`、文件名、确认时间，以及 `TITLE`、
   `DOCUMENT_TYPE`、`DOCUMENT_DATE`、`AUTHORING_ORGANIZATION`、`PROJECT_STAGE` 五个目录字段；
   每个目录字段均包含 `value`、`source` 与 `has_source_evidence`。不返回 `VERSION_NUMBER`、
   `KEYWORDS`、并发版本、持久化文档 UUID 或原文证据正文。项目档案助手陈述目录字段时必须
   表述为“已确认登记信息”，不得将人工无证据字段表述为原文事实。
6. `document_ref` 只用于本轮目录结果，不是持久化资源标识，证据工具不得接收它。后续追问使用
   已见文件名或登记信息重新组织自然语言查询，并重新执行当前正式范围校验。
7. 参数无效的工具调用也计入单轮两个调用上限；模型可在剩余额度内修正一次。模型若一次返回
   多个 Tool Call，则本轮以稳定错误结束，不执行该批调用。连接失败或超时最多额外尝试一次，
   不能借重试增加工具调用预算或无限循环。
8. SQLite Checkpoint 保存跨轮消息；历史接口只展示完整的用户/助手消息，不展示 ToolMessage。
   每次实际工具调用在 PostgreSQL 写入脱敏摘要、状态和耗时。MVP 不新增 AgentTurn 或
   AgentTurnCitation 表，也不承诺恢复历史回答的引用；当前消息响应仍必须返回完整引用。
9. 成功响应的 `answer_status` 复用 `ArchiveAnswerStatus`：目录回答和有据回答均为 `ANSWERED`，
   无依据拒答为 `REFUSED_NO_EVIDENCE`。`CATALOG` 仅是 Graph 内部路由状态，不新增公开状态枚举。

#### 异常与边界

- 会话不属于当前用户、项目不一致或试图借会话访问其他项目时，系统拒绝请求且不泄露
  会话、项目、档案或检索结果。
- 历史制度 Agent 会话使用 `POLICY` 类型；项目档案助手入口必须拒绝 `POLICY` 会话，不提供反向制度 Agent 入口。
- 待确认、待重新确认、已删除或正处于可见性阻断删除中的档案不得出现在目录工具、
  原文工具或助手回答中。
- 原文工具返回空候选时，系统直接返回固定拒答和空引用；存在候选时，证据充分性与回答
  沿用 P14-D5 的单次结构化判定层及 D6 的文档绑定、Top-8 候选和服务端引用编号映射，
  不使用统一 Reranker 阈值决定拒答。目录为空时只可说明当前项目没有可见的正式档案。
- 模型没有调用本轮目录工具时不得陈述目录登记结果；没有调用本轮证据工具或工具没有返回充分
  证据时不得陈述档案原文事实，必须按无依据拒答处理。
- 正常完成时只由最后一次成功工具调用决定最终回答：目录调用使用该次安全结果的确定性目录投影，
  证据调用只把该次原始 Top-8 交给 D5/D6 判定层；更早的工具结果仅可辅助选择下一工具或调整查询，
  不得进入最终正文或引用。本轮没有任何成功工具调用时，一律返回固定无依据拒答，不提供普通自由回答。
- 工具业务结果为空不属于基础设施失败；工具、模型或 Checkpoint 发生连接、超时或内部失败时，
  返回稳定 `503`，禁止模型根据失败文本或旧知识猜测答案。客户端不得收到原始异常、提示词、
  完整原文、Token 或模型隐藏推理。
- 连接失败或超时最多自动重试一次。同一 HTTP 请求内的自动重试不得重复追加用户或助手可见
  消息，不得重复写工具调用审计，同一模型 `tool_call_id` 在同一会话中最多对应一条日志。
  客户端主动重发请求在本期视为新一轮消息，不提供 `Idempotency-Key`。
- 自动重试不得重复追加用户可见消息或工具审计；客户端主动重发仍视为新一轮。本期不承诺把
  基础设施失败保存成完整对话轮次，也不解决 SQLite 与 PostgreSQL 无法原子提交的极端窗口。
  历史接口与后续模型输入使用同一完整轮次投影：从一次 HumanMessage 开始，跳过其中间
  AI Tool Call 与 ToolMessage，只有随后存在最终 AIMessage 时才形成可见轮次；遇到下一条
  HumanMessage 前仍没有最终 AIMessage 的轮次一律忽略。最终 AIMessage 正文必须与用户收到的
  `answer` 完全一致，工具选择循环的自由文本不得进入 Checkpoint。该限制必须在 README 和验收报告中声明。
- 项目只有在没有未删除文档时才可删除。项目删除成功前必须一并删除其项目档案助手会话、
  对应 SQLite Checkpoint 线程和脱敏工具调用记录；任一层清理失败时不得宣称项目删除成功。
  删除成功后，旧会话标识再次访问统一按资源不存在处理。本地单实例 MVP 不承诺消息执行与
  项目删除并发时的强一致性；演示和验收不得并发执行这两个动作。
- 本期会话管理只包含创建会话、发送消息、读取用户可见消息和读取脱敏工具调用记录；不提供
  会话列表、用户主动删除或重命名。
- 创建会话不调用 DeepSeek，因此模型不可用时仍可创建；发送消息时若 DeepSeek 最终不可用，
  则不调用工具并返回稳定 `503`。
- 本期不提供写工具、自动确认、自动清单关联、跨项目检索、自动合规判断或运行时多 Agent
  编排。

#### 验收标准

- **AC-FR-042-01**：Given 当前用户拥有项目，When 创建项目档案助手会话并连续发送两条消息，Then
  两轮均在同一稳定线程中执行，且第二轮可读取第一轮的用户可见对话上下文。
- **AC-FR-042-02**：Given 用户询问当前项目有哪些正式验收资料，When 助手调用目录工具，Then
  返回内容只包含当前项目 `CONFIRMED` 且未被可见性阻断的档案摘要。
- **AC-FR-042-03**：Given 用户询问正式档案中的原文事实，When 助手调用原文证据工具，Then
  回答只基于服务端映射的当前项目原文证据，并复用 FR-039 引用中的 `filename`、
  `location_type`、`location_start`、`location_end`、`excerpt` 字段名称与语义；FR-042 的脱敏
  引用 DTO 按 BR-038 排除持久化标识与检索分数，不新增第二套文件、位置或摘录字段定义。
- **AC-FR-042-04**：Given 模型工具参数试图提交或覆盖 `user_id`、`project_id`、`kb_id`，When
  工具执行，Then 这些参数不属于模型可控输入，检索范围仍等于会话的服务端绑定范围。
- **AC-FR-042-05**：Given 证据只存在于待确认档案或其他项目，When 用户在当前会话提问，Then
  助手不得返回、暗示或引用该证据。
- **AC-FR-042-06**：Given 原文工具没有充分依据，When 助手回答，Then 返回明确拒答和空引用，
  且拒答由空候选短路或 D5/D6 结构化判定得出，不使用统一 Reranker 阈值；Given 本轮没有
  任何成功工具调用，Then 服务端不采纳模型自由文本并统一改为无依据拒答。
- **AC-FR-042-07**：Given 用户读取会话历史和工具调用记录，When 请求成功，Then 历史不含内部
  ToolMessage 或不完整轮次，工具记录只包含脱敏参数和结果摘要；When 发送下一轮消息，Then
  模型输入使用同一完整轮次投影，不包含被历史接口隐藏的孤立消息，且每轮最终助手正文与该轮
  HTTP 响应的 `answer` 完全一致。
- **AC-FR-042-08**：Given 客户端请求体包含任一未声明范围字段，或消息去除首尾空白后为空或
  按既定换行规范化后超过 2000 个 Unicode 码点，When 提交请求，Then 返回
  `422 VALIDATION_ERROR`，不创建会话、不执行 Graph 且不写工具记录。
- **AC-FR-042-09**：Given 同一轮工具或模型连接失败触发自动重试并最终成功，When 读取消息与
  工具记录，Then 只存在一轮用户/助手可见消息和每个 `tool_call_id` 的一条工具记录。
- **AC-FR-042-10**：Given 一份文档已进入既有删除可见性阻断，When 目录或证据工具执行，Then
  该文档不可见；FR-042 不新增第二套删除状态机。
- **AC-FR-042-11**：Given 用户删除一个无未删除文档但存在项目档案助手会话的项目，When 删除
  成功，Then 对应会话、Checkpoint 线程和工具记录均已清理，旧会话标识不能继续执行或读取。
- **AC-FR-042-12**：Given 一个制度 Agent 会话 ID，When 通过项目档案助手入口执行消息、读取历史
  或读取工具记录，Then 请求被拒绝且不得读取该会话的 Checkpoint 或审计；反向访问同样拒绝。
- **AC-FR-042-13**：Given 模型在一轮中尝试发起第三次工具调用或一次决策返回多个 Tool Call，
  When Graph 继续执行，Then 停止后续执行并返回 `503 ARCHIVE_AGENT_MODEL_OUTPUT_INVALID`；
  调用不得并行或部分执行。该错误表示服务端依赖的模型输出违反 Graph 契约，不是客户端参数错误。
- **AC-FR-042-14**：Given 模型调用目录工具时提交白名单外筛选、超过 20 的 `page_size`，或调用
  证据工具时试图提交 `top_k`，When 校验工具参数，Then 调用被拒绝、该次调用计入单轮两个
  工具调用上限，且服务端范围与 Top-8 不变。
- **AC-FR-042-15**：Given 目录摘要包含人工登记且无原文证据的字段，When 助手返回目录结果，Then
  工具只返回规定字段及其 `source`、`has_source_evidence`，助手不得把该值表述为原文事实。
- **AC-FR-042-16**：Given 工具或模型最终失败，When 请求结束，Then 返回稳定 `503`，已实际
  发起的同一 `tool_call_id` 最多写一条 `FAILED` 脱敏记录，且不会根据失败文本生成答案；真实连接、
  超时或存储失败使用 `ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`，与 AC-13 的模型输出错误区分。
- **AC-FR-042-17**：Given 目录工具本轮返回 `document_ref`，When 模型回答或用户下一轮追问，Then
  本轮回答的目录来源由服务端按该临时引用映射；证据工具不接受该引用，后续证据查询重新执行
  当前会话项目范围校验。
- **AC-FR-042-18**：Given DeepSeek 不可用，When 用户创建会话，Then 会话仍可创建且不调用模型；
  When 用户发送合法消息且最终重试仍失败，Then 不调用工具并按 AC-FR-042-16 返回。
- **AC-FR-042-19**：Given 证据工具返回候选，When 生成 ToolMessage、Checkpoint、当前响应和
  工具审计，Then 只有请求内编号、文件名、已确认的可空文档标题、位置和摘录进入模型与
  Checkpoint，持久化文档/Chunk 标识及检索分数只存在于请求内映射；文档标题不进入工具审计或
  当前公开引用 DTO，当前响应仍使用 AC-FR-042-03 定义的脱敏引用 DTO。

## 9. 业务规则

| 编号 | 规则 |
|---|---|
| BR-008 | 第一版只有一种普通用户角色，但所有操作保留操作人信息。 |
| BR-009 | 一个项目对应一个知识库，项目是所有业务数据和检索的隔离边界。 |
| BR-010 | 项目名称去除首尾空格后在同一用户范围内唯一。 |
| BR-011 | 只支持文本型 PDF、DOCX、TXT、MD；单文件 20 MB，每项目最多 100 份未删除文档。 |
| BR-012 | 重复只按当前项目内完全相同文件哈希判断；不同项目互不泄露。 |
| BR-013 | 文档只能按第 7.5 节状态和允许的操作流转。 |
| BR-014 | AI 分类、字段、证据和清单匹配都只是建议，不能自动成为正式业务事实。 |
| BR-015 | 标题和类型必须非空；七个字段都必须人工检查，允许空字段需明确接受为空。 |
| BR-016 | AI 非空字段必须有当前文档证据；人工无证据字段必须显式标记。 |
| BR-017 | 字段或证据修改使正式档案进入待重新确认并退出正式检索。 |
| BR-018 | 只有 `CONFIRMED` 档案可以进入正式目录、检索和问答。 |
| BR-019 | 清单满足必须同时存在已确认档案和已确认关联。 |
| BR-020 | 清单名称、类型或阶段变化使关联失效；说明变化不使关联失效。 |
| BR-021 | 必需项未满足为“缺失”，可选项未满足为“未提供”；无清单不输出缺失结论。 |
| BR-022 | 文档物理删除必须清理文件、业务记录、向量和关联，并保留脱敏审计。 |
| BR-023 | 只对连接失败和超时自动重试一次，业务或格式错误不自动重试。 |
| BR-024 | 状态校验、并发版本和幂等规则必须防止重复文档、向量、档案及成功审计。 |
| BR-025 | 审计只保存必要的脱敏操作摘要，不保存正文或模型输入输出。 |
| BR-026 | 第一版只允许虚构或脱敏资料，并提示片段可能发送给外部 DeepSeek。 |
| BR-027 | DeepSeek 不可用时，人工归档、目录、筛选、清单和重复校验仍可使用。 |
| BR-028 | 内置清单是虚构演示规则，不代表法定或行业归档要求。 |
| BR-029 | 从 `PARSED` 或 `SUGGESTION_FAILED` 状态开始人工归档时，必须通过独立动作创建七个字段均为待检查的空白草稿，并转为 `PENDING_CONFIRMATION`。 |
| BR-030 | 项目档案助手会话创建后固定绑定用户、项目、知识库与 Graph 线程；模型和客户端均不能切换其授权范围。 |
| BR-031 | 项目档案助手仅能调用 `list_formal_archives` 与 `search_confirmed_archive_evidence` 两个只读工具；FR-039 直接问答继续保留。 |
| BR-032 | 目录工具只能导航正式档案；文档原文事实必须由证据工具返回的服务端引用支持，人工无证据字段不得作为原文依据。 |
| BR-033 | SQLite Checkpoint 仅保存可序列化的会话消息和 Graph 状态；会话归属、项目绑定及脱敏工具审计仍以 PostgreSQL 为事实来源。 |
| BR-034 | 项目档案助手只接受 `ARCHIVE` 会话；历史 `POLICY` 行不得进入档案入口。任何档案入口都必须校验用户所有权、会话类型及项目绑定。 |
| BR-035 | 同一请求内的连接或超时自动重试不得重复追加用户可见消息或工具审计；客户端主动重发视为新一轮，不提供请求幂等键。 |
| BR-036 | 项目删除成功前必须清理项目档案助手会话、Checkpoint 线程和工具调用记录；MVP 不提供删除与消息并发执行的强一致性保证。 |
| BR-037 | 历史接口和后续模型输入使用同一完整轮次投影：只使用具有最终 AIMessage 的 HumanMessage 轮次，不展示/输入中间 ToolMessage 或任何孤立消息；不新增 PostgreSQL 轮次业务表。 |
| BR-038 | ToolMessage、Checkpoint、用户可见响应和工具审计不得包含持久化文档/Chunk 标识或检索分数；原始候选只存在于当前请求映射。MVP 不新增历史引用表，也不承诺历史消息恢复引用。 |
| BR-039 | FR-039 与 FR-042 必须共用同一个基于既有 Top-8 候选的 D5/D6 结构化判定入口；FR-042 的候选获取不使用统一 Reranker 拒答阈值。 |

## 12. 质量验收

### 12.1 验收资料

- 六个资料分类均需覆盖。
- 每类至少 2 份、目标 3 份，共 12～18 份虚构资料。
- 少量脱敏样本只用于确认真实结构、命名和字段表现。
- 另准备 2～3 份异常样本，覆盖字段缺失、分类混淆、同哈希重复和扫描 PDF。
- 验收资料必须预先人工标注资料类型、可识别字段和标准证据。

### 12.2 AI 分类与字段建议

- 资料类型建议准确率不低于 80%。
- 12 份资料时至少 10 份正确；18 份时至少 15 份正确。
- 人工标注为可识别字段的建议正确率不低于 80%。
- AI 非空字段证据覆盖率为 100%。
- 原文不存在的信息不计为可识别字段，模型不得据此生成值。

### 12.3 检索与问答

至少准备 12 个问题：

- 8 个有明确标准证据的问题，其中至少 7 个检索结果包含标准证据。
- 2 个当前项目无依据问题，必须全部拒答。
- 2 个项目隔离问题，不得泄露其他项目任何内容。
- 最终回答引用正确率必须为 100%，任一错误引用均不通过。
- 不得引用待确认或待重新确认档案。
- Chroma 距离度量类型、分数方向、Embedding、Reranker、候选池与 Top-8 必须使用已冻结的
  P14-D6-B 基线。D4 已证明不存在可行的统一 Reranker 拒答阈值；证据充分性必须沿用 D5
  结构化判定层和 D6 文档绑定/Top-8，不得重新以统一阈值决定回答或拒答。后续改变冻结变量
  仍须遵循 `docs/review/验证冻结清单.md`。

### 12.4 业务闭环

- 正常链路可以从创建项目执行到确认入档、满足清单和带证据问答。
- AI 关闭时可以通过完全手工方式确认入档。
- 删除已满足清单项的档案后，向量、文件、记录和关联被清理，缺失结果恢复。
- 同项目重复、容量超限、扫描 PDF、越权、旧版本并发修改和无依据问答均有稳定结果。

### 12.5 项目档案助手质量

项目档案助手固定集复用 §12.3 的 12 个正式检索问答样本，并新增至少 2 个目录导航问题和
2 组两轮追问。每条样本必须标注会话轮次、允许或必须调用的工具、禁止调用的工具、预期
目录项或引用、预期回答状态及隔离范围；运行时不得读取 Ground Truth。

- §12.3 的 8 个有据、2 个无据和 2 个隔离问题继续验证证据工具、D5/D6 判定与引用安全；
  不因引入 Agent 降低既有 `7/8`、`2/2`、`2/2` 和引用正确率 100% 门槛。
- FR-039 直接问答与 FR-042 证据分支必须调用同一个“既有候选 → 结构化充分性判定 → 服务端
  引用映射”公共函数；固定集需证明两个入口在相同候选上得到相同回答状态、选中相同候选，并且
  `filename/location_type/location_start/location_end/excerpt` 一致。FR-042 排除的内部标识与分数
  不参与响应等值比较；不能以复制实现或第二次检索冒充复用。
- 2 个目录导航问题必须全部调用目录工具、返回正确的正式档案集合，且不得把登记字段表述为
  原文事实。
- 2 组两轮追问必须全部保持同一项目和线程上下文，并满足每轮标注的必需工具与结果；任何一组
  出现跨会话、跨项目或错误引用均不通过。
- 范围字段不可覆盖、会话类型隔离、待确认/删除阻断不可见、工具调用上限和自动重试不重复
  通过确定性测试全部通过；这些结果不替代真实 DeepSeek 工具选择和回答质量评测。
- 固定集内容、运行器和评测维度先由主 Agent 依据本节设计并产生一次基线；所有安全门保持
  100%，其余尚未在本节固定的质量或延迟阈值只能基于基线提出，由用户确认后按
  `docs/review/验证冻结清单.md` 冻结。未完成真实固定集运行前不得宣称 FR-042 质量通过。

## 13. 异常与边界汇总

| 场景 | 预期业务结果 |
|---|---|
| 扫描 PDF 或无有效文本 | 解析失败，提示上传文本版资料，不生成 AI 建议 |
| 文件格式不支持 | 保存前拒绝 |
| 文件超过 20 MB | 保存前拒绝 |
| 项目已有 100 份文档 | 保存前拒绝 |
| 同项目同哈希 | 返回已有文档摘要，不创建重复数据 |
| AI 未配置或关闭 | 禁用 AI 建议和问答，保留人工归档与结构化功能 |
| AI 输出无证据字段 | 该建议不得作为有效 AI 字段 |
| 七个字段未全部检查 | 禁止确认入档 |
| 修改正式字段或证据 | 转为待重新确认并退出正式检索 |
| 清单关联未确认 | 清单项不能视为满足 |
| 无清单 | 不输出资料缺失结论 |
| 无检索依据 | 明确拒答 |
| 跨项目访问 | 拒绝且不泄露资源是否存在之外的敏感信息 |
| 外部连接失败或超时 | 自动重试一次，仍失败则返回稳定错误 |
| 项目档案助手请求含未声明范围字段、空白或超长消息 | 返回参数错误，不执行 Graph 或工具 |
| 项目档案助手工具返回空业务结果 | 按目录为空或无证据拒答处理，不伪装成基础设施错误 |
| 项目档案助手模型输出违反 Tool Call 契约 | 返回 `503 ARCHIVE_AGENT_MODEL_OUTPUT_INVALID`，不执行越界调用 |
| 项目档案助手工具、模型连接、Checkpoint 或 PostgreSQL 最终失败 | 返回 `503 ARCHIVE_AGENT_DEPENDENCY_UNAVAILABLE`，不根据失败文本继续回答；历史与模型输入忽略不完整轮次 |
| 项目档案助手达到单轮工具调用上限 | 停止循环并返回稳定不可用结果 |
| 客户端提交旧版本 | 返回业务冲突，不覆盖较新数据 |
| 跨存储删除部分失败 | 不虚假宣称全部成功，保留可观察失败信息 |

除本需求已明确确认的 `422 VALIDATION_ERROR` 外，具体 HTTP 状态码、稳定错误码和响应 Schema
在后续 `docs/design/接口设计.md` 中定义，不得在需求阶段自行制造未确认的协议细节。

## 14. 数据与安全要求

- 文档、档案、清单、关联、向量、问答和审计必须限定在当前用户与项目。
- Chroma 检索必须包含服务端注入的用户 ID 和项目/知识库 ID。
- Chroma 只能在部署内部网络开放；浏览器和外部客户端不得直接连接 Chroma，必须经由 FastAPI
  完成身份校验、资源授权和范围过滤。
- 客户端和模型不得覆盖资源所有者或检索授权范围。
- 密码只保存强哈希；Access/Refresh Token 不写入业务审计、应用日志或响应以外的持久化记录。
- 受保护接口只接受 Bearer Access Token；不得保留 `X-User-ID` 兼容后门。
- 只允许虚构或脱敏资料，禁止真实商业秘密、个人敏感信息和未授权资料。
- Swagger 和 README 必须提示 AI 相关片段可能发送给外部 DeepSeek。
- 工具和业务审计不得保存完整正文、Token、密码或模型隐藏推理。
- 删除档案后不保留原文、完整字段和可恢复副本。

## 15. 假设与限制

- 第一版面向个人学习和小范围演示，不是档案馆级生产系统。
- 相邻 Vue 工作台是 P14 的本地操作界面；Swagger/OpenAPI 仍用于接口契约检查，不以公开多用户网站为部署目标。
- 文档解析和外部调用采用当前同步后端基础，不在第一版引入任务队列。
- 部署目标为 2 vCPU / 2 GB 的小型云服务器。Chroma 已完成独立服务验证以替代 Milvus，
  但本地 BGE 与 PostgreSQL 同机运行的完整栈内存可行性必须在 AV1-C02 后实测；未实测前
  不承诺该规格可以承载完整链路。
- 20 MB 和每项目 100 份文档是验收前暂定上限；若本地实测需要调整，必须在
  验收版本冻结数值并同步本文档。
- 清单模板和样本均为虚构演示规则，不能用于判断真实项目的法定资料完整性。
- 项目档案助手的 SQLite Checkpoint 只面向当前本地单实例学习环境，不构成多实例共享、
  生产级备份或无限期保留方案；会话与 Checkpoint 的保留、迁移或容量策略若需扩展必须另行决策。
- 项目档案助手 MVP 的模型上下文不设置独立轮数或码点上限；历史与模型输入使用 BR-037 的同一
  完整轮次投影。当前只面向短会话演示，长会话 Token、延迟和成本增长属于已知限制。
- 项目档案助手的历史消息与工具日志读取接口不分页且不设置响应条数上限，只适用于上述本地
  短会话 MVP；若需要长会话、归档或分页能力，必须另行设计。
- DOCX 段落序号和 TXT/MD 行号范围是 V1 的证据定位契约，用于固定原文件下的
  查证；它们不承诺在外部编辑器重新保存文档后保持不变。AV1-P01 已冻结 UTF-8 解码、
  换行/空白归一化、表格/编号列表处理、DOCX 前 50 字辅助定位，以及归一化有效文本
  最小 20、最大 1,000,000 字符的规则，详见 `docs/design/智慧档案V1解析器设计.md`。
